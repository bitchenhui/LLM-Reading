# A Complete End-To-End Open Source Toolchain for the Versatile Video Coding (VVC) Standard

## 1. 背景与动机

VVC（ITU-T H.266 / ISO/IEC 23090-3）于 2020 年 7 月由 JVET（ITU-T VCEG 与 ISO/IEC MPEG 联合团队）定稿。其两项设计目标——相对 HEVC 的可观码率节省与面向多样化内容/应用的通用性——已在独立主观验证测试中得到确认：以朴素观众为被试的受控实验下，HD/UHD 内容平均码率节省超过 40%，360 度视频超过 50%（摘要口径为同等主观质量下约 50%）。

但标准文本与参考软件并不等于可部署的生态。论文指出的三个现实缺口构成本文动机：

1. **参考软件不可实用**：VTM 面向标准验证与压缩潜能评估，未做运行时优化，且编码端缺失真实世界必需特性——码率控制、主观质量优化、并行化、效率/速度可调档位。
2. **系统层集成是落地前提**：VVC 只规定码流语法与解码过程，实际应用必须进入传输层（MPEG-2 TS、ISOBMFF/MP4 track），进而接入 DASH 自适应流。
3. **生态滞后周期**：按历史规律，芯片/设备支持与 MP4 封装播放支持通常在标准定稿后 2–3 年才出现。

本文的核心主张是：借助开源软件（Fraunhofer HHI 的 VVenC 编码器与 VVdeC 解码器、ATEME 的 FFmpeg fork、GPAC 多媒体框架），在 VVC 定稿仅一年后即可搭建“编码—封装—分发—解码—播放”的完整端到端工具链，并给出文件播放与 DASH 流媒体两个可复现的分步教程。这是一篇系统工程/生态型论文，其价值在于把标准化成果压缩到工程可用周期内。

## 2. 方法总览

工具链由四个组件构成，覆盖媒体处理的完整数据通路：

**编码/打包链路**：原始 YUV → VVenC（简单应用 `vvencapp` 或 VTM 风格的专家应用）输出 VVC 基本流 → GPAC（`MP4Box` / filter 管线）完成 MP4 封装（`vvc1` 样本入口 + `vvcC` 配置）、DASH manifest 与分片生成，或 MPEG-2 TS 复用直播；音频轨另行封装合流。

**接收/播放链路**：DASH manifest 或 TS 流 → GPAC 播放器（MP4Client）或 ffplay → 定制 libavcodec（内嵌 VVC 解析、demux 与 MP4-to-AnnexB 转换）→ VVdeC 解码核心 → 渲染显示。

**版本与许可时间线**（均以论文撰写时为准）：VVenC 首发于 2020 年 9 月（VVC 定稿后仅两个月），本文报告 v1.0.0（2021 年 5 月）；VVdeC 最新版 v1.1.1（2021 年 5 月）。两者源码均在 GitHub 以 3-clause BSD 许可发布，明确覆盖商用与非商用场景——这一许可选择是“可被产业直接采纳”的关键工程决策。

**接口形态**：VVenC 内核为 C++，对外暴露 C 库接口并附带两个独立 CLI（易用型与专家型）；VVdeC 同样提供 C 库接口与独立解码应用（基本流 → raw YUV）。C 接口设计使其可被 FFmpeg/GPAC 等框架嵌入。

**分发场景定位**：该链路同时覆盖传统数字广播（DVB-T2/S2 下的 MPEG-2 TS 承载）与全 IP 广播（ATSC-3.0 风格的 DASH/ROUTE 组播，以及巴西 SBTVD TV3.0 技术征集场景）。

## 3. 关键设计

### 3.1 VVenC：从 VTM 血统到实用编码器

VVenC 由 VTM 派生，设计目标是“保持 VTM 高压缩效率 + 显著更快 + 具备真实应用特性”，具体工程手段包括：

- **五档 preset（faster/fast/medium/slow/slower）**：显式的速度/压缩效率权衡。slower 档以不到 VTM 一半的运行时间交付完整 VTM 压缩性能；其余档位以码率增加换更快编码。
- **并行架构**：CTU 行级与帧级并行的组合，提供良好的线程数—时间缩减扩展性；多线程带来的压缩效率退化被描述为“最小”。这直接回应了 VTM 无法利用多核的问题。
- **码率控制**：实现单遍与两遍帧级 RC，均针对多线程操作优化，其中帧级并行“无性能影响”。
- **感知优化（本文最有方法论价值的部分）**：采用加权扩展 PSNR（XPSNR）作为失真度量，用简化的人眼视觉系统模型计算权重，以克服 SSD/SAD 与感知失真相关性弱的固有缺陷。关键在于 XPSNR 可**按块计算**，因而能嵌入块级率失真判决；实现上通过局部量化参数自适应（QPA）落地，并顺带提升码率控制的精度与性能。这是“分析式感知模型进入硬判决回路”的典型路径，区别于事后后处理。
- **语法范围与约束**：当前符合 Main 10 profile（4:2:0、每样本最高 10 bit），面向 SDR 及 HDR/WCG 优化；包含全部 Main 10 profile 屏幕内容编码工具；限制为每图仅支持单 slice、单 tile、无子图。另提供面向 open-GOP 自适应流（含分辨率切换）的约束编码模式，为后续“分辨率切换自适应流”应用预留了编码器侧支撑。

### 3.2 VVdeC：面向直播解码的 VTM 派生解码器

VVdeC 同样自 VTM 派生并做优化与并行化，符合 Main 10 profile 且能正确解码当时的 VVC 一致性测试集（JVET-U2008）。论文坦承：由于 VTM 血统，其性能存在“超出 VVC 标准本身复杂度”的限制——即解码器仍有结构性优化空间。实时性指标：多数现代计算机上仅需 2–3 线程即可 60 fps 播放 HD；60 fps UHD 则需核心数充足的高性能工作站以充分释放多线程潜力。这一“HD 轻线程可达、UHD 需满并行”的分层定位对直播部署选型有直接指导意义。

### 3.3 FFmpeg 侧 VVC 集成（ATEME fork）

分两层推进：

- **主线开发分支（当时评审中）**：实现 VVC parser 与码流类型（CBT）支持，使 FFmpeg 能处理 VVC 基本流，但尚无系统层（MPEG-2 TS / DASH）能力。
- **公开 fork**：在此基础上补齐系统层——libavformat 的 MPEG-2 TS demuxer 增加 VVC 视频流类型；ISOBMFF demuxer 升级支持 `vvc1` tag 与 `vvcC` MOV 表项；libavcodec 中实现 VVC 的 MP4-to-AnnexB 过滤器（即 MP4 长度前缀 NAL 单元到 Annex-B 起始码格式的转换），保证正确 demux 与解码。

由此 ffplay 可直接播放 DASH manifest 或 UDP MPEG-2 TS 流（`ffplay -i URL/manifest.mpd`、`ffplay -f mpegts -i udp://host:port`）；更重要的是该能力经 libavcodec 输出，可被 GPAC 等第三方项目复用——这是工具链各组件之间的耦合方式。

### 3.4 GPAC 侧 VVC 支持

GPAC 基于 filter 架构，其 systems 层 VVC 支持已进入 master 分支与 nightly 构建，覆盖三类用例：MPEG-2 广播（VVC 内容的 TS 复用/解复用）、MP4 封装（VVC 码流导入与导出）、MPEG-DASH 与 HLS 内容打包。播放链路上，GPAC 支持 libavcodec 集成的全部编解码器（含 VVdeC），在 configure 阶段检测，当时需自编译 GPAC + 定制 libavcodec + VVdeC 的完整链条。VVenC 在 libavcodec 集成完成之前，GPAC 通过文件与管道消费其码流输出。

### 3.5 应用层胶水设计

教程中若干细节体现了分发约束对编码器参数的反向要求：HTTP 流式分片每段须以 IDR 帧起始，且固定分片时长要求强制帧结构，因此 VVenC 需以 `--refreshtype idr` 编码；TS 直播示例中因“VVenC 码流可能超出某些码率约束”而以 `rate=10m` 显式整形；live DASH/HLS 示例采用 2 s 分段、0.1 s chunk、1.9 s 可用段偏移与低时延 HLS（`llhls=br`）等参数，展示了该链路对低时延流场景的直接适配能力。

## 4. 实验结果

压缩性能对比口径：JVET 公共测试条件（JVET-T2010）的 HD+UHD 序列、随机访问（RA）条件、PSNR BD-rate，锚点为 HEVC 参考软件 HM-16.22；对比方包括 VTM 12.0、x265 3.4、aomenc 3.0 与 VVenC 1.0.0。注意公平性口径：除 HM 与 VTM 外，其余编码器均以 8 线程多线程运行。文中以文字给出的关键结论如下：

| 对比项（锚点 HM-16.22，JVET CTC HD+UHD，RA） | 结论 |
|---|---|
| VVenC slower 档 vs VTM 12.0 | 压缩效率持平（“完整 VTM 性能”），运行时间不到 VTM 一半 |
| VVenC 多线程 vs aomenc 3.0（AV1） | 稳定约 20% 码率节省，运行时间相当 |
| VVenC 三个较快档（faster/fast/medium）vs x265 3.4 最慢三档（slower/veryslow/placebo） | 编码时间相当，码率节省约 50% |
| VVenC vs x265 更快档位 | 当时无对应速度的 VVenC preset（明确承认的速度覆盖缺口） |

**主观质量（JVET 验证测试）**：VVenC 早期版本（UHD 用 v0.1、HD 用 v0.3）与 VTM、HM 一同在受控实验室环境下由朴素观众评测，结论是 VVenC medium 档叠加主观优化后在视觉上**优于 VTM**。这是“感知优化使实用编码器在主观质量上反超参考软件”的直接证据，也是 XPSNR/QPA 设计的实证支撑。

**解码实时性**：VVdeC 在多数现代计算机上以 2–3 线程实现 HD 60 fps；在核心充足的高性能工作站上实现 UHD 60 fps（口径见 ICIP 2020 论文 [15]）。

**互操作与现场验证**：FFmpeg 播放器已被用于一次端到端 UHD 卫星广播 VVC 现场试验（MPEG 文档 m54377），证明与遗留分发基础设施的互操作性；该组件链亦被用于巴西 SBTVD TV3.0 技术征集的响应方案（以 ATSC-3.0 风格的 DASH/ROUTE 组播 + GPAC 客户端 + libavcodec/VVdeC 接收）。

## 5. 消融要点

本文属工具链/系统论文，**未包含严格的受控消融实验**，但内嵌了三类可作为准消融证据的权衡描述：

1. **preset 阶梯即效率/速度控制变量**：slower 档锚定 VTM 效率（<1/2 运行时间），更快档以码率增加换时间。但各档位相对 HM-16.22 的逐档 BD-rate 数值未在正文给出（文中指向 VVenC v1.0.0 白皮书 [9]），复现者应以白皮书为准。
2. **并行的压缩代价为定性描述**：多线程“最小压缩效率退化”、帧级并行 RC“无性能影响”，均无量化数字；线程数—运行时间扩展曲线亦不在本文。
3. **主观优化（XPSNR/QPA）的贡献未被隔离量化**：其效果由 JVET 主观验证间接支持（medium + 主观优化视觉胜过 VTM），但缺少同版本编码器开/关 QPA 的对照，无法区分“XPSNR 权重的贡献”与“版本间其他改进的贡献”。

未覆盖的量化空白还包括：单遍 vs 两遍 RC 的 BD-rate 与时间差异、VVdeC 相对 VTM 解码器的加速倍数（仅有绝对 fps 指标）。对需要精确复杂度—效率建模的读者，这些空白需回到引用的姊妹文献（白皮书 [9]、ICIP 论文 [15]、VCIP 投稿 [10]）补齐。

## 6. 贡献与启示

**核心贡献**：在 VVC 定稿后一年内交付了首个完整、开源、可商用的 VVC 端到端链路（编码—MP4/TS 封装—DASH/HLS 分发—解码—播放），且其编码器在 slower 档达到 VTM 量级的压缩效率。这把新标准的“可实验周期”从传统的 2–3 年生态等待期压缩到一年以内。

**方法层面的启示**：

- **分析式感知模型可进入块级硬判决**：XPSNR 以简化 HVS 模型做加权、按块计算并嵌入 RD 判决（经 QPA 实现），使 medium 档在主观测试中反超 VTM。这证明在标准语法约束内、不引入神经网络的感知优化路径是可行且高效的，同时还能反哺码率控制精度。
- **系统层标准化可以由开源实现先行**：`vvc1`/`vvcC` 封装、TS 流类型、MP4-to-AnnexB 转换等承载规范在正式产品出现前即有开源参考实现，显著降低生态冷启动成本；FFmpeg fork → libavcodec → GPAC 的分层复用结构是值得借鉴的集成范式。
- **现场级验证的价值**：卫星广播试验与 TV3.0 技术征集表明该链路不是纸面原型，而是经过真实分发基础设施检验的方案。

**局限（论文自述）**：仅支持 Main 10 profile（4:2:0、≤10 bit）；每图单 slice/单 tile、无子图；FFmpeg 主线集成当时仍在评审；GPAC 播放 VVC 需自编译定制三方链；VVenC 快档尚未覆盖 x265 更快 preset 的速度区间；VVdeC 受 VTM 派生结构限制仍有优化空间。**未来方向**：分辨率切换的自适应流、面向 VR 的高分辨率 tile 流——两者分别对应编码器已预留的 open-GOP 约束模式与尚缺的 tile/子图支持。
