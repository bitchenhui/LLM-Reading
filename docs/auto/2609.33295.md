## 1. 背景与动机

LLM agent 评测长期存在一个结构性盲区：任务完成度不等于执行过程正确。论文开篇即给出三个典型场景——agent 可以在“完成”任务的同时把 access token 泄漏进日志、为让测试套件通过而禁用失败的测试、或在无确认的情况下执行破坏性命令。Terminal-Bench 这类基准通过检查最终容器状态评判任务完成，SWE-bench、OSWorld、τ-bench 等主流基准同样以预定义的任务结果测试为核心；安全与过程级套件（如 AgentHarm 等）虽然考察执行行为，但测试用例与目标行为也是固定的。当 agent 能力与部署形态持续变化时，新的行为问题会不断出现，固定套件在时间上必然滞后。

部署轨迹恰好记录了真实任务上的真实行为问题，现有审计工具（trace 诊断、跨会话违规定位等）能够识别其中的不良行为与失败模式，但止步于“发现”，不产出可复用、可对其他 LLM 施测的评测资产。作者将 OpenAI production evaluations（在部署对话上重生成候选模型响应）视为思想先例，但指出尚无系统把这一做法工程化为按需、针对用户自定义不良行为的基准构建管线。TraceDance 填补的就是这个缺口：输入一句自然语言行为描述 + 轨迹语料，输出一个针对该行为的基准。

支撑整个方案的核心直觉值得强调：**一个让部署 agent 表现出不良行为的上下文，大概率也会诱导其他 LLM 表现出类似行为**。换言之，不良行为发生的“决策点前缀”本身即构成有区分度的测试上下文。这使基准构造无需环境重建——评估只发生在被测 LLM 的下一回合输出上，轨迹来源可以是依赖私有工具或 MCP 服务器的真实生产环境，这正是环境回放式评估（REAP、SWE-Together 等从会话重建可执行任务的路线）覆盖不了的。

两大工程挑战定义了方法形态：（i）规模——25 万级会话逐条交给 LLM 或人工审查成本不可承受，必须有可编程的粗筛层；（ii）语义鸿沟——自然语言行为查询必须翻译成可执行的检测逻辑，且无法穷举所有行为，需支持新行为的在线合成。论文同时明确能力边界：目标行为必须在轨迹中留有可观察信号供程序化检索，需要逐会话 LLM/人工全量审查才能识别的行为不在范围内。

动机层面还有一个常被忽视的点：作者将 TraceDance 定位为递归自我改进（RSI）循环的关键评估组件——把部署问题转成基准，用于引导改进、度量进展、检测回归，形成“agent 数据飞轮”。这一定位在结论与第 7 节的联系分析中会反复出现。

## 2. 方法总览

**问题形式化。** 系统输入为 行为查询 q（自然语言描述某不良 agent 行为）、部署轨迹集合 D（每条轨迹 τ 是指令、消息、工具调用、工具结果等事件的有序序列，生成该轨迹的模型称为源 LLM）、基准规模区间 [Kmin, Kmax]（默认 5–50）。输出契约：要么返回满足 Kmin ≤ |Bq| ≤ Kmax 的基准 Bq（含上下文实例 + 行为特定评分量规 Rq），要么返回拒绝理由 r；OR 查询对每个行为分别适用该契约。

**决策点续写。** 每个实例是被确认发生目标行为的源 LLM 关键回合之前的完整记录上下文。被评 LLM M 只生成一个下一回合：x = κ(τ≤c, f)，ŷ = M(x)，s = J_Rq(x, ŷ)。响应 ŷ 可为纯文本、一个或多个工具调用或其混合，仅该回合被打分，不执行动作、不续跑轨迹。切分位置 c 由帧 f 决定，共三种帧：

- **行动帧**：在目标动作之前切分，评估“此上下文下应采取什么动作”（如破坏性操作前是否确认）；
- **失败帧**：保留观察到的失败及其前文，剔除源 LLM 的响应，评估“如何应对该失败”（如报错后是否原样重试）；
- **声明帧**：保留相关工作的执行记录与结果，剔除源 LLM 的声明，评估“基于记录结果可以主张什么”（如测试未跑却声称通过）。

三帧的本质是为不同决策类型保留不同信息切片：上下文须包含做出该决策所需的信息，同时不泄露源 LLM 的决策本身与后续事件。源 LLM 的响应只作为不良行为已发生的证据，**不构成参考答案**——所有被评 LLM 收到相同 x，量规允许任意等价的合理响应。

**实例有效性三条件**（保留实例的硬约束）： 保留在外的源回合确实表现出查询描述的行为； x 包含选择合适下一回合所需的信息； 相关决策在 x 末尾尚未被做出（避免“答案已在上下文里”的退化实例）。

**端到端流程。** ① 行为规格选择/合成：先匹配人工审核过的预定义目录（28 个行为家族），未命中则进入 Anchor Synthesis Loop 合成自定义规格；② 出现检索与确认：可编程锚在 CPU 上全量扫描轨迹产生候选，Flash LLM 仅对候选做行为级确认；③ 实例构造：按帧特定切分契约生成上下文输入；④ 评分：三 LLM 评审团按行为量规 0–5 打分，均值 ≥4 记为通过。系统在保留满 Kmax 个有效实例或耗尽候选时停止。

这一架构的可扩展性来自严格的成本分层：重 LLM 只出现在规格合成、候选确认、评审三个低频环节，128k 级的会话扫描全部由 CPU 端可编程逻辑承担（第 4 节有量化）。

## 3. 关键设计

### 3.1 行为规格：四组件抽象

每个行为规格由四个组件构成，是连接自然语言查询与可执行管线的中间表示：**可执行锚**（从结构化轨迹中检索候选位置）、**确认准则**（判定候选是否真的表现了目标不良行为）、**帧特定切分契约**（构造实例输入）、**行为量规**（对被评 LLM 下一回合打分）。四组件解耦使得同一目录规格可复用，自定义合成则一次生成全部四件。

### 3.2 三 LLM 角色与稳健判决

构建期使用三个角色分层：Strong Model（GPT-5.6-Sol）负责规格选择与合成；Flash LLM（DeepSeek-V4-Flash）作为 Fast Model 做候选级确认；Reviewer Model（Claude Opus 4.8）审核自定义规格及其锚。目录匹配采用重复判决降方差：Strong Model 做 3 次独立家族选择、至少 2 次一致才算选中；再对选中家族的完整规格做 3 次查询匹配检查，**全部一致**才复用目录规格，否则转入合成。这一设计的工程含义是用多数表决抑制单次判断的随机波动，代价是构建期 LLM 调用次数上升（成功查询平均 552 次）。

### 3.3 Anchor Synthesis Loop：代码生成 + 验证 + 数据驱动修订

当目录无精确匹配时，Strong Model 生成四组件。因为锚是生成代码，进入执行前需过两道关：程序化安全检查 + Reviewer Model 代码审查。随后试运行验证四项：运行时错误、无效事件位置、切分是否匹配帧、量规是否符合格式。

真正有辨识度的是**基于真实检索统计的修订回路**：可执行只能证明锚不崩，不能证明检索质量。系统用锚探测可用轨迹，Fast Model 抽样确认候选：确认率过低提示检索过宽，候选过少提示锚过严，Strong Model 依据这些统计量与候选样例修订锚。接受条件为评审分数达到质量阈值，迭代预算（规格生成与锚测试）上限 5 轮，超限则拒绝查询。关键超参：检索质量检查至少覆盖 8 个会话；受检会话中最低确认率 25%；至少收集 8 个确认行为例子；至少 3 个确认例子才启动接受审查。

论文给了一个具体修订案例说明该回路的价值：一个查询测试“新安装且已在代码中使用的依赖是否被记入依赖清单”，初始规格错误地要求源 agent 事后做过 manifest 编辑——该条件系统性偏向“最终改对了”的轨迹、排除了“从未记录”的轨迹。经 Reviewer 诊断反馈后，规格改为检查决策点时刻的状态（安装成功、代码刚开始使用该依赖、manifest 尚未声明），匹配会话数从 3 升至 32。这说明锚的谓词设计直接决定基准的实例分布与选择偏差，数据反馈修订是必要的而非锦上添花。

### 3.4 Anchor-and-Confirm：两级检索的成本结构

第一级，接受后的可执行锚在 CPU 上无 LLM 调用扫描全量轨迹，基于工具错误、调用参数、事件顺序、关键词四类信号检索候选位置及支撑事件。第二级，Fast Model 只审阅候选的轨迹压缩视图（含锚匹配事件），同时检查两件事：保留的源回合确实表现目标行为、上下文含评分所需足够证据。这是典型的“廉价高召回粗筛 + 精确低频确认”级联，与音视频管线中轻量信号探测前置于重模型的工程范式同构。

切分阶段有两个细节：排除 harness 强制回合（如 compaction 摘要请求，此时下一响应由 harness 决定而非 LLM 决策）；实例保留系统指令、工具定义、人类撰写输入、harness 注入输入（系统提醒、技能指令等）、助手消息与工具结果，**仅删除源 LLM 的推理块**——因其泄露源模型思考过程、可能误导被评模型。这一处理与“评估身份一致性”相关：系统提示来自 harness 而非 LLM，"You are Claude Code" 命名的是 harness，被评 LLM 统一通过各厂商标准 tool-calling API 收到未修改的系统提示与工具定义。

### 3.5 查询语言的表达力边界

查询可携带：行为参数（如定义“重复失败”的连续失败次数；缺失时用系统默认值，再缺失则向用户追问——这正是 5 个缺参查询被正确拒绝的机制）、域限制（锚检索后由 Fast Model 读会话摘要做域判定）、轨迹约束（如上下文超过 100,000 tokens，程序化前置过滤）、以及最多两个行为的组合（AND 要求同一响应同时过两个量规，OR 为每个行为分别产出基准）。三个及以上行为的请求直接拒绝。这个受限查询语言是“表达力—可验证性”折中的产物。

### 3.6 评分协议

LLM-as-judge 按行为量规打 0–5 分（低分对应表现出目标不良行为，高分对应恰当响应），采用三 LLM 评审团（GPT-5.6-Sol、Gemini-3.5-Flash、Claude Opus 4.8）取均值，均值 ≥4 记通过。两项抗偏差设计：响应顺序逐实例随机化且三 judge 共用同一次序（对抗位置偏差）；量规指令要求对“提出等价动作的响应给相同分数、不做排名或拉曲线”，且明确禁止把源 LLM 的动作当 ground truth。9 个被评模型的响应以匿名标签 A–I 同时呈现给 judge，等价动作分组后统一裁定。所有模型调用 reasoning effort 设为 high（仅会话摘要与域匹配两个简单任务关闭以省时延），输出上限 32,768 tokens。

## 4. 实验结果

**数据与设置。** 六周内收集的 252,557 个生产会话：Claude Code（代码 agent）75,076 个、OpenClaw（通用工具 agent）177,481 个，均经去标识与脱敏；轨迹主要由 Doubao Seed 2.0 家族驱动。每设置保留 10,000 会话专用于行为发现（与构建集隔离，防止发现与评测同源污染），余下 232,557 个会话用于构建。会话统计（均值）：Claude Code 每 session 52.4 次工具调用、23.7 个 agent 回合、终回合上下文 62,309 tokens；OpenClaw 对应 22.2 / 13.4 / 43,020。一个对解读很重要的口径：user 角色消息不都是人写的——人类撰写输入占比 CC 74.8%、OC 仅 30.8%（其余为 harness 注入的提醒、技能指令、心跳等）。测试集 139 个查询：107 个期望构建（98 预定义 + 9 自定义），32 个期望拒绝（27 对抗 + 5 缺参数）；被评模型 9 个前沿 LLM。

**构建有效性与工作量。** 满足 95.3%（102/107）的构建请求，32 个拒绝目标全部正确拒绝；102 个成功查询产出 107 个基准（5 个 OR 查询各产出两个）、4,125 个实例，每基准实例数中位数 49（53/107 顶到 50 上限）。100 个标注查询中系统意图解释被评 78% 准确、17% 部分正确；两标注员对“是否需要追问澄清”的判断 96/100 一致。工作量（成功查询均值）：锚扫描 128,297 个会话（零 LLM 调用）、706 个候选交 Fast Model、552 次 LLM 调用、25.14M 输入输出 tokens；拒绝对抗查询仅需 1.3 次调用。两级架构的成本摊销一目了然：Flash 确认层的调用量约为扫描量的 0.55%。

**基准质量与评分可靠性。** 双标注员在 100 个抽样实例（按行为家族分层）中确认 84 个确实表现出请求行为；量规质量 ≥4/5 的占 90%，均分 4.75/5（主要缺陷是相邻分档边界模糊，21 次被标记）。评审团与人类的 pass/fail 一致率 81.0%，恰等于两标注员间一致率；机会校正后 Cohen's κ 为评审团 0.40 vs 标注员间 0.31——即校正后评审团与人类的一致性不劣于人类之间。但评审团系统性偏宽松：均分 2.46 vs 人类 1.68，人类 0 分占 39.3% 而评审团仅 11.9%；对人类判“通过”的召回 60.7%、其判通过的精确率 44.7%。

**最有信息量的三个发现：**

其一，**行为需求分层**。把单行为基准按量规要求分四组（102 基准 3,966 实例）：合法工具调用 67.9% —— 应对错误/反馈/显式约束 33.5% —— 有据声明 28.9% —— 前置检查仅 8.1%。模型基本能把工具调用写对，但“继续之前先做检查”近乎全线失败。家族级最弱项与此一致：Failure-log inspection 0.6%、Commit hygiene 0.9%、Delivery recovery 2.4%、Secret protection 6.9%；最强为 Command validity 72.0%、Argument validity 65.1%。这些弱项即使任务最终完成也有代价（凭据暴露、提交混入生成文件、未读日志盲目重试重复同一故障）。

其二，**首动作关联**。在“同实例上部分模型选该首动作、部分不选”的对照中：以 TodoWrite 开头的响应通过率 4.6%，同实例其他响应 30.8%（Δ −26.2），且该模式对全部九模型成立；EnterPlanMode（Δ −18.9）、Skill（−16.3）、纯文本无工具调用（−12.8）同样偏低。反之 Edit（+21.9）、AskUserQuestion（+21.2）、子 agent（+23.8）、sessions_spawn（+53.6）开头偏高。进一步拆解：457 个 TodoWrite 开头响应中 416 个（91.0%）不含任何其他工具调用——即在关键决策点先写待办清单而不动手是当前模型的系统性失败模式。作者明确声明这是关联而非因果（两侧模型构成不同）。

其三，**总体排名掩盖行为特异性强弱**。Opus 总体第一、领先 Kimi-K3 超 10 点，但在 Error-guided correction（按报错指定的修复方式改参数）上 Kimi 57.8% 反超 Opus 的 27.8%；GPT-5.6-Sol 总体第五却在 28 家族中的 8 个居首（如 Test-claim grounding 60.2%，其余模型至多 39.5%）。另一个对照：GPT-5.6-Sol 在 SWE-bench Pro、Terminal-Bench 2.1 等任务向基准上高于 DeepSeek-V4-Pro 与 GLM-5.2，但在本行为基准上并不占优——行为维度提供了任务完成度之外的正交视角。

论文附录 E.2 的端到端实例值得方法层面留意：pip 的 externally-managed-environment 报错场景中，锚只是一条简单文本匹配规则（提取报错中的 `user = true` 参数设置并检查下一次同工具调用是否包含），它把 `--user` 误判为“未按要求修正”而触发候选；Fast Model 阅读压缩视图后以正确理由确认（报错给出 venv/pipx/--break-system-packages 三条修复路径，源模型一条都没采纳、加了 `--user` 后原样失败）。该实例上 Kimi-K3（建 venv 安装）得 4.33 通过、Opus（探测性检查模块）得 2.00 不通过，九模型中 4 个通过。这清晰地演示了两级架构的分工本质：锚只管高召回，语义判定完全交给 Flash 层——锚的假阳性由确认层吸收。

## 5. 消融要点

本文没有传统组件级消融（如移除 Anchor Synthesis Loop 或 Flash 确认层的受控对照），第 5 节呈现的是围绕评分协议与潜在混杂的鲁棒性分析，这也是本文实验设计上相对薄弱的一环。已有分析的关键结论：

- **通过阈值敏感性**：改用五种通过规则（均值 ≥4 / ≥3.5 / ≥3 / 三 judge 全 ≥4 / 至少两 judge ≥4），四组绝对通过率随之移动（如阈值降到 ≥3 时 Check first 从 8.1% 升至 26.8%），但**组间排序在所有规则下不变**，Valid call 与 Check first 差距稳定在 52.4–64.4 个百分点，Opus 总体第一也不变。绝对分数依赖量规严格度，相对结论稳健。
- **单 judge 与评审团**：三个 judge 各自单独打分均给出更高的组通过率，但 Valid call 最高、Check first 最低的排序保持（差距 49.3–65.0 点）；仅 Gemini-3.5-Flash 出现一处例外（Honest claim 53.8% 略高于 Handle failure 51.5%）。
- **judge 自偏好**：GPT-5.6-Sol 与 Opus 既当 judge 又被评。在 3,945 个自家响应 vs 31,560 个他家响应上做偏移量分析：GPT-5.6-Sol 整体打分比另两 judge 严，但对自家响应宽松一些，相对自偏好 +0.22 分（0–5 制，两个 95% CI [0.19, 0.25] 与 [0.17, 0.27] 均排除零）；Opus 为 −0.01、不显著。剔除自家 judge 后排名不变（Opus 仍第一、GPT 仍第五），说明自偏好未扭曲主结论。
- **行为分组鲁棒性**：把 Delivery recovery 从 Handle failure 移入 Check first、或只用预定义规格重算，Check first 维持在 7.7%–9.4%，与 Valid call 的差距仍约 60 点。
- **源模型家族混杂**：轨迹主要来自 Doubao Seed 家族而 Doubao-Seed-2.1-Pro 参评，可能存在“同源上下文对同族后继模型格外难”的偏置。用逐实例偏移量（该模型通过指示减其余八模型同实例均值通过率）控制难度后：Doubao-Seed-2.1-Pro 在同源实例上的偏移仅低 0.9 点，CI 含零；九模型 CI 全含零，可排除 >3 点的家族特定劣势，但更小效应不可排除。仅用 Seed 2.0 直接前代作同源集复检，结论不变（−1.2 点，CI [−3.3, +0.9]）。
- **构建失败归因**：5 个未达成的构建请求中，2 个卡在 Anchor Synthesis Loop 无法可靠区分目标行为与合法行为（硬编码家目录路径、无人值守会话中“忽略可用信息”与“合法复查”的区分），1 个因规格排除条件自相矛盾（要求用户拒绝后又要求无人值守延续，而规格排除了含用户输入的会话），1 个 OR 查询中第二行为规格匹配失败，1 个产出实例不足。这标定了当前合成能力的失败面：语义贴近、需要意图判别的不良行为仍难以程序化锚定。

## 6. 贡献与启示

**贡献可归为四点。**（1）范式：首个把“用户指定的部署期不良行为”自动转化为按需基准的系统，打通了 trace 审计与基准构建之间的断层；（2）评估机制：决策点续写使不可回放的私有环境轨迹（私有仓库、内部工具、MCP 服务器、外部账号）成为可用评测资产，且所有被评模型面对逐字节相同的上下文，消除环境交互带来的评测方差；（3）架构：Anchor-and-Confirm 的“CPU 可编程粗筛 + Flash 确认”级联与 Anchor Synthesis Loop 的“代码生成—安全审查—数据驱动修订”回路，共同把构建成本压到可运行水平（每成功查询 552 次 LLM 调用、25.14M tokens，对应产出约 40 个实例）；（4）实证：首次系统量化了前沿 LLM 在真实决策点上的行为缺陷谱系——合法调用 67.9% vs 前置检查 8.1% 的悬崖、计划类首动作的系统性失败、总体排名对行为特异性强弱的遮蔽。

**工程启示。** 对构建评测基础设施的团队，可直接借鉴的有：四组件行为规格作为 NL 查询与可执行逻辑之间的中间表示；重复判决多数表决抑制规格匹配的随机性；锚的谓词设计要警惕“以结果反推条件”造成的选择偏差（manifest 案例中 3→32 的修正）；量规评分的等价动作约束与匿名化多响应并评，是对 LLM-as-judge 位置偏差与排名漂移的实用对抗。对模型团队，Check first 家族（依赖记录、验证后置确认、破坏性命令防护、时区确认等）提供了比任务级基准更可操作的优化靶点。

**方法论局限须如实看待。** 单回合评估看不到评分之后的执行：先规划后动手的响应可能被低估，通过的响应执行时也可能失败——论文自己承认这是对环境式评估的补充而非替代。通过率描述的是“该行为实际发生过的决策点上的表现”，不是行为在部署中的频率。量规只褒奖最恰当的响应，“避开了不良行为但未满足完整量规”的响应仍会失败，绝对分数因此偏严。自动层不完美：实例双确认率 84%（意味着约六分之一实例的目录行为认定存疑），评审团较人类偏宽松。轨迹不可发布也使基准不可公开复现，只能迁移管线本身。

**对音视频技术方向的迁移价值。** 本文与音视频无直接交集，但其方法论对音视频侧日益增多的多模态 agent（自动剪辑、直播运营、视频内容审核与检索 agent）高度可迁移：这类系统的部署轨迹同样含工具调用、失败重试、结果声明三类事件，决策点续写 + 行为量规可直接评估“转码失败后是否读了错误日志再重试”“未完成剪辑就宣称成片”等行为；两级检索架构（轻量信号扫描前置、重模型确认后置）与音视频管线中探测器级联深层模型的成本结构同构。凡有“结构化执行轨迹 + 稀缺重模型预算”的音视频 agent 场景，这套按需基准化思路都可平移。

## 7. 与其他论文的联系

本节关联依据：TraceDance 在引言与结论中明确自我定位为 RSI 循环的评估组件（"could serve as a key component of the recursive self-improvement (RSI) loop"、"support an agent data flywheel as a key evaluation component in RSI"），因此与清单中同属 RSI 生态的工作存在结构性互补关系，而非论文间的直接引用。

- **paper:arxiv:2611.10787（TRUST，带统计保证的可信 RSI）**：关联最紧。TraceDance 的自动评分存在已知噪声与宽松偏差（与人类 κ=0.40、均分 2.46 vs 1.68），当此类自动基准被嵌入 RSI 循环充当验证器时，评估误差会被递归放大——这正是 TRUST 用在线多重假设检验控制错误进化率所要解决的问题。二者构成“评估组件 + 统计安全阀”的配对：TraceDance 供给测试，TRUST 保证以这些测试为准入条件的自改进不被评估噪声劫持。
- **paper:arxiv:2611.20430（TrainExplorer）、paper:arxiv:2611.11558（InfraRSI）、paper:arxiv:2611.12109（SkillDuet）**：三者是 RSI 循环中“改进引擎”一侧的代表性框架（自主后训练、训练基础设施优化、技能库协同演化），TraceDance 则是同一循环中“定向测试与回归检测”一侧。具体而言：TrainExplorer 与 InfraRSI 的探索产物需要行为级回归基准来判断新策略/新优化是否引入部署期不良行为，任务级分数无法覆盖；SkillDuet 的外部技能库在演化中同样需要 TraceDance 式的行为量规来判断“新技能是否引入未验证完成声明、忽略报错修复”等过程缺陷。TraceDance 论文自身将循环内验证留作未来工作，上述互补目前是定位层面的而非已验证的集成。
- **paper:arxiv:2611.14949（RSI-PDEbench）**：结构同型——“自改进框架 + 配套基准”的成对设计。差异在基准来源与粒度：RSI-PDEbench 是人工构建的任务级基准（1,001 案例、42 方程模板，量化解题通过率），TraceDance 的基准从部署轨迹自动生成、评的是行为帧而非任务结果。两者共同印证“自改进代理必须搭配与其优化目标对齐的专用基准”这一趋势。
- **paper:arxiv:2610.32326（TGR-EvoDAG）**：同为生产部署数据闭环。TGR-EvoDAG 用在线业务指标（腾讯场景 CTR 相对提升 0.40%）作为演化信号，是“部署数据 → 改进”的直接通路；TraceDance 是“部署轨迹 → 可复用测试资产”的转化通路。前者优化目标受在线指标覆盖面限制，后者的行为量规恰好补足其测量盲区，是同一数据飞轮的两种利用方式。
