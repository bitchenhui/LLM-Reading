# FullStack-Agent: Enhancing Agentic Full-Stack Web Coding via Development-Oriented Testing and Repository Back-Translation

> 本笔记由引擎自动深读生成（glm-5.3, pipeline deep_read v1），底稿：全文文本

## 1. 背景与动机

自然语言驱动的网站生成已成为 LLM 代码智能体的主流任务，但现有系统（bolt.new、lovable.dev 等商业产品及 WebGen-Agent、TDDev 等研究工作）普遍只产出前端页面，用视觉交互的"表演"掩盖真实数据流的缺失——论文给出的典型失败形态是：表单可提交、成功提示正常弹出，但因缺少后端与数据库实现，没有任何数据被实际处理或存储。此外大量方法（Design2Code、Interaction2Code 一系）只生成单个 HTML 文件或极简代码库，不具备生产环境可扩展性。

论文将生产级 full-stack 生成的困难归结为三点：(1) 真实框架（Next.js、NestJS）代码库庞大复杂，要求高效代码导航与对隐蔽错误的精确定位与修复；(2) full-stack 工作流要求长程推理、熟练工具调用与对不断更新的 web 包的专家级掌握，当前骨干 LLM 在这些方面仍有明显差距；(3) 评测侧存在系统性盲区：WebGen-Bench 等基于 GUI-agent 的判分只看 UI 层交互，无法检出"前端效果正确但后端缺失/伪造"的假阳性。

方法论的动机判断在于：框架、模型训练、评测三者必须共同演进——没有可信评测则自我改进无锚点，没有数据引擎则框架上限受制于骨干模型。FullStack-Agent 据此提出三个紧耦合组件（开发框架 FullStack-Dev、训练管线 FullStack-Learn、评测基准 FullStack-Bench），从系统工程视角而非单点算法视角切入，这是本文区别于前作（同团队 WebGen-Agent/WebGen-Bench）的核心立意。

## 2. 方法总览

**FullStack-Dev（多智能体开发框架）**：Planning Agent 充当架构师，将用户指令转为 JSON 格式的前后端计划（backendPlan 含 entities/apiEndpoints/businessRules，frontendPlan 含 pages/dataFlows/sharedComponents 等），所有数据结构定义下沉到最细粒度类型（如 integer、`array<string>`、`object<{{field:type}}>`）。执行顺序为后端先行：Backend Coding Agent 完成后端并输出 API 构建摘要，Frontend Coding Agent 再基于真实 API 构建前端——该顺序从结构上杜绝前端使用 mock 数据。两个编码智能体共享 10 类工具（读文件、写文件、列目录、glob、内容正则搜索、批量读、shell 执行、精确字符串替换，以及两个专用调试工具），运行在沙箱环境中保证隔离与执行稳定性。

**FullStack-Learn（数据扩展与自我改进）**：核心是把 GitHub 爬取的真实仓库"反向翻译"为智能体轨迹。Information Gathering Agent 用导航/读文件/代码搜索工具产出仓库摘要（描述、0–5 质量分、前后端计划、一条能合理产出该仓库的用户指令）；Trajectory Back-Translation Agent 在"原仓库 + 同框架空模板"的工作区中，按高层计划将原仓库内容转录进模板；随后一个规则化程序（附录 C 算法 2）清除全部原仓库痕迹并重放工具调用，得到干净的开发轨迹。Repository Augmentation 对每个仓库生成 5 个增强计划（1 简化、1 扩展、3 个结构相似的应用迁移），实现后经调试工具与终局验证过滤，使仓库数量扩展 5 倍。迭代流程：M0 对爬取仓库回译得 D0（2K 轨迹）→ SFT 得 M1；M0 做增强得 Raug，用 M1 回译 Raug 得 Daug（8K）；最终在 D0∪Daug（10K）上从 M0 重新 SFT 得 Mfinal（注意终轮从 M0 而非 M1 起训，避免两轮数据的复合偏置）。

**FullStack-Bench（full-stack 评测）**：复用 WebGen-Bench 的 101 条用户指令与 647 条前端测试用例，新构 604 条后端与 389 条数据库用例（LLM 标注 + 人工精修）。三级判分互为印证：前端由 GUI-agent 判 YES/PARTIAL/NO，精度公式为 (N_YES+0.5×N_PARTIAL)/N_Total，但 YES/PARTIAL 仅当数据库交互检查通过才计入；后端判分智能体先收集全部 API 端点信息（同一站点的多条用例复用该收集过程以省算力）再发请求验证；数据库测试抽取每张表的列名与前 5 行构成 JSON 快照交判分智能体判定。

## 3. 关键设计

**3.1 类型化计划契约**。Planning Agent 的 JSON 计划是前后端之间的强类型接口契约：嵌套 object 需展开到字段级类型、静态路由必须排在动态路由（如 `/api/contests/{{id}}`）之前以避免路由误匹配、计划中禁止出现具体框架名（框架选择由外部模板机制决定）。这保证了前端 dataFlows 中引用的每个 endpoint 都在后端计划中有完整 requestSchema/responseSchema，是"数据流顺畅"的形式化保障，也是后端摘要可直接对接前端开发的原因。

**3.2 Frontend Debugging Tool：有监控的 GUI 调试**。工具接收一条测试指令，自动启动站点服务，由 GUI agent 驱动 Chromium 交互，同时紧密监控终端与浏览器 console 输出；一旦检出错误，向 GUI agent 追加消息要求其定位触发错误的动作并连同错误信息返回给编码智能体。与 WebGen-Agent/TDDev 的两点本质差异：(i) 前者"盲交互"只产生粗粒度观察，本工具以错误消息 + 网站反应双通道定位问题；(ii) 前者在编码开始时预定义测试用例并反复回放，本工具根据当前开发状态动态生成测试用例。验证提示词还强制"每次调用只测一个原子特性"，保证错误归因的局部性。该工具同时输出 1–5 分的功能分与外观分，直接服务于轨迹过滤与外观调优。

**3.3 Backend Debugging Tool：内嵌 Postman**。输入 URL、请求方法与请求数据，自动启动服务、发请求、返回响应与后端 console 输出；若日志中始终未出现 host:port 则直接判失败。工程含义明确：把"起服务—curl—读日志"的多步 shell 链条压缩为单次工具调用，消除中间失误。论文报告移除该工具后 Backend Coding Agent 平均迭代次数从 74.9 升至 115.5（约 +54%），是全文最直接的效率证据。

**3.4 回译轨迹的规则化清洗（算法 2）**。七步流水线：工作区归一（全部文件系统引用重写至调整后项目路径 w，含自然语言文本与工具参数）→ 提示词规范化（将阶段任务消息替换为由用户指令、计划、脚手架指导派生的标准编码提示）→ 叙事清理（抹除旧仓库引用）→ 剪除依赖旧仓库的工具调用 → 确定性重放环境初始化 → 按时间序重放状态变更类动作、重算检查类动作的输出并存入替换映射 M → 注入修正后的工具输出。关键洞见在于：由于转录由高层计划引导、动作顺序天然接近"先读文件再实现"的开发序，规则化转换不打断逻辑连贯性；重执行保证了轨迹中每条工具输出都对应真实重放后的项目状态，杜绝轨迹与状态漂移。

**3.5 三通道轨迹过滤**。每条轨迹派生三类分数：外观分与前端功能分（1–5，来自前端调试摘要）、后端功能分（响应码 200 且数据非空记 1，200 但空记 0，非 200 记 −1）。聚合公式 s_agg = Σ γ^(N−i)(s_i − s_thresh)，γ=0.9 使越早的调用权重越低（迭代调试后期状态更能代表成品质量），外观/前端阈值取 3、后端取 0，三类聚合分全部大于零才保留轨迹。另对 FullStack-Bench 做去污染：用户指令 5-gram Jaccard 相似度 >0.6 或句向量余弦 >0.7 的轨迹剔除。

**3.6 数据库日志门控评测**。前端交互期间数据库写入的日志条目被抽取，在 GUI 测试会话末尾追加校验消息，按"查看类操作应有 SELECT、修改类操作应有 INSERT/UPDATE/DELETE、纯导航可不触发"的准则判定数据库交互正确性——这一门控正是击穿"假成功提示"失败模式的机制核心，也是前端/后端"w/ Valid DB"指标与裸指标分离的原因。

## 4. 实验结果

推理配置：贪心解码、上下文 131,072、最多 400 次工具调用。基线（WebGen-Agent、TDDev、OpenHands、Bolt.diy、Qwen-Code）统一用附录 E 提示词显式要求生成含 PostgreSQL 后端的 full-stack 站点（指定 DB_HOST 等环境变量、`npm run install:all`/`npm run dev` 约定），保证对比公平。

480B 骨干关键行（FE/BE 均为 w/ Valid DB 口径，Appearance 为 1–5 分）：

| Framework (Qwen3-Coder-480B-A35B) | FE Acc. | BE Acc. | DB Acc. | Appearance |
|---|---|---|---|---|
| WebGen-Agent | 56.0 | 39.6 | 62.0 | 3.63 |
| OpenHands | 40.4 | 35.8 | 72.5 | 2.66 |
| Qwen-Code | 36.2 | 25.8 | 68.4 | 2.40 |
| **FullStack-Dev** | **64.7** | **77.8** | **77.9** | **3.72** |

相对前 SOTA WebGen-Agent 分别提升 8.7 / 38.2 / 15.9 个百分点。值得注意的结构性差异：基线普遍 BE 低于 FE（显式要求后端仍倾向用 mock 数据顶替），FullStack-Dev 则 BE 高于 FE；OpenHands 的 DB 裸分 72.5 尚可但 BE w/ Valid DB 仅 35.8，说明三级测试有效解耦了"建了表/种子数据"与"API 真正读写数据库"两类能力。30B 骨干上 FullStack-Dev 得 37.2 / 38.7 / 50.9（WebGen-Agent 为 35.8 / 16.6 / 14.4），小模型下后端优势进一步放大。

FullStack-Learn 两轮训练（Qwen3-Coder-30B-A3B，2 epochs、LR 2e-5、batch 32、32×H800）：

| Model | FE w/DB | BE w/DB | DB | Appearance |
|---|---|---|---|---|
| 30B base | 37.2 | 38.7 | 50.9 | 2.97 |
| round1（爬取 2K） | 42.3 (+5.1) | 45.4 (+6.7) | 51.2 (+0.3) | 3.32 |
| round2（2K+增强 8K） | 46.9 (+9.7) | 48.2 (+9.5) | 53.7 (+2.8) | 3.40 (+0.43) |

全程不依赖任何更强模型，纯自我改进。模板扩展实验（附录 B）加入 Vue.js/Django 后 FE w/DB 68.1、BE w/DB 78.5、DB 81.0、Appearance 3.58，各精度小幅上升（作者归因于模板选择空间增大后可挑更顺手的栈），外观分略降。错误分析（300 例，六个智能体各抽 50）：前端错误中 Functionality Not Implemented 29.7%、Unresponsive Component 23.7% 合计过半；后端错误中 No Database Interaction 34.3% 与 API Not Implemented 33.3% 并列主导；数据库错误中 Database Empty 高达 46.7%（未初始化库是最普遍问题）。评测可靠性：前端/后端/数据库各随机抽 200 例，4 名计算机相关学士人工核查（仅当评测轨迹与数据库日志完全支持结论才记正确），人机一致率 90.5% / 94.0% / 97.5%。

## 5. 消融要点

**框架组件消融（480B）**：去多智能体机制（单 agent 全干）→ 62.1 / 61.4 / 63.5，全指标下滑，验证规划-前后端分工的必要性；去 Backend Debugging Tool → BE w/DB 从 77.8 跌至 57.9（−19.9），且迭代数 74.9→115.5；去 Frontend Debugging Tool → FE w/DB 从 64.7 跌至 51.9（−12.8）、外观分 3.72→3.17；两个调试工具全去 → 51.0 / 61.9 / 74.8。两个工具各自命中其职责侧指标，交叉影响小，说明误差定位通道是解耦的。

**数据生成方式消融（30B）**：从 WebGen-Instruct 随机采指令直接生成 2K 轨迹做 SFT，FE w/DB 36.2 / BE w/DB 33.6 / DB 47.8 / 外观 2.87——相对不训练（37.2 / 38.7 / 50.9 / 2.97）整体不升反降；同为 2K 规模的回译数据则达 42.3 / 45.4 / 51.2 / 3.32。这是全文最有信息量的消融：同等数量下，真实仓库承载的工程知识是自产指令数据无法替代的，且未经真实代码锚定的自我生成数据存在负收益风险（可能固化模型自身的坏习惯）。

**可信度边界**：前端判分人机一致率最低（90.5%），GUI-agent 判分仍是整条评测链最薄弱环节；数据库判分 97.5% 最稳，与其基于结构化快照的判分形态一致。

## 6. 贡献与启示

按软件工程/LLM 智能体领域标准评估，本文贡献有三层： 上游评测方法——数据库日志门控把"不可验证的 UI 断言"转化为"可验证的数据流证据"，直接堵死假阳性通道，且该机制同时服务于评测（Bench）与数据质控（Learn 过滤），一体两用； 中游数据引擎——回译把"存量工程资产→训练轨迹"打通，配合算法 2 的重放式清洗解决了轨迹-状态一致性，对一切存在大量存量代码资产的领域具有通用配方价值； 下游框架——后端先行的执行序 + 类型化计划契约 + 双调试工具，是可复用的工程模式。

局限亦应如实指出：主实验仅用 Next.js+NestJS 两个模板（作者以结果稳定性与训练成本为由，附录 B 补充实验证明可泛化）；自我改进仅两轮 SFT、无 RL 阶段；30B 上 DB 精度只提升 2.8 个点，数据库侧（尤其初始化习惯）是最难迁移的能力；前端判分依赖 Qwen3-VL-235B 判分器质量；外观分带主观性。

对音视频交叉方向的关系（以下为笔记作者外推，论文本身未涉及媒体负载）：(a) 下游形态上，媒体资产管理、UGC 平台管理台、转码任务队列看板等正是"前后端+数据库"full-stack 生成的典型目标站点，DB-log 门控可直接迁移用于校验"发布按钮确实写入转码任务记录、收藏操作确实落库"这类有状态媒体操作；(b) 最大缺口在于 GUI-agent 评测只覆盖 DOM 交互，无法检验播放语义（起播、seek 连续性、A/V 同步、缓冲策略、多码率切换），媒体站点评测需在 frontend test 类工具中引入媒体事件与播放状态探针，这是该框架迁移到音视频领域必须补的一层；(c) 回译思路对存量工程资产密集的音视频子领域（如 ffmpeg 滤镜链仓库、流媒体服务配置库）同样适用——把存量 artifact 反译为智能体轨迹做 SFT，可绕开从头合成数据的质量陷阱。

## 7. 与其他论文的联系

- **FGSE（arxiv:2611.14326，When Should Agents Remember? Falsification-Gated Self-Evolution）**：同属"自我改进的内容质量控制"问题族。FGSE 将经验教训作为可证伪假设、经三类探针验证后才写入智能体记忆；FullStack-Learn 则用调试工具派生的聚合分数（γ=0.9、阈值 3/3/0）与增强终局验证过滤轨迹后才进入 SFT。两者分别在记忆层与训练数据层实现"先验证后学习"，动机同源：阻止错误经验污染自改进回路。
- **SkillDuet（arxiv:2611.12109）**：同为不依赖更强教师的能力自提升闭环。SkillDuet 以响应反馈协同外部技能库与模型参数演化，FullStack-Learn 只更新参数（两轮 SFT）将技能内化为权重——"外置技能库"与"权重内化"构成互补对照，FullStack 的调试工具分数恰可类比为 SkillDuet 的响应反馈信号。
- **TRUST（arxiv:2611.10787，Trustworthy Recursive Self-Improvement with Statistical Guarantees）**：直指 FullStack-Learn 留下的开放缺口——其轨迹过滤是启发式阈值判定，无任何统计保证；TRUST 用在线多重假设检验控制自改进的错误进化率并提供统计保证。"回译数据工厂 + TRUST 式错误率控制"是自然的组合方向。
- **InfraRSI（arxiv:2611.11558）**：领域平行的"验证在环"工程智能体——其五阶段验证工作流将开放式指令转化为分布式 LLM 训练优化（最高 2.75× 加速），与 FullStack 以调试工具验证驱动轨迹生产的范式同构，均为工程域递归自改进而非纯代码生成。
- **LongCapHarness（arxiv:2611.10463）**：反向对照——其主张免数据合成与后训练即可挂接长上下文推理底层能力，而 FullStack-Learn 的核心配方恰是数据合成+SFT；两者的分歧点（能力挂接 vs 数据回灌）对选择自改进路线有直接参考价值。
