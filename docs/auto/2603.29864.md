# HLC: A High-Quality Lightweight Mezzanine Codec Featuring High-Throughput Palette

## 1. 背景与动机

Mezzanine（制作域/中间链路）编码的处境是：SDI 有线与 IP 无线传输的带宽增长追不上分辨率与帧率增长，无压缩视频不可行。论文将其需求归纳为四点：(1) 高质量——10–30× 压缩比下保持高视觉质量；(2) 轻量——最小化硬件资源以支持边缘部署；(3) 高吞吐——实时处理；(4) 帧独立——每帧可随机读取与修改而不影响其他帧。第 (4) 条直接决定了 mezzanine 场景使用图像编码器而非视频编码器。

现有两类方案各有结构性缺陷。分发类编码器（HEVC 等）采用基于块的混合架构，预测与熵编码工具丰富、压缩效率极高，但架构复杂度与“轻量、高吞吐”根本冲突；mezzanine 类编码器（JPEG-XS）为低时延与硬件简单彻底放弃“块”与“预测”的概念，吞吐与资源达标，但缺少屏幕内容专用工具，在文字密集区域质量很差——而云游戏、投屏等正是屏幕内容主导的场景。

作者的切入点是把 HEVC-SCC 中针对屏幕内容的 palette（PLT）移植进轻量架构，但 PLT 的像素聚类存在串行数据依赖：传统算法中每当新像素归入某簇，簇中心（CC）即被更新，迫使其他并行单元中在飞的像素以新 CC 重算 SAD，流水线被反复冲刷。已知唯一的先前 palette 硬件设计 [9] 仅达 1080P@30fps、66K LUT，与 4K@120 级吞吐相差一个量级以上。由此 HLC 确定三个发力点：(i) 去数据依赖的 palette 架构；(ii) 保证 PLT 在自然内容上不劣化（甚至受益）的协同 RDO；(iii) 通过率估计—熵编码数据复用控制系统级硬件开销。

## 2. 方法总览

HLC 为混合架构图像编码器，三级流水（S0/S1/S2），编码单元为 **16×4 块**——与 8×8 等像素数（64），但形状选择使参考行缓存深度从 8 行降到 4 行，同时该形状支撑硬件友好的 lifting 式 DWT，是形状—存储联合优化的直接体现。

- **S0**：空间域冗余消除与码率控制。两条编码路径并行：DP 路径做方向预测（精简为 DC/VT/HT 三模式），PLT 路径做像素聚类与索引映射（8 份 PCE 并行实例）；RC 沿用 [8] 的方案，依据目标 bpp（Btar）与累积比特误差（Berr）逐 CU 调 QP。
- **S1**：RDO 仲裁与频域压缩。对 DP/PLT 两路径分别估计率失真代价 J = D + λR（D 为原始与重建像素的 SAD；R 由 RCEDP/RCEPLT 两模块估计），逐 CU 选最优模式；DP 残差经多维 DWT 与量化进一步去除频域冗余，经 IQT/IDWT 得到重建以计算 SAD。
- **S2**：熵编码。定长+变长混合策略：先传定长语法声明后续变长数据长度以保证并行性，且定长统计量直接复用 S1 率估计的中间结果。

三条关键闭环值得注意：率估计模块（RCE）同时服务 RDO 判决与 EC 码流组织（一份硬件两份用途）；QP–λ 表由离线拟合的 R–D 模型导出；RC 输出的 QP 同时驱动 PLT 的聚类阈值，即码率控制可直接调制 palette 行为。PLT 的失败回退内建于 RDO：某 CU 需要第 9 个簇时判为不适合 PLT，退回 DP 路径。

## 3. 关键设计

### 3.1 去数据依赖的 Palette：虚拟簇表

聚类基本单元为 Pixel Clustering Engine（PCE）。规则：每个像素与全部已有 CC 做 SAD 比较，若最小 SAD 低于 QP 导出的阈值 **1<<(QP>>1)**，归入该簇；否则若簇数 <8，该像素自身成为新 CC；若需要第 9 个 CC，CU 判为不适合 PLT。阈值随 QP 指数放宽——低码率下簇更粗，聚类粒度与率控天然耦合。

传统实现的依赖链在于像素归簇后 CC 立即更新（向簇均值靠拢），该更新迫使其他 PCE 重算，流水线冲刷，本质上是在线均值漂移的串行性。HLC 的解法是**双寄存器解耦**：

- **标准 CC Reg**：仅在簇创建时写一次，CU 内全部聚类判决都基于该静态值做 SAD——判决依据不变，数据依赖彻底消除，可全并行全流水；
- **Virtual CC Reg**：持续更新，但只用于 CU 末尾的像素重建，不参与判决。

即“判决用静态中心、重建用动态中心”：索引归属由静态中心决定，代表性颜色用连续更新的虚拟中心，重建质量接近传统均值式聚类。代价是判决基于初始 CC 而非滚动均值，text 数据集上 BD-PSNR 损失 **0.121dB**（Section III-A 口径）——以 0.121dB 换掉整个吞吐瓶颈。工程结果：PLT 引擎 **15.4K LUT 实现 4K@120**（KC705）；对照 [9] 的 1080P@30、66K LUT，像素率约 16 倍（995 对 62 Mpix/s）而 LUT 不足其 1/4。

### 3.2 Run-Length Index Mapping：三符号一维化

簇表定稿后每像素表示为簇索引，形成 2D 索引图。HLC 将其映射为三符号流：与左邻居相同记 L(0)、与上邻居相同记 T(1)、否则记 N(2)（携带新簇索引）。该映射把二维空间冗余折叠为一维同符号 run，后续 RCEPLT 与 EC 直接对 run 的数目与长度操作（长度用 zero-order Exponential-Golomb 组织码流），语法面收敛到 run 数目/长度两个维度，便于定长—变长混合编码与并行展开。

### 3.3 协同设计的 RDO：双 RCE + QP–λ 表

RDO 的可靠性取决于 R 估计准确性与 λ 标定两点。

**率估计**：
- **RCEDP**（DP 路径，作用于 DWT+QT 后系数）：CU 划分为 16 个 2×2 系数立方，RDP = 所有序数位宽之和；每立方内最大位宽记为 bit-plane——该中间量同时是要传给 EC 的定长语法。
- **RCEPLT**（PLT 路径，作用于 RLI 符号图）：RPLT = 表示每个 run 长度所需位宽之和；run 总数与各 run 长度同样作为中间量交给 EC。

**QP–λ 标定**：λ 取 R–D 曲线斜率（经典 λ 域思想）。用多样训练集的平均 R–D 曲线拟合幂律模型 D = C·R^(−K)，拟合优度 **R² = 0.9896**（文中给出的拟合式为 D = 1×10⁶·R^(−1.291)），再逐点求斜率预计算 QP–λ 表，确保 RDO 判决在 DP/PLT 间的平衡有效。

效果上，这套仲裁让 PLT 只在其有利处被选中：即便自然内容 NAC 上，启用 PLT（含 RDO 仲裁）也带来 **+0.345dB** BD-PSNR（由 Table I 中 w/o PLT 相对 HLC 的 −0.345dB 取反）。

### 3.4 RDO→EC 数据复用：打破 VLC 瓶颈

分发编码器的变长熵编码是硬件与吞吐瓶颈常客。HLC 的 EC 采用定长+变长混合：先传定长语法声明后续变长数据长度使变长段可并行；而定长统计量不从零统计，直接复用 RCE 中间结果——DP 流复用 2×2 立方的 bit-plane 标示系数长度，PLT 流复用 run 数目与长度并以 zero-order EGC 组织。此复用策略估计节省 **10.2K LUT**（相对不复用设计），EC 模块最终 **17.4K LUT**。本质上把“率估计”与“熵编码前端”合并为一个硬件部件。

### 3.5 其他工程取舍

DP 仅保留 DC/VT/HT 三模式（自分发编码器精简）；RC 为 Btar+Berr 逐 CU 调 QP 的轻量方案 [8]；16×4 CU 使行缓存减半并支撑 DWT。

## 4. 实验结果

**口径**：KC705 FPGA 实现测硬件；算法侧以 BD-PSNR 度量、**HLC 为参考锚点**（表中负值即劣于 HLC 的幅度），三个数据集：TEC（JVET 非 4:2:0 CTC 文本内容 [11]）、GAC（HDR 游戏数据集 [12]）、NAC（JVET HDR/WCG CTC [13]），四个目标码率 **BPP = 1.75/1.50/1.25/1.00**（若按 8bit RGB 24bpp 折算约 13.7×–24× 压缩，落在论文所述 10–30× 需求区间；原文未给位深，此为推断）。对比对象：JPEG-XS FPGA 编码器 [5]、两版 JPEG-2000 [6][7]、作者自行在 KC705 复现的简化 intra-only HEVC [8]。

结论要点：

- **对 JPEG-XS [5]**：同平台、同 4K@120 吞吐下，LUT 不到一半（82K 对 172K）、存储约 59%（9388 对 15952Kb）、DSP 6 对 43；TEC/GAC/NAC 分别领先 **5.312/3.461/3.299 dB**。注意 REG 反而更高（108K 对 85K）——以寄存器换流水并行度的痕迹。
- **对 JPEG-2000 [6]**（4K@60）：LUT 减半、吞吐翻倍、TEC 领先 1.766dB。
- **对 [7]**：LUT 相当（79K 对 82K）、吞吐大幅领先、TEC 领先 1.731dB；但在 mezzanine 对比中仅 [7] 于 NAC 反超 **1.941dB**，且 [6]/[7] 在 GAC 上小幅领先 0.194/0.391dB——HLC 的压缩优势集中于屏幕内容，自然/游戏内容相对高质量小波仍有差距。
- **对 HEVC-Intra [8]**：LUT 相当（108K）但仅 **4K@2fps、69MHz、798 DSP**，瓶颈在熵编码阶段；同平台下 300 对 69MHz 的时钟差直接反映关键路径长度差距，佐证分发架构对 mezzanine 实时性的结构性不适用。需注意该基线为作者自复现的简化 intra-only 版本，吞吐显著低于原文献 [8] 报告的 4K@30，作为分发编码器代表偏保守；即便如此其在 GAC/NAC 仍领先 6dB 量级。
- 存储结构上，HLC 主要被输入行缓存与跨 CU 流水级的旋转缓存消耗，仅行缓存随图像宽度扩展，分辨率升级的存储增量很小。

## 5. 消融要点

- **PLT 系统级收益/代价**：移除 PLT 后 TEC 掉 **3.983dB**（即 PLT 在文本内容的全部贡献），系统级代价 **24K LUT**（82K→58K）、+586Kb 存储、+32K REG、+6 DSP（w/o PLT 为 0 DSP，即全部 DSP 都在 PLT 路径上）。论文判断 24K LUT 换近 4dB 是高性价比交易。注意分解：PLT 引擎本体 15.4K LUT，其余约 8.6K 为 RCEPLT 与码流组织等配套（由两处数字差推得）。
- **虚拟簇表去依赖的算法代价**：0.121dB（TEC，Section III-A 口径）——去串行化的全部压缩损失。
- **RDO 仲裁的必要性**：PLT 增益在 RDO 仲裁下于三数据集全面为正——TEC +3.983、GAC +0.813、NAC +0.345dB（均由 w/o PLT 行取反），即仲裁避免了自然内容劣化并偶有收益。
- **RDO→EC 复用**：省约 **10.2K LUT**，EC 总量 17.4K LUT。
- **16×4 CU**：与 8×8 等像素量下，行缓存 8 行→4 行。

## 6. 贡献与启示

**贡献**：(1) 首个进入 mezzanine 吞吐量级的 palette 硬件化方案，核心思想是“**判决状态静态化**”——聚类判决只依赖建簇时刻的静态中心，把本质串行的在线均值漂移改为可并行的最近静态中心查询，重建端再用虚拟中心补偿质量；0.121dB 换约 16× 像素吞吐，是算法—硬件取舍的正确示范。(2) 率估计与熵编码前端融合的复用模式：RCE 不只做判决，还直接产出 EC 的定长语法，轻量硬件的关键手法。(3) QP 联动聚类阈值（1<<(QP>>1)）实现了码率控制对 palette 粒度的调制，工具间耦合的干净样例。(4) 16×4 CU 的形状级存储优化。

**启示与局限**：对云游戏串流、远程桌面、无线投屏等屏幕内容 mezzanine 场景，HLC 验证了“轻量骨架 + 一个高效专用工具 + 可靠模式仲裁”的路线；对 JPEG-XS 文本内容 5.312dB 的差距说明传统 mezzanine 编码器在屏幕内容上的空白确实巨大。局限在于：自然内容仍逊于 JPEG-2000 [7]（−1.941dB NAC）、游戏内容小幅逊于两版 J2K；评测以 PSNR 为锚，感知质量未评估；单平台（KC705）验证；REG 开销高于 JPEG-XS 提示并行化并不免费，LUT/REG/BRAM/DSP 间的资源转移值得在设计早期建模。此外“静态判决状态换并行度”的思路可推广至其他聚类类算法（如颜色量化、K-means 类）的硬件化。
