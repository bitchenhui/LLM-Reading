## 1. 背景与动机

论文切入的是代码生成自我进化训练中的**监督信号退化**问题。LLM 代码生成长期依赖大规模标注题解与“基于验证的监督”，成本高且封顶性能。近年 solver–verifier 范式（DSTC、ReVeal、CURE 等）用程序执行构造自动监督：verifier 生成带期望输出的单元测试做语义正确性确认，双方迭代优化。但该范式存在一个结构性瓶颈，论文称之为**验证饱和（saturation）**，其机理值得拆解：

- verifier 测试必须给出期望输出，因此其输入空间天然被限制在“期望输出可被可靠计算”的区域内；
- 当 solver 达到中等熟练度后，大多数候选程序在这些可验证输入上都能通过语义检查，verifier 生成测试的判别力迅速饱和，训练信号越来越偏向“已解决的实例”；
- 角落用例、边界违规、运行时脆弱性（runtime fragility）这类更隐蔽的失败模式被系统性遗漏。

论文特别强调：饱和源于**语义验证本身的结构约束，而非 verifier 能力不足**——这是一个信号定义层面的缺陷，加大 verifier 容量无法修复。

ACE 的动机由此导出：借鉴软件工程中的 fuzzing 与对抗测试（Godefroid 等的白盒 fuzzing、灰盒对抗测试），把“仅看执行结果”的失败信号（运行时错误、异常、不终止）引入训练环，作为 verifier 语义确认之外**互补的第二监督通道**——该信号不需要期望输出，因而天然工作在 verifier 有效覆盖之外。这一问题设定对音视频领域有直接对应物：媒体处理代码的正确性极易在常规素材上确认、却难在极端内容（畸形码流、异常时间戳、高位深边界）上暴露，正是“验证饱和”的典型场景。

## 2. 方法总览

ACE 是一个 solver–adversary 架构的自我进化框架，核心是**单一 LLM 在两个角色间交替**，角色切换仅通过固定的 prompt 模板实现，不引入额外模型。每轮、每题的流程：

1. solver 以 temperature 1.0 采样 k₁=16 个候选程序；adversary 同样采样 k₂=16 个**只有输入、不带期望输出**的对抗测试；
2. 所有候选在 T_GT ∪ T_adv 上于沙箱执行（严格时间/内存限制），构建执行布尔表 E ∈ {0,1}^{k₁×(|T_GT|+k₂)}。两列语义不对称：**GT 列成功 = 限内终止且输出与 oracle 精确一致；对抗列成功 = 仅要求限内正常终止**——是否崩溃即为全部判据；
3. E 驱动三件事： 硬过滤 + 加权评分选出鲁棒程序构成 SFT 数据； 为对抗测试构造 KTO 偏好标签； 执行丢弃规则（违反输入规范/超资源限制的测试；使全部候选失败的可疑测试）；
4. 参数更新：共享 backbone + 每角色独立 LoRA adapter（rank 64，跨轮复用），solver 走 SFT，adversary 走带长度惩罚的 KTO。

整个训练环**不需要参考实现（ground-truth code）、不需要外部奖励模型**——但需精确表述：r_GT 过滤仍依赖数据集自带测试的 oracle 输出，即框架免的是“题解标注”，不免“测试集”。基准结果取 5 轮自我进化后的模型；动力学趋势分析在固定 10% 训练子集上进行。

## 3. 关键设计

### 3.1 崩溃式 oracle 的对抗测试生成

对抗测试只含输入，判据是“是否在资源限制内正常终止”，把测试的价值定义从“确认正确”翻转为“诱发失败”。相对 verifier 测试有两个结构性优势：其一，无需推断期望输出，输入空间不受“期望输出可靠可计算”的约束，正好覆盖 verifier 失效区域；其二，论文以低维表示空间可视化佐证两类测试形成视觉可分的簇（定性证据），即对抗测试占据与 verifier 式测试不同的输入区域，提供分布上互补的执行信号。

丢弃规则有两个要点：违反输入规范或超限的测试直接丢弃；**使所有候选程序都失败的测试同样被丢弃**——作者的实测观察是这类情况多反映非法输入而非有意义的对抗信号。这条规则同时是后文偏好构造的前置清洗，也是全框架最朴素的一道“信号质量门控”。

与 TitanFuzz、UAgent、ATGen 等独立对抗测试工作的本质区别（论文自述）：ACE 中测试效用通过“执行级判别力”定义并**与模型更新直接耦合**，对抗测试不是端目标，而是训练信号的发生器。

### 3.2 鲁棒性感知的 solver 数据选择

对每个候选程序计算 r_GT（GT 通过率，精确匹配口径）与 r_adv（对抗执行存活率），施加硬过滤 r_GT ≥ 0.8 且 r_adv ≥ 0.3，再按综合分 s = α·r_GT + (1−α)·r_adv（α=0.6）排序，每题至多保留 Top 12.5%（ρ）进入 SFT。

机理上有两层：r_adv ≥ 0.3 把“抗对抗存活性”注入 SFT 数据分布——被选中的是“正确且在当前对抗压力下存活”的样本，而非仅正确样本；更隐晦的一层是，随着 adversary 逐轮变强，同一阈值实际构成**自动收紧的课程**：第 1 轮的 30% 存活率与第 5 轮的 30% 存活率对应的对抗强度完全不同。

### 3.3 基于执行表的偏好构造与 KTO 优化对抗方

对每个对抗测试 j 统计候选群体上的失败数 e_j 与成功数 s_j = k₁ − e_j，标签规则为：

- **desirable**：e_j ≥ 1 且 s_j ≥ 1，即测试在候选群体上有判别力（能区分好坏代码）；
- **undesirable**：全部候选成功，不提供任何对抗监督信号；
- **丢弃**：全部候选失败（歧义，可能违反题面约束）。

这个设计有三点值得深挖。第一，标签是执行结果的**确定性函数**，零额外标注成本。第二，判别力是**相对于当前 solver 候选群体**定义的——目标随 solver 演化而移动，构成军备竞赛式共演化动力学：solver 通过某类测试后，这些测试退化为 undesirable，KTO 的梯度压力驱使 adversary 探索新的失败模式；反之 SFT 在鲁棒幸存者上更新 solver 分布。论文观察到的“约 4–5 轮收敛、之后边际收益”即双方达到稳定交互态。第三，选用 KTO 而非 DSTC/SOL-VER 采用的 DPO，理由是偏好数据**天然不配对且不均衡**（desirable/undesirable 数量不对称），KTO 放松配对要求并支持非对称不均衡数据；实现上两端样本等权（w_des = w_undes）。

对抗测试的退化风险是单纯堆长度的 stress test，故在 log 概率比上引入长度惩罚：Δ_LP(x) = Δ_θ(x) − λ·ℓ(x)，λ=0.001，ℓ(x) 为 token 长度；Δ_θ 相对固定参考策略 π_ref。按 Algorithm 1，每轮先 SFT 再在 SFT 后的参数上做 KTO；π_ref 的具体取法（初始模型还是轮首模型）论文未明确，属未披露细节。

### 3.4 训练配置与“SFT+KTO 而非 on-policy RL”的取舍

超参全程固定：SFT 与 KTO 各 2 epochs/轮、batch size 4；训练集 CodeContests 约 4.5k 题；LoRA rank 64、无量化、双角色独立 adapter 复用跨轮（防角色干扰、共享底层表示）；硬件仅 2× NVIDIA RTX PRO 6000。论文在结论中明确交代设计取舍：在稀疏且噪声的执行反馈下优先训练稳定性，SFT+KTO 避免了 on-policy 策略梯度的高方差奖励，换取多轮一致增益；框架兼容策略梯度等更丰富 RL 目标，留作未来工作。这是务实而非能力上限的定位。

## 4. 实验结果

设定：Qwen3-4B-Instruct 与 Qwen2.5-7B-Instruct 双骨干；CodeContests 为 ID（训练分布），MBPP 与 LiveCodeBench v2 为 OOD；指标 pass@k（k∈{1,5,10}，temperature 0.8，所有方法同解码配置）+ 每解平均 token 数。关键行摘录（pass@1/@5/@10）：

| 模型 | MBPP | CodeContests (ID) | LiveCodeBench (OOD) |
|---|---|---|---|
| Qwen3-4B-Instruct | 25.6 / 36.5 / 39.9 | 41.7 / 53.3 / 56.5 | 32.4 / 46.9 / 50.6 |
| ReasonFlux-Coder-4B | 33.3 / 46.1 / 50.6 | 24.0 / 30.0 / 31.4 | 33.2 / 40.8 / 43.4 |
| **Qwen3-4B-ACE** | **35.8 / 49.9 / 52.3** | **46.7 / 55.7 / 60.1** | **37.5 / 49.5 / 53.4** |
| Qwen2.5-7B-Instruct | 24.1 / 33.5 / 39.8 | 23.2 / 35.6 / 40.2 | 30.4 / 37.2 / 43.7 |
| ReasonFlux-Coder-7B | 29.5 / 44.8 / 51.7 | 26.4 / 38.6 / 43.1 | 33.5 / 43.2 / 47.2 |
| **Qwen2.5-7B-ACE** | 28.8 / **46.3 / 54.2** | **29.3 / 38.8 / 43.7** | **38.9 / 45.6 / 49.9** |

要点与口径核对：

- **ID**：4B 档 CodeContests pass@1 从 41.7 → 46.7（+5.0），@10 从 56.5 → 60.1；两规模全部 pass@k 指标 ACE 最优。
- **OOD**：LiveCodeBench 上两规模全指标最高，7B @1 达 38.9（较 Instruct 基线 +8.5，较 ReasonFlux +5.4），是最大单项增益，支撑“对抗暴露失败模式 → 分布偏移下更鲁棒”的论断。MBPP 上 4B @1 为 35.8（较 ReasonFlux +2.5）；但 **7B @1 28.8 低于 ReasonFlux 的 29.5（−0.7），@5/@10 反超**（46.3 vs 44.8、54.2 vs 51.7）——正文“MBPP 上 pass@1 提升 2 到 4 点”的表述与表格在 7B 对 ReasonFlux 处不吻合，宜以表格逐项读数为准。摘要声称对强 solver-verifier 基线 pass@1 绝对增益 3–7%，按表实际分布并不均匀（4B CC 对 ReasonFlux 高达 +22.7，7B MBPP 为负）。
- **异常基线**：Qwen2.5-Coder-7B 在 CodeContests 上 pass@1 仅 5.0（Avg. Tok. 2738），论文未解释，疑似与 stdin/stdout 评测管线的适配有关——提示所有绝对数值依赖其自有 harness，跨论文可比性有限。
- **效率**：MBPP 4B 平均 token 785.9 → 688.8、LCB 4B 2346.7 → 2286.6（降），CC 4B 2808.2 → 3174.3（升）；7B 多数基准高于 Instruct 基线。“持平或更优”的结论主要相对 ReasonFlux（其开销 1.5k–3.5k token）成立，作者解读为对抗自进化促使解法更精炼而非更长探索。
- **动力学**（10% 子集口径）：前若干轮单调上升，约 4–5 轮收敛，之后边际。
- **测试画像**（末轮 CC 训练集随机 100 条、确定性规则分类）：边界/极值 30.2%、格式敏感 24.1%、组合 corner case 22.7%、大规模 stress 12.3%、其他 10.7%——adversary 未坍缩到单一失败模式。

## 5. 消融要点

Qwen3-4B 骨干、全量训练、第 5 轮 checkpoint，pass@1（训练集 / CodeContests）：

| 变体 | Training | CodeContests |
|---|---|---|
| Full ACE | 46.2 | 34.8 |
| 随机测试替代对抗测试 | 41.8 | 30.7 |
| No KTO（adversary 仅作测试生成器） | 40.8 | 24.9 |
| No SFT（solver 仅靠 KTO） | 41.2 | 22.9 |

三点结论：**随机测试**（同等数量、prompt 扰动生成、无对抗目标与偏好优化）下降约 4 点，证明增益来自被优化的对抗目标而非测试多样性本身；**No KTO** 训练集 −5.4 但 CC −9.9，说明偏好优化是把测试生成持续适配 solver 演化失败模式的关键——一次性对抗收益不可持续，泛化受损更重；**No SFT** 训练集降幅相对小（−5.0）而 CC 降幅最大（−11.9），SFT 的作用是把执行反馈固化为**可迁移**的行为而非仅拟合训练分布。三者互补，缺一即退化。

**口径警示**：本表 Full ACE 的 CodeContests 34.8 与主结果表的 Qwen3-4B-ACE CC pass@1 = 46.7 在论文口径下（同骨干、全量训练、第 5 轮）未被调和，疑为评测子集或配置差异；消融结论宜读**相对差值**而非绝对值。

## 6. 贡献与启示

论文的三条自述贡献成立且清晰：把对抗测试生成内嵌为多轮自我进化框架的监督通道；证明纯执行结果足以同时构造 solver 的 SFT 信号与 adversary 的偏好信号（无参考实现、无奖励模型）；在三个基准上取得一致性增益且 OOD 更大。

方法论层面的深层价值有两点。其一是**把测试生成目标从“确认正确”重构为“在 solver 当前失败边界上最大化判别力”**——判别力相对候选群体定义，形成自动移动靶课程，这直接绕开了语义验证的结构性饱和。其二是**崩溃 oracle 的经济学**：不需要期望输出的判据几乎零成本，却能在 verifier 覆盖之外持续产生信号；“全败丢弃”与硬过滤共同构成朴素的伪信号防线。工程上，2× RTX PRO 6000 + LoRA + 4B/7B 骨干的算力规模对领域团队可负担，主要可变成本是每题 16×16 次沙箱执行。

对音视频技术上下游的含义（本笔记解读层）：媒体软件鲁棒性测试本就以崩溃 oracle 为中心——demuxer/parser/decoder 对畸形码流与容器边界的 fuzzing 传统悠久，ACE 的“LLM 对抗输入生成 + 仅执行判据 + 偏好优化生成器”可迁移为一个**可学习的媒体 fuzzing 环**：GT 测试对应常规素材回归集，对抗测试对应自动生成的极端内容样本，且崩溃/挂起/断言判据在媒体域比“精确匹配输出”便宜得多，沙箱超时机制也与防解析器死循环的既有基础设施一致。进一步，LLM 生成媒体代码（FFmpeg 滤镜链、GStreamer pipeline、HLS/DASH 打包脚本）同样面临验证饱和——常规素材易验证、HDR 元数据异常/10与12bit 溢出/异常 PTS-DTS/可变帧率难验证——ACE 机制提示构造与代码生成器共演化的“内容级对抗探针”生成器，替代昂贵的人工测试素材资产；需注意解码正确性仍需参考解码器做 oracle，属迁移时的必要改造。风险面：论文自认的 reward hacking（学会防御性 try/except 掩盖失败）在媒体链路中代价被放大——静默花屏、音画不同步比崩溃更难排查，鲁棒性选择（r_adv ≥ 0.3）与服务化“优雅降级”诉求同构，但掩盖型退化必须以更强测试约束或统计控制兜底后方可进入生产代码生成。

局限（论文自述 + 阅读补充）：SFT+KTO 是务实起点而非上限；reward hacking 未解；实际依赖数据集 GT 测试集；骨干 ≤7B；绝对数值依赖自有 harness；π_ref 取法、CC 两表数值差异等细节未披露。

## 7. 与其他论文的联系

- **FGSE（arxiv:2611.14326）**：两者都在“什么信号被允许进入自我进化更新”上设门。ACE 以执行表硬过滤 + “全败测试丢弃”做执行级门控，FGSE 将经验教训作为可证伪假设经三类探针验证后才写入智能体记忆。关联依据：同属自我进化的信号质量门控，ACE 处理“非法输入伪装成强测试”、FGSE 处理“不可证伪教训写入记忆”，是同一问题（伪信号注入防护）在数据通道与记忆通道上的两个实例。
- **TRUST（arxiv:2611.10787）**：ACE 在结论中自认对抗测试存在 reward hacking 风险（防御性 try/except 掩盖失败）且未提供控制机制；TRUST 用在线多重假设检验为递归自改进控制错误进化率并给出统计保证，是对该缺口的直接补位——ACE 的执行布尔表天然产出可检验的统计量，二者具备组合条件。
- **SkillDuet（arxiv:2611.12109）**：同为双通道共演化式递归自我改进。ACE 把对抗方内化为同一 backbone 上的独立 LoRA adapter（参数内双角色、共享底层表示），SkillDuet 以响应反馈驱动 LLM 参数与外部技能库的协同演化（对抗方/技能外化为可审计资产）。对比价值在于“共演化对手的载体选择”：内化利于表示共享与低成本切换，外化利于复用与审计。
- **CompoundingKernel（arxiv:2611.19230）**：同为“执行测量作为唯一监督”的代码域自我改进——该文以 B200 上内核实测性能登顶 SOL-ExecBench 公开榜单，ACE 以崩溃/存活执行结果为目标。差异在优化目标：性能（更快）对鲁棒性（更抗崩溃）；ACE 的对抗共演化机制原则上可叠加进性能导向循环，例如生成诱发内核性能退化或越界的对抗负载。
