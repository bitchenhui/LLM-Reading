## 1. 背景与动机

论文的出发点是 "Agent = Model + Harness" 这一分解：冻结的 LLM 之上，prompt、记忆、技能、工具、编排共同构成执行 harness，同一模型在不同 harness 下表现差异巨大。随着 agent 从编码扩展到办公工作流与法律等高风险专业领域，harness 设计必须容纳持续分化、不可预测的任务需求，人工反复打磨不可持续，因此催生了面向 harness 的递归自我改进（Recursive Self-Improvement, RSI）。

作者将已有 harness RSI 工作分为两代：第一代（Meta-Harness、AHE 一类）在固定训练任务、单元测试或验证反馈上离线搜索候选组件、部署前选优，但静态 harness 在开放世界（任务持续到达、需求持续演化）中泛化失败；第二代把 harness 演化搬到线上，要么针对当前任务递归改进一个 harness，要么把成功的执行 harness 逐批携带下去。第二代面临两个耦合的难题，构成本文动机：

其一，开放式任务在设计阶段不可见、测试时新颖，普遍缺乏 ground-truth 标签或可靠验证器。现有方法依赖代理信号、假设的真值答案或成对输出判别，而如何安全地用不完美的执行证据指导 harness 修改，仍未解决。其二，为一个任务改进 harness 并不自动改进下一个任务的改进方式——任务特定的编辑在需求变化时常失效，直接继承高度定制的执行 harness 在任务分布漂移下会引入噪声递归。作者的关键观察是：改进过程本身产生高度可复用的经验（弱点如何被诊断、哪些改动被测试、执行揭示了什么），因此改进机制本身必须成为学习对象。

由此提出中心问题：**RSI 能否同时改进当前 harness 和"未来 harness 被改进的方式"？** 这本质上是把递归从对象层（执行 harness）提升到元层（改进 harness），是 Gödel 机式自我改进在 agent 工程化场景下的两层落地。

## 2. 方法总览

**形式化设定。** 模型 M 参数冻结；harness H=(c₁,…,c_K) 为 K 个可编辑组件，与 M 组合成 agent A(·; M, H) 而不改权重。执行 harness 采用 AHE 的文件级分解并扩展一个组件，暴露 K=8 个组件，每个组件以文件形式挂载进运行时（编辑即 diff）。系统在无真值答案、无标注验证反馈的开放任务流 q₁,…,q_N 上运行，每个任务从公共执行 harness H₀ 出发，可在有界预算内重跑当前任务后提交交付物。

**双层递归定义。** 论文给出"递归 agent harnessing"的定义：任务级递归用生成的 harness 与执行证据细化当前执行 harness；harnessing 级递归在每任务后，用被采纳的 harness 与改进经验更新指导后续细化的改进 harness。二者的区分是全文的概念支点——被改进的系统（执行 harness）与改进它的机制（改进 harness）解耦，改进 harness 在任务内保持固定、任务后通过 harness 改进库更新。

**单任务 pipeline。** 任务级递归以一个对比式改进步骤（Propose–Probe–Compose）为原子操作 Φ：先采样参考执行暴露当前 harness 的行为方式（而非交付物对错）；随后以双 scope（不变式/领域特定）提出两个可执行候选 harness；每个候选在同一任务、匹配配置下执行，与参考执行对比得到行为对比；最后 Composer 读取参考、候选、diff 与全部任务内执行证据，选择性地合并、修订、整体采纳或保持原状，形成后继 harness 并执行。并行递归将此原子操作横向铺开（k 个候选每 scope、k 个组合会话），串行递归纵向链式（k 步，逐步携带精炼后 harness 与累积证据）；k>1 时由盲选器在匿名交付物中选一提交。

**跨任务 pipeline。** 每任务结束后，Experience Reflector 审查完整改进记录（参考执行、候选与探针、组合决策、选择结果），仅当执行对比支持时提炼经验，连同被采纳的完整 harness 树写入改进库（每条目附 EXPERIENCE.md 记录适用情形、教训与证据）。下一任务仍从 H₀ 起步，但其 Propose/Probe/Compose 由更新后的 R_{t+1} 指导：库中组件被选择性复用或适配，而非自动继承——这是与"携带执行 harness 跨批"类方法的本质区别。

## 3. 关键设计

### 3.1 八组件可编辑面与激活成本分层

八个组件按运行时角色分四组，各自的激活方式决定了其上下文成本与强制力，这一分层是工程上最值得借鉴的设计：

- **上下文构造**：C1 系统提示、C2 guardrails、C3 长期记忆（每次调用常驻）；C6 技能（经 skill tool 按需加载，未触发则零成本）。
- **工具接口**：C4 工具指导（常驻）；C7 脚本（经 bash 执行，用确定性计算替代逐 token 推理）。
- **编排**：C5 子代理（独立上下文窗口、只返回结果，是唯一增加推理上下文的组件）。
- **中间件**：C8 TypeScript 插件（在 tool loop 内挂钩，位于模型自由裁量之外，"强制行为而非指示行为"）。

编辑器 prompt 中给出了明确的成本优先序：技能（有可识别触发器的流程）> 脚本（确定性操作）> 子代理（大输入小答案的有界调查）> 插件（tool loop 内的机械问题）> 常驻文本（最后手段，且加一句须删一句）。这个"形式与内容同等重要"的原则，把 harness 编辑从写 prompt 提升为运行时架构决策。配套的三条硬验证规则（技能目录名必须在常驻文本中出现 verbatim 触发行；常驻文本禁止 Jinja 模板花括号；被引用脚本必须随提案交付）违反即整份提案作废，从源头消除了"未被触发的技能""悬空引用"这类静默失效。

### 3.2 对比式 Propose–Probe–Compose：无验证器下的证据构造

该步骤是全文的方法核心，解决的是"没有对错信号时，什么才算改进的证据"：

- **Propose**：参考执行揭示 harness 行为而非正确性。双 scope 提案将诊断空间正交分解——不变式候选针对跨领域复现的 agent 性缺陷（规划、工具使用、上下文管理、委派），领域特定候选针对当前领域的知识、流程、约束。提案可复用库中组件，但任务特定事实必须对照当前任务证据重验（"早前任务的映射在此处只是假设，不是事实"）。编辑必须能追溯到轨迹中的具体时刻：优先级为"多 run 分歧点（最便宜，agent 已会只差提示）> 反复出现的具体失败 > 轨迹中可见但未兑现的风险"，无法指认时刻的编辑被视为投机。
- **Probe**：候选在匹配配置下执行，其轨迹与交付物同参考执行对比，判定编辑是缓解目标缺陷、无行为改变还是引入回归。关键立场是：对比用于指导组合而非验证正确性，因为执行随机性与共享模型偏差限制了证据可靠性。
- **Compose**：组合是选择性的——合并、修订冲突、整体采纳其一或保持原状（KEEP_BASE 被明确定义为合法答案），每个决策绑定具体观察而非假定分增益。Composer prompt 中进一步给出证据加权细则：k 条基线 rollout 是同一分布的抽样，1/k 出现的缺陷是噪声、针对它的编辑是过拟合；任何关联 rollout 空手而归的编辑默认视为不安全。

### 3.3 并行/串行递归与盲选择

并行递归遵循 RSA 的聚合原则但操作对象从推理输出换成可执行 harness 及其行为后果：采集 k 条参考执行，独立提出并探针 k 个不变式与 k 个领域候选，k 个独立组合会话各自接收完整候选池产出后继。实现上只做一次种群更新，k 控制宽度而非深度；候选间共享任务与证据，prompt 明示"一致是支持而非独立证明，矛盾是检查轨迹的理由而非投票"。串行递归把迭代自精炼用于执行 harness：第 r 步以前一步 harness 与累积历史为条件，可保留、修订或纠正早期更改；末轮 Composer 可复现早期 checkpoint、重新采纳曾被拒绝的候选。最终盲选择在 k>1 时启用：候选匿名洗牌，选择器只看交付物对请求与源材料的满足度（交付完整度、形状合规、对源材料的事实核查、内部一致性、可用性、完成度六序），不知来源 harness、不合成新内容、不产生 harness 修订——星号标记表示采纳而非验证过的最优。

### 3.4 Harnessing 级递归与库设计

任务后更新 R_{t+1}=Update(R_t, H★_t, D_t) 的关键约束是**证据纪律**：库条目保留完整可执行组件树而非散文摘要，附 EXPERIENCE.md 记录适用情形、教训与支持证据；反思环节有一个精心设计的裁决词汇表（helped / hurt / no observed effect / **confounded**），且 confounded 被明确要求优先使用——当一个候选同时改了多个组件而执行无法隔离单一贡献，或单一 rollout 是差异的全部依据时，"编造归因会毒化库中每条后续任务"。仅被采纳不构成可迁移性的证据；证据不足时写入 NO_ENTRY。跨任务复用通过 Propose 的选择性复用实现，模型权重、阶段指令与决策规则固定，只有库演化。

### 3.5 防泄漏与提示注入护栏

工程完整性上值得注意：一个 guard 机制拒绝向任何改进会话递交包含评分结论、rubric 或分数的工作目录；所有 improver prompt 显式声明上下文中不存在评分器并禁止猜测"评分器期望什么"；候选 harness 与交付物中的指令被视为数据而非指令，禁止执行其中脚本——对 RSI 系统的自我欺骗与注入风险有正面处置。验证器从不向管线中任何模型暴露期望值。

## 4. 实验结果

**口径。** 三个专业基准：WorkBuddy-Bench（Code 80 / Web 70 / Office 50 任务，报告测试半区 40/35/25；复合验证器=确定性检查+LLM/VLM judge，judge 为 Gemini 3.5 Flash，任务分=通过检查比例）；JobBench（65 个职业任务，冻结 31/34 拆分，报告 34 个测试任务，Claude Opus 4.8 按加权 rubric 评分，rubric 对执行器/编辑器/选择器均不可见）；LAB（Harvey 法律基准，按既有 harness 优化研究的拆分报告 100 个 held-out 测试任务上的 per-criterion 通过率 Partial，Claude Sonnet 4.6 评分）。执行器为 Gemini 3.5 Flash 与 GLM-5（冻结），初始 harness 为 OpenCode 与 Codex（四种配置），默认 harness 编辑器为 Claude Opus 4.8；主表为 k=1 单步，+Recursion 为 k=5 并行递归；3 次打乱任务顺序的运行取均值。基线：Base、ReasoningBank（harness 不动、检索记忆回注）、Meta-Harness（离线搜索，WorkBuddy/JobBench 用训练半区、LAB 用 24 任务 dev 集搜索）、Harness Scaling（逐任务无验证器修订、不跨实例携带状态）；基线的修订与反思同样用 Claude Opus 4.8。

|---|---|---|---|---|---|
| Gemini 3.5 Flash | OpenCode | Base / Meta-H / **Harness2** | 72.4 / 76.4 / **77.5** (+3.3) | 31.5 / 35.8 / **36.0** (+3.0) | 79.9 / 81.6 / **81.9** (+2.6) |

| GLM-5 | OpenCode | Base / Meta-H / **Harness2** | 64.2 / 69.7 / **75.7** (+3.9) | 20.6 / 20.9 / **24.2** (+4.2) | 59.6 / 60.0 / **71.4** (+6.7) |
| GLM-5 | Codex | Base / Meta-H / **Harness2** | 64.4 / 74.2 / **75.3** (+3.0) | 23.6 / 23.9 / **24.8** (+3.1) | 58.1 / 59.0 / **65.9** (+4.8) |

要点：（1）单步对比改进在全部 3 基准 × 4 配置上均为正增益，最大单步增益为 WorkBuddy 上 GLM-5+OpenCode 的 +11.5（64.2→75.7）、JobBench 上 Gemini+OpenCode 的 +4.5（31.5→36.0）、LAB 上 GLM-5+OpenCode 的 +11.8pp（59.6→71.4）。（2）Harness2 在全部四配置的 WB Avg 与 JobBench Score 上超过所有基线；LAB Partial 上 Gemini+Codex 配置 Meta-Harness（76.5）反超 Harness2（75.6），是唯一例外。（3）反例基线表现印证动机：ReasoningBank 在编码任务上最多低于 base 6.6 点（GLM-5+Codex Code：56.8→50.2）；Harness Scaling 在 12 个基准–配置对中 7 个低于 base。（4）弱执行器在 WB 与 LAB 获益更大：GLM-5 加一步后（75.7/75.3）即超过 base 配置的 Gemini（72.4/74.5）；而 JobBench 上更强的 Gemini 获益更多（+4.5/+1.4 对 GLM-5 的 +3.6/+1.2）。（5）递归对初始 harness 差距的作用不均匀：JobBench 上 OpenCode–Codex 差距由 2.4/3.0 缩至均为 0.5；WB 上 Gemini 的差距 2.1→0.4 但 GLM-5 的 0.2→1.3。（6）步数总体下降（如 Gemini+OpenCode WB Avg 25.4→21.9），说明增益并非靠更长执行换来。

**预算与计算。** WB-code / WB-office 上并行与串行均随 k 从 1 到 5 单调上升（并行 Code 76.5→80.8、Office 79.5→83.4）；k=2 的两种递归形式即超过所有基线在 k=5 的表现，而 Harness Scaling 在 k=2→3 回归、ReasoningBank 波动——单纯加大测试时探索不保证改进，递归式 harness 精炼才产生一致增益。k=5 时并行高于串行（k=2 时 Code 上串行更高），并行提案与组合可并发以压延迟。计算–性能平面（计入交付前全部 token，含执行与改进开销）上 Harness2 两种配置均位于经验 Pareto 前沿：Gemini+OpenCode 下 k 1→5 使对 base 增益 4.5→7.5、5.1→8.4（JobBench/WB）；Meta-Harness 计算量超过 Harness2@k=5 而性能更低。

**补充分析。** 同模型兼任执行器与编辑器（OpenCode，k=2）：五个模型（GLM-5 至 Claude Opus 5）在三基准全部改进，Opus 5 为 +3.3/+5.5/+3.0，GLM-5 在 LAB +13.7——改进不依赖更强编辑器。跨模型迁移：为 Gemini 3.5 Flash 精炼的 harness 原封用于 GLM-5 使 WB Code +17.3（58.5→75.8），Gemini 3.7 Flash 与 Opus 4.8 也均为正增益但幅度差异大。工具可靠性（k=1，Gemini+OpenCode）：三基准工具错误率全部下降，JobBench 降幅最大（14.4%→9.1%）；调用数在 WB 降（20.0→17.8）而在 JobBench/LAB 升——精炼提升的是可靠性而非压缩执行。对比生产 harness（k=5，自 OpenCode 出发）超过最强固定替代（CodeBuddy/OpenCode/Codex/Claude Code 各域最优者）4.6/5.8/4.9 点（Code/Web/Office）。失败分析给出 9 个回归案例的三类归因：盲选择偏好弱候选（如池中 95 分被弃、55 分被选，-41）、错误前提跨候选传播（编辑器自写的检查规则无法检查编辑器自身假设，单案损失 2–11 点）、结果变异与 judge 缺失（judge 崩溃单案 -34）——直观展示了无验证器 RSI 的回归尾部。

## 5. 消融要点

**三大组件消融**（Gemini 3.5 Flash + OpenCode，k=1，隔离测试时预算因素）：

| 配置 | WorkBuddy Avg | JobBench |
|---|---|---|
| Harness2 | 77.5 | 36.0 |
| w/o library（不读写改进库） | 74.4 (−3.1) | 34.2 (−1.8) |
| w/o scoping（双通用编辑器替代 INV/DOM） | 74.6 (−2.9) | 32.3 (−3.7) |
| w/o composition（探针后取优、不组合） | 75.9 (−1.6) | 34.1 (−1.9) |

三者均贡献显著；scoping 在 JobBench 上损失最大（−3.7），说明在证据与预算完全相同时，**让编辑器在声明的作用域内读轨迹**（过程缺陷 vs 从业者知识）本身就是关键信号；library 证明跨任务经验传递有真实收益。

**Harnessing 级递归的机理验证。** 直接用改进 harness 编辑 base 而无参考执行、候选探针与库时，性能反而退化（WB Code 73.4→63.2、Web 69.9→65.0）——脱离执行证据的 harness 编辑是净负资产；k=1 积累的库恰好恢复 base 性能，k=5 积累的库则支持单步精炼再 +0.9/+4.4/+5.1（Code/Web/Office），即**任务级探索越充分，后续任务无需额外探针即可获益更深**。跨基准迁移：JobBench 衍生库令 WB 单步精炼 +0.6/+0.5/+2.9（Office 获益最大）。留一复跑（每任务排除自身库条目、可用其余全部条目）：WB 77.5→79.4、JobBench 36.0→37.7，作者明确标注这是事后离线复用分析而非在线增益估计（且重复执行本身可能贡献部分差异）。

**改进后 harness 的组件贡献**（WB，k=5 full=80.8 Avg，移除组件组不重跑改进）：去 skills −5.3（Code −3.6、Web −6.9）、去 scripts −3.7（Office −7.4）、去 prompt 组 −1.5；所有消融配置仍高于 base，多组件组共同贡献但论文明确不主张可加性。**库来源分析**：修改文件中含库来源的占 22%（LAB、WB-office）至 47%（JobBench），但保留≥50% 行来自库条目的仅 2–10%——适配远多于整块复制，skills 与 scripts 合计约占各基准编辑量一半，印证"可执行命名组件优于散文"的设计取向。

## 6. 贡献与启示

**方法论贡献。**（1）首次把开放式 harness RSI 显式拆为对象层/元层双递归并给出可运行实现，"改进过程本身成为学习来源"是对 RSI 累积性主张的具体化；（2）对比式 Propose–Probe–Compose 提供了无验证器场景下的证据构造范式：行为对比只回答"编辑是否改变目标行为"，把正确性判断推迟到盲选择与事后反思，并用 confounded 优先的归因纪律防止噪声经验污染库；（3）概念贡献是执行 harness 与改进 harness 的解耦：不继承定制化执行 harness（避免分布漂移下的噪声递归），而是携带组件与经验供选择性复用。

**工程含义。** 八组件分解与其激活成本分层（常驻 vs 按需 vs loop 内强制）可直接迁移到任何 agent 系统的改进接口设计；三条提案验证硬规则与防评分泄漏 guard 是 RSI 系统防自欺的实用模板；k=2 即超过基线 k=5 的结果说明并行候选 + 独立组合的证据杠杆率高于单纯加码探索；跨模型迁移（GLM-5 +17.3）提示团队可把为一个模型调好的 harness 资产低成本迁移到新模型。局限作者自陈：递归精炼带来额外推理开销（并行只降延迟不减计算，实验只刻画有界预算内的权衡）；行为对比对执行变异与共享模型偏差敏感，不保证采纳更改的正确性与跨任务迁移——失败分析中的 -41/-34 案例即是明证。

**与音视频技术上下游的关联。** 本文属 agent/harness 工程，非音视频核心，但其范式与音视频管线上下游有多处实质对接：其一，音视频内容生产与质检（转码、字幕对齐、长节目拆条、合规审核、媒体资产报表）正是"交付物难以自动化验证、只能 rubric/判别式评估"的开放任务形态，与 WorkBuddy-Office 的文件操作复合验证、JobBench 的加权 rubric 判分同构，无验证器 harness 改进范式可直接套用；其二，长视频理解与长音频转写 agent 的核心瓶颈是上下文预算管理，本文"常驻文本最贵、按需技能零成本、子代理隔离上下文、插件在 loop 内强制"的分层，为多模态长上下文 agent 的 harness 设计提供了现成的成本模型；其三，插件组件"到点未产出即注入 watchdog 警告、写入后立即机械复查"的机制，对批处理媒体管线中"推理耗尽预算无产物""写出即当作成功"两类高频故障是直接可复制的工程对策（例如写后自动 ffprobe/结构校验的自动化等价物）；其四，失败案例确立的"交付物形状属于请求而非 harness"原则，对容器格式、编码参数、时间戳精度等强格式约束的音视频产物尤具警示意义——harness 只能改"怎么做"，不得改"交什么形状"。

## 7. 与其他论文的联系

- **paper:arxiv:2610.32026（RSI-Opt）**：结构上最同构的工作。RSI-Opt 的元智能体跨训练运行演化优化器策略与代码库，与 Harness2 的 harnessing 级递归（用任务级探索经验更新改进机制本身）共享"双层递归、元层携带可复用资产跨轮次"的设计；差异在 RSI-Opt 面向训练运行优化、有可比较的优化指标，Harness2 面向无验证器的部署任务流。
- **paper:arxiv:2611.12109（SkillDuet）**：同以外部资产库为 RSI 载体（技能库 vs harness 组件+EXPERIENCE.md 库），且都强调库条目须带经验/反馈信号演化；关键分野是 SkillDuet 用响应反馈联合更新 LLM 参数，Harness2 严格冻结权重、仅演化 harness 层——二者在"参数内/参数外"改进维度上互补。
- **paper:arxiv:2611.10787（TRUST）**：正面针对本文承认的核心风险。Harness2 的失败分析给出 9 个回归案例（盲选择单案 -41、前提污染 -8~-11），说明无监督采纳决策存在错误尾部；TRUST 用在线多重假设检验为 RSI 采纳决策提供错误率统计保证，可作为 Harness2 组合/采纳环节的候选加固手段。
- **paper:arxiv:2611.10463（LongCapHarness）**：同为 test-time、免后训练的 auto-harnessing，共享"冻结模型、改进 scaffolding、控制成本低于重训练路线"的主张；长上下文能力挂接与 Harness2 的上下文构造组件组（C1/C3/C6）在改进对象上直接相邻，对长序列多模态推理场景是并行可组合的两条 harness 通路。
- **paper:arxiv:2611.11558（InfraRSI）**：RSI 工程化的对照组——InfraRSI 依赖五阶段验证工作流把关开放式指令到训练优化的转化，属于验证信号可得场景；Harness2 恰以"无 ground-truth 验证器"为前提构造行为对比证据，二者共同覆盖了验证信号可得性谱系的两端。
- **paper:arxiv:2611.07319（WeightLoop）**：RSI 对象谱系的另一端。WeightLoop 编辑已部署模型权重、Harness2 编辑模型外 harness；对需要感知/生成底座能力的任务，权重编辑与 harness 编辑原则上可叠加（本文的跨模型迁移结果暗示 harness 收益与模型底座相对正交）。
- **paper:arxiv:2610.32326（TGR-EvoDAG）**：同为自动进化 agent/管线并要求在线验证收益的工业实践（腾讯生成式推荐，在线 CTR 相对 +0.40%），与 Harness2 的流式任务协议互为印证：前者证明管线进化在生产指标上可行，后者给出无真值流场景下的证据构造与经验留存机制。
- **paper:arxiv:2611.14949（RSI-PDEbench）**：PDE 求解具备方程模板与可判定通过率，RSI 可直接以客观对错驱动递归；与 Harness2 的专业交付物（rubric/判别式评估、无真值）形成验证信号硬度上的鲜明对照，凸显行为对比范式在软评估域的必要性。
