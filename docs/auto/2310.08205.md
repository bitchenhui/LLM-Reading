# LiveVV: Human-Centered Live Volumetric Video Streaming System

> Kaiyuan Hu, Yongting Chen, Kaiying Han, Junhua Liu, Haowen Yang, Yili Jin, Boyan Li, Fangxin Wang. *arXiv:2310.08205v2 (2023-10-12)*
> 本笔记由引擎自动深读生成（glm-5.3, pipeline deep_read v1），底稿：全文文本

## 1. 背景与动机

体积视频（VV）以点云/纹理网格/体素表示三维动态场景，向用户提供六自由度视口切换（yaw/pitch/roll 三旋转 + X/Y/Z 三平移），被论文定位为"空间计算"时代的候选杀手级应用（引 MarketsAndMarkets 预测：2028 年全球市场 76 亿美元）。表示格式上，彩色点云（PtCl）因结构简单、易操纵而最常用。但数据量与带宽的矛盾极其尖锐：论文引 FSVVD 的口径，30fps、每帧约 92 万点的全场景 PtCl 流需要约 11.1 Gbps。

既有工作集中于 VOD 场景：tile/FoV 自适应的 ViVo、神经超分的 YuZu（每个视频需数小时预训练）、缓存辅助的 CaV3、Holoportation（实时采集但每场景 1–2 Gbps）、仅限人脸远程呈现的 FarfetchFusion——没有一个系统能实时完成"采集—处理—分发"全链路。作者归纳直播场景三大挑战： **采集部署重**：多深度相机阵列需预置参考结构做标定与同步（FSVVD 需在采集区中心放参考结构，CWIPC 需标靶，ORB 棋盘格标定一旦超出标记空间边界即失效），直播要求即放即用； **带宽鸿沟**：无法套用 VOD 的离线压缩与缓冲优化； **网络波动**：不能像 2D 视频直接切分辨率——点云全局抽稀会造成感知质量坍塌。

测量驱动动机（FSVVD 三段数据）给出四个量化机会：
- **带宽构成**：场景拆为动态人体 + 静态外场景分别传输，静态外场景平均占总带宽 **92.8%**，人体仅 **7.2%**；
- **时间冗余**：Octree + Chamfer 距离检测相邻帧差异，外场景大部分时间静止，可见变化仅集中于对整体贡献很小的局部；
- **抽稀容忍度不均**：以多视角 2D 渲染归一化 SSIM 评估（每场景 30 帧、6 档下采样率），50% 抽稀 SSIM 降幅 **<11%**；但部位差异极大——40% 下采样率下头部损失 **3.1%**、手臂 **14.8%**；带宽随 PDL 近线性收缩（人体 PtCl 全量≈325Mbps、50%≈151Mbps、10%≈27Mbps）；
- **显著性稀疏**：以 15cm 边长 cube 划分场景、10 用户 3 场景测量，仅少量 cube 呈高显著。

由此确立"以人为中心"的两条设计公理：对低显著区域抽稀、对低差异静态数据复用。从音视频技术上下游看，该工作上承 RGB-D 传感、点云生成（Open3D）与 V-PCC/G-PCC 标准化语境，下接 XR/MR 渲染与远程呈现应用，是典型的全链路流媒体系统工作。

## 2. 方法总览

LiveVV 由四模块构成闭环：**实时 VV 生成**（分布式采集单元 + 边缘处理）、**场景分割与复用**、**VABR 传输适配**、**MR 显示**。数据流：每个相机端完成 RGB+深度 → RGBD → 彩色点云与 32 关节骨骼提取，帧附时间戳 descriptor 上传；VABR 服务器按时隙 ΔT 软同步、以骨骼对齐矩阵标定合并为全场景 PtCl 流；骨骼滤波把人体按 15 个圆柱滤波器拆成部位并做差异化 PDL 抽稀，外场景按 cube 做显著性分级差异检测与增量更新；VABR 将流拆为动态/静态两类 chunk，按有限窗口 QoE 优化做分层渐进传输；Meta Quest Pro 客户端渲染并持续回传视口轨迹，作为服务器端显著性分析输入形成反馈闭环。整体指标：稳定 **24fps**、端到端时延 **<350ms**。

核心思想三条： 骨骼即标定标记/分割锚点——复用深度相机自带 body tracking，免标靶部署； 静态/动态分流——静态内容按需增量更新而非逐帧传输； 显著性驱动的非均匀质量分配——密度预算优先给敏感/高显著部位与 cube。

## 3. 关键设计

### 3.1 实时 VV 生成
- **点云生成**：对每深度像素在彩色图定位亚像素坐标并双线性插值取色得 RGBD；由内外参导出焦距/主点，反投影 z = D·S、x = (j−px)·z/fx、y = (i−py)·z/fy 生成带色点云。
- **骨骼提取**：深度骨骼跟踪输出 32 关节及置信度，低置信关节去噪后，以"子骨骼投影到主骨骼"求各采集单元到主单元的变换矩阵。
- **软时间同步**：摒弃硬件触发（Holoportation、CWIPC 均需线缆互联，限制设备移动性），每帧封装含精确采集时刻的 descriptor，服务器按预定义时隙 ΔT 分组，每时隙应收帧数 = 采集单元数，输出帧率 = 1/ΔT；时隙内丢帧复用前帧以避免场景空洞。
- **动态标定**：标定结果即 N−1 个 4×4 变换矩阵（子→主）。关键观察：骨骼关节与点云同坐标系，故骨骼对齐矩阵可直接用于点云配准；不依赖任何前置标定物，矩阵更新频率可调以容忍采集单元被移动。计算仅 32 点矩阵运算（实测 2.1ms）。

### 3.2 场景分割与复用
- **骨骼滤波分割**：15 个圆柱滤波器，轴由相邻骨架关节连线定义，落入滤波区的点判为对应部位 PtCl（Head、Right lower arm 等），同时完成人体/外场景二分。
- **视觉显著性建模**：S_V = ρc·f_g / D_c，其中 ρc 为 cube 点云密度、f_g 为该 cube 落入用户视锥的采样频率（f_g = ΣN_g(i)/N_sample）、D_c 为头显到 cube 中心距离。视口由头显内置加速度计与眼动仪数据计算：欧拉角（yaw α、pitch β、roll γ）转旋转矩阵 R 得视口向量，与"头显→cube 中心"方向向量夹角小于 **30°**（取裸眼有效注意范围）判入视锥；因运动追踪采样率高于直播帧率，多个 FoV 样本合并取平均。
- **差异检测**：外场景划分为边长可调（按网络条件）的均匀 cube；帧已对齐公共坐标系，cube 有唯一坐标可与前一实例同位 cube 直接比较；先建 Octree 加速最近邻搜索，度量取 Chamfer 距离（双向平均最近邻欧氏距离）。显著性三分级映射检测频率：High 每帧、Mid 每 5 帧、Low 每 10 帧。

### 3.3 VABR
- **QoE 模型**：QoE = Σq(R_k) − λ·Σ|q(R_{k+1})−q(R_k)| − μ_s·T_s；q(R_k) 通过用户视点的 2D 表征评估 chunk 平均质量，λ、μ_s 分别权衡质量平滑与启动时延。
- **决策机制**：承袭 Yin 等的优化式 DASH 框架，向前看 N 个 chunk 的有限窗口搜索最大化效用函数的分配。与 DASH 独立多码率版本的本质差异：PtCl 帧是数十万无序彩色点，VABR 不为每档质量独立编码，而是**分层渐进增强**——
  - 动态 chunk：最低层保留关键部位（以头部为代表）全 PDL、其余部位低 PDL 勾勒轮廓；逐层对单个部位增密；最高层为完整人体全部点；
  - 静态 chunk：cube 级分层，各层点的分配按历史视觉显著性；持续在视锥外的低相关区域可不即时更新；
  - 已取质量 Q_c 的 chunk，升级即在 [Q_c, Q_cMAX] 内搜索、仅补取增量层。
- **动态优先**：动态内容承载用户主要显著性，带宽优先保动态 chunk，动态码率 R_d(k) = Σ_{f=1..Nf} Σ_{i=1..15} P_b(i)（帧数 × 15 部位抽稀后密度之和）。
- **静态更新**：剩余带宽 R_s(k) = R_k − R_d(k)，且 R_s(k) = Σ_i (C_d/C_dmax)·P_c(i)·F_d：归一化 Chamfer 距离决定该 cube 更新的 PDL；F_d 由 S_v 分档：S_v≥16.0 取 1、9.0≤S_v<16.0 取 0.2、S_v<9.0 取 0.1。仅更新有变化的 cube；此前存在而当前为空的 cube 置空同步。

### 3.4 MR 显示
Unity 客户端接收 VABR 流并持续上报视口轨迹（服务器显著性分析的数据源）；内置 GUI 支持：向场景添加外部物体的内容管理、虚拟/虚实混合切换的 Passthrough 模式、环境光调节。

## 4. 实验结果

**实现**：3 个采集单元（各 Intel i7-12700 + 2×Azure Kinect，共 6 相机）；VABR 服务器 2×10 核 Xeon Silver 4210、64GB RAM、RTX 3090；LAN 互联；客户端 Meta Quest Pro。Python/C++ 实现，Open3D 做 RGBD→点云。采集 30FPS，彩色 1280×720，深度 320×288（NFOV 2×2 binned 模式取最高深度分辨率）。

**（1）部位抽稀组合的带宽—质量关系**（① 充足带宽 / ② 保头优先 / ③④ 同预算反向分配 / ⑤ 低带宽）：

| 组合 | head/chest/arm/leg 保留率(%) | 带宽 | 归一化SSIM |
|---|---|---|---|
| base | 100/100/100/100 | 325 Mbps | 1 |
| ① | 100/60/25/80 | 226 Mbps | 0.953 |
| ② | 80/55/5/60 | 174 Mbps | 0.939 |
| ③ | 80/40/5/40 | 144 Mbps | 0.921 |
| ④(a) | 70/20/70/25 | 144 Mbps | 0.909 |
| ④(b) 均匀 | 44/44/44/44 | 144 Mbps | 0.886 |
| ⑤ | 50/25/15/25 | 97 Mbps | 0.878 |

带宽降则 SSIM 单调变差，但同预算下分配方案决定质量档次（③ > ④ > ④(b)）。

**（2）cube 级更新 vs 整场景逐帧传输**（2 分钟直播）：平均带宽节省 **>22.5×**。

**（3）吞吐**：单采集单元点云构建稳定 **24 FPS**；骨骼提取 **15.5 FPS**，是下游分割/合成的依赖瓶颈；预提取骨骼后基准测试显示骨骼分割&抽稀与场景合成随人物进出/静止/移动在 **4–29 FPS** 波动。

**（4）端到端时延**（每帧取 6 相机中最慢者、3600 帧平均）：

| 阶段 | 平均时延 |
|---|---|
| 采集一帧 | 17.2 ms |
| 点云构建 | 6.3 ms |
| 骨骼提取 | 67 ms |
| 传输至 VABR 服务器 | 72 ms |
| 动态标定 | 2.1 ms |
| 骨骼分割与抽稀 | 167.5 ms |
| **总计** | **332 ms** |

动态标定仅 2.1ms；最大开销在骨骼分割&抽稀（约占一半）。系统整体 24fps 稳定输出、<350ms 时延；论文声称优于 SOTA LiveScan3D，但评估节未给出量化对比数字，该论断为定性表述。

## 5. 消融要点

- **同预算（144Mbps）下骨骼感知抽稀 vs 均匀下采样**：③（0.921）、④（0.909）对 ④(b)（0.886）有 2.3–3.5 个 SSIM 百分点的优势，验证部位质量敏感度差异可兑现为同带宽下的质量增益，这是全文最硬的消融证据。
- **③ 与 ④ 同预算反向分配**：把点数预算更多给 arm/leg（点数多的部位）反而全局 SSIM 更低，与测量节"40% 下采样率下头部损失 3.1% vs 手臂 14.8%"自洽——预算应流向敏感部位（头/躯干）而非点多的部位。
- cube 级静态复用的 22.5× 节省（配合静态 92.8% 带宽占比）实质是对"静态/动态分流"设计点的独立验证。

## 6. 贡献与启示

**贡献**：首个（作者声称）贯通采集、分割复用、自适应传输与 MR 渲染的 PtCl 直播体积视频系统；骨骼标定实现免预配置部署；静态复用大幅省带宽；VABR 在波动网络下维持 QoE。

**工程启示**（按流媒体系统领域标准评估）：
- **骨骼即标定物**：复用深度相机 body tracking 的副产物，N 相机只需 N−1 个 4×4 矩阵、2.1ms 级开销，直接消解直播部署的标定痛点，是"human-centered"最务实的落点；
- **时间冗余是体积视频最大带宽杠杆**：静态外场景占 92.8% 带宽，cube 级增量更新带来 22.5× 节省。这与 V-PCC 把点云拆为纹理/几何两路 2D 视频再编码的思路同源，但 LiveVV 在系统/调度层按时间特性拆分，而非编码层按信号特性拆分；
- **分层渐进式 PtCl 质量模型**：用"增量层补取"替代 DASH 独立码率版本集合，对无序点集天然适配、免多遍编码、客户端缓存可复用，对点云直播系统的码率梯子设计有直接参考价值；
- **HMD 视口轨迹闭环**：视锥判定 → 显著性 → 更新频率/密度分配，30° 阈值取自裸眼注意范围，把"用户看哪里"变成传输调度的先验。

**局限与开放问题**：
- **单人强假设**：分割、标定、抽稀锚点全部依赖被追踪人体骨骼，多人/无骨架物体场景未讨论；
- **管线瓶颈**：骨骼提取 15.5FPS 低于 24FPS 目标，下游分割/合成 4–29FPS 波动，吞吐结论依赖"预提取骨骼"的基准测试口径；
- **时延预算**：332ms 中 167.5ms 在分割&抽稀、67ms 骨骼提取、72ms 上行传输，GPU 化/并行化空间明确；300ms+ 对对话级远程呈现仍偏高；
- **评估口径**：仅 LAN 部署，公网/无线波动下 VABR 相对基线 ABR 的 QoE 增益未量化；质量度量用多视角 2D SSIM 代理，缺 3D 感知质量指标；
- **音频缺位**：系统只传点云视频，无音频通路、无视听同步与空间声设计——对强调音视频一体的远程呈现/远程教学场景是明显缺口（作者未来工作仅提深度传感改进与神经压缩方向）。

## 7. 与其他论文的联系

- **ResStreamGS（arxiv:2610.21121）**：同为"双流"体积视频思路——LiveVV 按静态/动态时间特性拆分点云并差异化更新频率，ResStreamGS 按高斯时间残差敏感度分流编码传输。两者共享"时间冗余异质性是体积视频带宽主杠杆"的核心判断，但表示格式（PtCl vs 3DGS）与作用层（传输调度 vs 编码）不同，可视为同一思想在经典点云管线与神经表示管线上的两次实例化。
- **InViStream（arxiv:2608.11645）**：同为多视角 RGB-D → 点云的实时体积视频管线（30FPS+），且同在融合前于相机端做前置处理——LiveVV 在相机端做骨骼提取与抽稀，InViStream 在相机端做隐私净化后仅融合安全点云。对照可见"相机端前置处理 + 选择性融合"是该类实时管线的通用范式，LiveVV 的骨骼分割机制恰可为隐私类系统的对象级策略提供锚点。
- **DIA（arxiv:2610.13698）**：DIA 为云游戏做 DRL 驱动的兴趣感知对象级码率分配，LiveVV 按视觉显著性对人体部位/cube 做差异化 PDL 分配，同属"ROI/显著性驱动的非均匀码率预算"且都面向交互式低时延流媒体；差异在决策机制——DIA 用 DRL 决策 2D 对象码率，LiveVV 用 MPC 式有限窗口优化决策点云分层。
- **ImViD 多模态框架（arxiv:2604.09473）**：面向 6-DoF 沉浸的视听一体体积格式与时空高斯光场/声场重建管线，正凸显 LiveVV 纯视频、无空间声通路的缺口；两者在"6DoF 沉浸媒体"目标上互补——LiveVV 贡献直播传输系统侧，ImViD 贡献内容格式与音视频联合重建侧。
