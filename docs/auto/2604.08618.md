# SkillForge: Forging Domain-Specific, Self-Evolving Agent Skills in Cloud Technical Support

## 1. 背景与动机

论文面向企业级云技术支持场景的 LLM agent 部署问题。该场景依赖两类超出原始语言能力的资产：程序性知识与组织上下文。Anthropic 于 2025 年形式化的 Agent Skills 概念——即 SKILL.md（指令与工作流）+ scripts/（可执行代码）+ references/（领域文档）的便携文件包，可像软件模块一样版本化与组合——为这类专业化提供了载体，但生产化存在两个明确痛点：

其一，通用技能生成器缺乏领域接地，初始技能与真实任务要求错位。SkillsBench（86 任务、11 个域）给出了关键实证锚点：人工精选技能平均提升成功率 16.2pp，而自生成技能无任何收益。这说明“生成式技能冷启动”必须注入领域数据，否则产物不可用。其二，部署后缺乏系统性机制将执行失败回溯到技能缺陷并驱动定向修订，技能质量在持续累积的运行证据面前停滞不前。同期工作 Agent-in-the-Loop（EMNLP 2025 Industry）依赖人工标注作为反馈信号，SkillForge 的差异化在于直接以技能工件为操作对象，用 LLM-judge 失败分析加自动改写替代逐次部署人工监督。

应用形态决定了评测范式：生产中 AI 回复交由人工客服审核采纳后才发送客户，这一 human-in-the-loop 设计使“与历史工单中专家实际处置的一致性”成为贯穿全文的技能质量代理指标——一个典型的 IR 式判分设计（本文发表于 SIGIR 2026 Industry Track），本质是把技能质量评测转化为对参考解的一致性判分问题。

从音视频交叉视角看：本文五个评测场景（OSS 对象存储、DNS、Domain、ECS、Account）恰是音视频云（点播/直播/CDN 分发/自建转码算力）的技术支撑面；附录 OSS 案例中的三类代表性失败——私有桶签名 URL 访问、镜像回源 502、资源包计费抵扣——均为音视频云客服的标准题型，框架结论对该领域具备直接可迁移性。

## 2. 方法总览

SkillForge 是一个端到端“创建—评测—修订”闭环，流程为六段：

1. **初始化**：Domain-Contextualized Skill Creator 从领域数据生成 Skill_v0；
2. **执行与监控**：agent 加载 Skill_v_n 执行任务产出客户回复，LLM-judge 与专家参考比对，低一致性输出标记为 Bad Case；
3. **Phase 1 失败分析**：Failure Analyzer 对每个 bad case 在四个维度（Knowledge/Tool/Clarification/Style）并行分析，产出结构化失败记录；
4. **Phase 2 聚合**：按类别聚合批次记录，识别系统性模式并选取代表案例；
5. **Phase 3 诊断**：Skill Diagnostician（ReAct agent）将失败映射到技能定义的具体位置，产出诊断报告与优化计划；
6. **Phase 4 优化**：Skill Optimizer 依据计划经 Virtual File System 定向编辑 Skill_v_n，提交 Skill_v_n+1，进入下一轮。

**受限技能解剖**是前提性工程决策：出于企业安全与稳定性考虑去掉 scripts/，仅使用预定义、已验证的系统工具（schema 存于 references/tools.json）；所有技能资产交互——包括业务 agent 与负责演化的元 agent（Diagnostician/Optimizer）——均经由内存态 VFS，不执行任意代码。理由有三：高频客服任务可由“指令/知识注入 + 预定义工具”覆盖；消除可执行脚本显著提升生产稳定性；动作空间限定为文本操作使失败诊断与优化简化。需实时沙箱脚本执行的场景明确留作未来工作。

**Creator 四段流水线**（因数据合规，用内部 LLM Qwen3-Max 处理私有数据）：

- **Workflow Mining**：LLM 充当过程挖掘引擎，从工单对话逆向专家思维-动作链，含问题识别（将粗类别标签增补为自含上下文的问题描述）、解决路径重建（澄清→信息收集→诊断执行→方案交付）、经验蒸馏（显式标注正/负教训）、示范回复抽取（带使用语境标注的人工高质量逐字回复，供技能内置响应模板）；prompt 强制匿名化（姓名/电话/订单号/域名替换为类型化占位符）。每工单产出结构化 JSON（core_issue / resolution_path / accumulated_experience / exemplar_responses），按主题聚合成高频模式，充任 case-type 处理流程主干。
- **Tool Mining**：解析工单操作日志构建工具调用频次表，按阈值筛选高频工具，从内部注册表抽取 schema，并用共现统计将工具关联到常用场景，产出 tools.json 与场景级用法标注。
- **Knowledge Extraction**：双通道——文档检索（由任务描述与场景构造查询，检索内部知识库与官方文档，过滤并浓缩）和工单引用文献（收集人工客服在工单中实际查阅过的链接，去重按场景组织，即“经真实使用验证的权威源”）。决策关键知识标记直接进 SKILL.md。
- **Skill Synthesis**：预定义云服务模板填充，强制四条约束——每条流程须溯源到挖掘数据中的真实解决路径（而非通用产品知识）、工作流须编码条件分支而非线性序列、错误症状须配根因与处置步骤、每类须有显式升级兜底；SKILL.md 超 500 行/10K 字符时细节下沉 reference 文件。

**执行侧**：技能作为"Meta-tool"按场景动态加载进上下文，而非污染全局系统提示——这是一个值得注意的上下文工程选择，保证了技能间的组合性与系统提示的稳定性。

## 3. 关键设计

**3.1 SKILL.md 五节模板**：Background Knowledge（客户最常误解的概念，论文明确将其有意优先为技能质量的首要决定因素）；Case-Type Triage（决策树，按可观测信号路由到对应处理流程）；Per-Case-Type Handling（每技能通常 4–8 个 case type，各含适用性描述、由挖掘路径重建的分支工作流、工具调用指引、失败原因-处置对、升级兜底）；FAQ（频次低于场景工单 5% 的长尾问题，经真实出现验证）；Reference Index。

**3.2 四维 Failure Analyzer 与确定性聚合**：四个分析通道各自产出严重度与问题类型——Knowledge（缺失/事实错误/矛盾/过时/误用/已有知识未呈现）、Tool（漏调/选错/参数错/重复调用/结果误读/利用不足）、Clarification（过问/欠问/问错焦点）、Style（机械/冗长/冷淡；仅在语义内容正确时才纳入考量）。四维结果由确定性代码规则合成裁决：high≥1 或 medium≥2 判 fail；primary category 平级时按 knowledge > tool > clarification > style 固定优先级定序。关键设计：**判分与归因分离**——Judge 决定“是否可接受”（充当业务指标代理），Analyzer 诊断“为何失败”（面向技能修订），两者独立运行，避免评测信号与修复信号互相污染。

**3.3 失败到技能位置的映射**：论文给出 FA 类别到技能缺陷的映射表——knowledge:missing → SKILL.md 缺该场景知识；knowledge:not_surfaced → 知识存在但组织不良；tool:missed_call → 缺“何时调用该工具”的指引；tool:wrong_params → 参数文档不足；clarification:over_asking → 信息收集规则过宽；style:verbose → 缺简洁性指引。Diagnostician 四阶段运行：Skill Understanding（读并总结 SKILL.md 结构）→ Evidence Collection（解析聚合结果取代表案例）→ Root Cause Attribution（映射到具体位置，缺陷类型分为 missing/insufficient/incorrect）→ Plan Generation。优化计划机器可解析，每条建议指定修改位置（文件与行号区间）、内容变更、是否需示例或知识检索、预期影响（可解决的 case 数）、风险评估——这使下游 Optimizer 能精确执行而非泛化重写。

**3.4 Optimizer 三原则与分层知识放置**：Minimal Modification（只改诊断到的问题）、Do No Harm（仅增量修改，绝不删除在用内容）、Evidence-Based（每次修改溯源到具体失败证据）。执行含建议合并、插入点判定、按优先级应用、示例注入（取自 FA 结果中的专家参考摘录）、去重检查与安全校验。知识增广采用分层策略：高频稳定知识写入 SKILL.md 相应节；缺权威文档的长尾入 FAQ；有官方文档时只引用源链接、留待 agent 运行时检索——复用同一 500 行下沉阈值，防止技能体被 case-specific 事实膨胀。该策略与后文知识平台期分析直接呼应：它是设计者主动选择的“技能不膨胀”约束，代价是长尾知识错误无法靠技能级优化根除。

**3.5 VFS 工程细节**：纯内存 KV 存储（绝对路径→文件节点，节点含元数据与内容），支持标准文件操作与 grep/head/tail/find 类 Unix 工具；所有操作返回统一结构 {success, data, error, message} 而不抛异常；路径规范化自动处理相对路径；会话初始化注入任务文件，全部操作记入执行 trace 供失败分析；与宿主文件系统完全隔离。统一返回结构与全量 trace 是“失败可归因”的基础设施前提。

**3.6 LLM-Judge 细节**：四输入（工单全局摘要/当前对话历史/专家参考/agent 实际回复）；先抽取参考的核心动作并过滤寒暄套话；参考被视为“一种可接受解”而非唯一正确答案——替代路径若与工单最终解决一致也判 Consistent。Inconsistent 判据含生产特化规则：建议客户“提交工单/转人工”（因其本身就是支持 agent）、暴露 AI 身份。输出结构化 JSON（verdict/ref_core_action/actual_action/reason），inconsistent 与 partial 均作为 bad case 转入 FA。人机对齐验证：抽样子集由两名领域专家独立标注，judge 与人类共识一致率超 90%。

## 4. 实验结果

**设置**：五个真实脱敏生产工单场景——S1 Account（389 工单/706 任务）、S2 Domain（527/1061）、S3 DNS（256/572）、S4 OSS（385/730）、S5 ECS（326/668），合计 1883 工单/3737 任务。task 定义为工单内可推进解决的单轮对话（输入为含当前查询的消息历史）。工单按时间序四等分：前三份依次喂给 v1/v2/v3 三轮演化（模拟生产批次到达的 bad case），第四份为演化中从未见过的 held-out 评测集。骨干统一为 Qwen3-Max；每项离线评测重复 3 次取均值。基线三种起点：S_generic（Claude Code + Claude-Sonnet-4.5 生成，含挖掘的工具 schema 但无私有数据访问）、S_domain（本文 Creator 产物）、S_manual（人工专家撰写）。指标为 Strict CR（判 Consistent 占比）与 Lenient CR（Consistent + Partially Consistent）。

**RQ1：领域化创建的初始技能质量**（五场景，格式 Strict (Lenient)，最佳 Strict 加粗口径取自原文）：

| 方法 | S1 | S2 | S3 | S4 | S5 |
|---|---|---|---|---|---|
| S_generic | 58.0 (61.4) | 57.9 (64.4) | 63.0 (69.6) | 59.1 (66.3) | 43.4 (55.3) |
| S_domain | **64.0** (65.7) | **60.5** (68.8) | **65.4** (70.6) | **62.5** (72.7) | **50.6** (57.2) |

S_domain 五场景全胜，平均 +4.3pp Strict / +3.6pp Lenient，最大增益在 S5（+7.20pp Strict）。由于 S_generic 已含工具 schema，该差距分离出工作流知识与知识抽取在工具之外的净价值。

**RQ2：自演化环路**（held-out 上累计增量 Δ，格式 Strict (Lenient)）：

| 迭代 | S_manual 起点 | S_domain 起点 | S_generic 起点 |
|---|---|---|---|
| v1 | +4.09 (+5.39) | +2.36 (+0.24) | +7.70 (+1.60) |
| v2 | +9.64 (+9.94) | +7.31 (+4.13) | +8.40 (+4.60) |
| v3 | +10.99 (+12.21) | +9.23 (+8.00) | +11.60 (+4.90) |

三点结论：三种起点均获益（三轮后 Strict 增益 9–12pp），证明环路有效性与初始质量无关；累计增益逐轮单调上升；弱起点 S_generic 累计增益最大（+11.60），环路对低质初始技能补差能力最强；专家撰写的 S_manual 仍获 +10.99 Strict / +12.21 Lenient，说明自动演化可超越人工策展知识。

**收敛与失败类别动力学**：S_manual 边际增量为 +4.09/+5.55/+1.35（v1/v2/v3），趋向性能上限。类别层面：Tool 与 Style 失败逐轮稳定下降（论文报告 −14.5%/−18.2% 与 −16.4%/−20.9%），Clarification 亦持续下降（−13.1%/−16.4%）；Knowledge 在 v1 后平台化（v2 再降 0%），是收敛的主要驱动。

**对生产遗留系统**：遗留系统为预定义决策树工作流加长期调优的人工专家提示词；v3 在同一 held-out 上取得 +13.76pp Strict CR 优势。

**附录案例量化**（OSS 错误诊断技能，判 inconsistent 的 108 个 bad case，单案例可多维度）：Style 108 例（72 高/36 中，verbose 78、robotic 25）、Clarification 97 例（64/33，过问 59、欠问 31）、Knowledge 76 例（48/28，missing 48、not_surfaced 19、incorrect 13）、Tool 59 例（43/16，missing_call 34、tool_missing 21）。三个代表案例展示级联归因：Case 1 知识缺失（有效签名 URL 可直接访问私有桶文件）级联出工具未调、过度澄清与冗长清单式回复；Case 2 知识错误（镜像回源 URL 实际允许 https:// 前缀与 /* 通配，502 真因是源站未返回 200/206/404）级联出未经验证即否定客户有效配置；Case 3 工具缺失（资源包“仅抵扣激活日之后用量、不追溯”依赖计费查询能力）。优化计划按影响面与风险排出三条优先级：P1 填知识缺口（覆盖 48 例 missing + 13 例 incorrect，低风险）、P2 澄清策略与风格（覆盖 59+78+25 例，低风险）、P3 工具调用逻辑（覆盖 34+21 例，中风险——需验证新工具可用性）。

## 5. 消融要点

论文未设独立消融表，但正文含三组准消融证据：

**工具接地的对照隔离**：S_generic 基线已注入从工单挖掘的工具 schema，RQ1 的 +4.3pp Strict / +3.6pp Lenient（五场景平均）因此可归因于工作流挖掘与知识抽取超出工具之外的增量——“领域接地”被分解为工具接地（已被基线吸收）与流程/知识接地（净贡献）两层。

**起点敏感性**：三种起点均单调获益且排序为 S_generic (+11.60) > S_manual (+10.99) > S_domain (+9.23)。环路对弱初始技能补差最强；而专家起点仍有两位数增益是“自动演化超越人工策展”的直接证据。注意 S_domain 起点绝对值高、可挖空间小，其 +9.23 并非环路弱化。

**失败类别的可优化性差异**：Tool/Style/Clarification 可被技能级优化持续压缩（对应优化器改写调用指引、响应模板、信息收集规则的能力），Knowledge 在 v1 后不可再压。论文给出三重根因： 参考不一致——不同人工客服对相似工单常给出分歧甚至矛盾回复，优化器的知识检索可调和部分冲突但无法消除历史数据固有歧义； 设计约束——刻意禁止用 case-specific 事实膨胀技能体（技能体只编码稳定高频常识，FAQ 只收无权威文档长尾，其余deferred到运行时检索）； 隐性专家知识——专家回复常省略低频长尾问题背后的隐性推理链与经验直觉，无法从文本恢复。由此得出强结论：纯文本、全自动的技能优化存在固有上限，bad-case 驱动的迭代无论多少轮都无法根除长尾知识错误；human-in-the-loop 审核对该残差长尾是互补保障而非被自动化替代。这条“平台期分析”是全文对自进化范式边界最诚实的刻画。

## 6. 贡献与启示

**核心贡献**：(1) 把自改进粒度从 prompt/单任务层提升到可版本化的技能工件层，并以结构化三段管线（FA→聚合→诊断→优化）实现“失败→缺陷具体位置”的可追溯定向修订，而非整体重写；(2) 用 LLM-judge 失败分析替代逐次人工标注，闭环无需部署期人工监督（区别于依赖人工标注反馈的 Agent-in-the-Loop）；(3) 实证自动演化可超越人工专家策展（S_manual 起点 +10.99pp）与成熟生产系统（+13.76pp）。

**工程启示**：无脚本、VFS-only 的约束是稳定性/可诊断性与表达能力之间的显式取舍，代价是放弃需动态代码执行的场景；500 行/10K 字符下沉阈值与分层知识放置是防止技能随迭代退化为不可维护长文的关键治理机制；Skill_v_n+1 的版本化提交提供回滚与审计能力，这对生产采纳是硬前提；判分（Judge）与归因（Analyzer）分离的架构值得同类系统借鉴。

**度量口径警示**：CR 是代理指标，依赖 judge（>90% 人机一致为抽样验证），且“参考为一种可接受解”的宽松口径可能高估替代解正确性；task 定义为单轮对话，回避了多轮策略质量评估；离线工单回放与在线分布漂移的差异论文未量化；知识平台期部分源自参考本身的矛盾性，意味着 CR 上限受数据质量约束。

**与音视频技术的上下游关联**：上游——框架消费的工单系统与知识库正是音视频云（点播/直播/CDN/转码）的既有资产；知识抽取的“官方文档检索 + 工单引用文献”双通道在 AV 错误码与参数类文档上覆盖率高，天然利于分层放置策略中的“引用链接 + 运行时检索”分支。下游——人工客服采纳流程对应 AV 云坐席工作台，CR 可与采纳率/修改率等业务指标对齐校准。场景同构性是最大的迁移利好：附录三案例（签名 URL 私有访问即 VOD 防盗链私有播放、镜像回源 502 即 CDN 回源与源站状态码问题、资源包计费即流量/存储包争议）就是 AV 云客服日常题型，SKILL.md 模板（Case-Type Triage + 分支工作流 + 症状-根因-处置对）可直接作为 AV 排障 SOP 的形式化载体，LLM-judge 一致性范式可作为 AV 智能客服离线回放评测的低成本方案。AV 特有缺口有三：其一，AV 工单高度多模态（截图、播放器日志、mtr/tracert、HAR 文件），本文纯文本单轮设定需先扩展多模态输入与多模态 judge；其二，AV 诊断常需主动探测（拉流测试、流探测命令），与“仅预定义工具 + VFS、无脚本”约束正面冲突，论文自认的实时沙箱未来工作恰是 AV 落地的关键缺口；其三，知识平台期在 AV 场景预计更尖锐——码率阶梯、编解码参数、协议兼容性的排障直觉高度隐性，文本化工单恢复难度大，提示 AV 部署需更早引入模型侧更新或专家闭环补充。

## 7. 与其他论文的联系

- **SkillDuet（arxiv:2611.12109）**：同属“技能库演化”路线的递归自改进工作，关联最直接。SkillForge 在骨干冻结（Qwen3-Max）前提下仅演化技能工件；SkillDuet 以响应反馈同时驱动 LLM 参数更新与外部技能库协同演化。二者共享技能级（而非 prompt 级）的改进粒度；SkillForge 观察到的知识平台期（隐性专家知识无法从文本恢复）恰是模型侧更新可能补齐的部分——参数更新可内化文本中不可见的模式，两条路线构成互补。
- **FGSE（arxiv:2611.14326）**：都解决“自进化中哪些更新允许写入持久知识”的门控问题。SkillForge 的 Optimizer 以 Evidence-Based + Do No Harm（仅增量、不删在用内容）做一次性证据门控；FGSE 将经验教训视为可证伪假设、经三类探针验证后才写入记忆。SkillForge 的 knowledge:incorrect 类缺陷（如镜像回源格式规则写错）若被错误“修复”写入 SKILL.md，会在后续轮次持续误导——FGSE 的探针机制正是对这类更新风险的更强门控，二者在更新安全性维度直接可比。
- **TRUST（arxiv:2611.10787）**：SkillForge 报告了经验性的单调改进与收敛，但无错误演化率控制机制或统计保证；TRUST 用在线多重假设检验为递归自改进提供错误率统计控制。SkillForge 的幻觉分析承认参考不一致（人工客服对相似工单给出矛盾回复）会污染知识增广，这正是需要统计保证的错误演化场景，TRUST 式机制是其自然补强方向。
- **WeightLoop（arxiv:2611.07319）**：同属“实验反馈驱动已部署系统持续改进、无需重训”范式。差异在编辑对象：WeightLoop 编辑权重空间（有界参数编辑程序），SkillForge 编辑文本化技能工件（经 VFS 版本化提交）。前者反馈为实验指标，后者为 LLM-judge 判定的 bad case 批次；SkillForge 的文本工件编辑天然具备人类可读审计优势。
- **InfraRSI（arxiv:2611.11558）**：都是企业/基础设施场景下将开放反馈转化为系统优化的多阶段结构化自改进工作流——InfraRSI 以五阶段验证工作流将开放指令转化为分布式训练优化，SkillForge 以“失败分析→聚合→诊断→优化”管线将部署失败转化为技能修订；两者都强调阶段化带来的鲁棒性与可追溯性，可视为同一范式在训练基础设施与客服运维两个域的实例化。
- **LongCapHarness（arxiv:2611.10463）**：都在免后训练、免数据合成前提下以递归自我改进挂接骨干模型既有能力——LongCapHarness 挂接长上下文推理能力（HELMET/RULER 口径），SkillForge 挂接领域 SOP 执行能力（一致性率口径）；共同点是改进发生在工件/流程层而非模型参数层，且均以显著低于后训练的成本取得超越基线的收益。
