## 1. 背景与动机

RLVR（可验证奖励强化学习）成熟之后，LLM agent 的端到端 RL 训练已相对普及，但论文指出其根本短板：RL 训练的 agent 通常被锁死在训练场景内，部署到新环境后缺乏利用在线交互经验持续改进的能力。技能库是弥补这一缺口的主流思路——把历史交互轨迹固化为可复用技能，测试时经验回放，同时由于技能本质是动作序列的封装，还能压缩交互长度、提升效率。

但既有技能库工作（Voyager、Agent Workflow Memory、Synapse、SkillWeaver、Agent Skill Induction、DynaSaur 等）几乎全部依赖 prompt 驱动技能的生成与调用，能力上限被基座模型的指令遵循能力封死。论文用自身对照实验直接量化了这一点：Qwen2.5-32B-Instruct 上，纯 prompting 的技能库 agent 在 AppWorld Test-Normal 上 TGC 仅 30.7%，反而低于同模型 ReAct 基线的 39.2%——prompt 化的技能库不仅没有收益，还引入了误用技能导致的失败。

将技能库纳入 RL 训练并非平凡，论文识别出三个结构性障碍：其一，技能的质量只有跨任务复用才能显现，单任务的 outcome reward 无法为“技能生成”这一行为赋予信用，即存在跨任务信用分配问题；其二，常规 RL rollout 按单例组织，与“技能在任务间累积”的机制不兼容；其三，开源模型连稳定产出合法的“函数定义+调用”格式轨迹都困难（这正是论文必须先做专家 SFT 的原因）。此外，既有框架（ASI/AWM/Voyager）在任务完成后才事后归纳技能，对 RL 不友好：一方面长程任务上额外拉长上下文，另一方面任务执行与技能生成两种行为模式分离造成训练不一致。为此论文采用 DynaSaur 的统一格式——执行任务的过程本身就是先定义技能函数、再立即调用。

定位上，论文将范围收敛到 API 工具使用型 agent（基于 CodeAct 的代码动作），提出 SAGE（Skill Augmented GRPO for self-Evolution），自称是该方向的首批工作（pioneering）。

## 2. 方法总览

整体为三段式流水线：技能库 agent 脚手架 → 专家经验 SFT 冷启动 → SAGE 强化学习。

**技能库 agent 形式化**：给定任务分布 Q 与技能库 M（可空初始化），每个任务先检索 k 个技能 [a1,...,ak] 注入上下文，随后 agent 可执行四类库操作： Skill Usage，调用已有技能； Skill Generation，定义由多动作组成的函数并立即调用； Skill Update，技能执行失败时改写并重调； Skill Save，执行无错即写入库（新技能或覆盖更新）。定义函数无必要时允许直接 API 调用。Save 判据仅为“执行无错”，是免验证器的廉价可验证性，技能质量则靠 RL 奖励软塑形。

**SAGE 的两个核心组件**：

- **Sequential Rollout**：不再按单任务 rollout，而是从同一场景采样任务链（默认 K=2，记为 (q1,q2)），顺序执行：q1 生成的技能留存库中供 q2 使用。这样 q2 上“技能复用成功”的奖励信号可沿轨迹回传，塑形 q1 的技能生成行为——这是跨任务信用分配的实现载体。选同场景任务构链是为了保证技能可被立即复用。
- **Skill-integrated Reward**：设 r1,r2∈[0,1] 为链上两个任务的可验证完成率，R1 = r1 + 1[r1=1]·1[r2=1]·1_skill(q2|q1)，R2 = r2 + 1[r2=1]·1_skill(q2|q1)，其中 1_skill(q2|q1) 指示 q2 是否复用了 q1 生成的技能；对“无代码即终止任务”的响应施加 −1.0 格式惩罚以强制代码交互格式。

**算法层**：以 GRPO 为基础，沿用 LOOP（Chen et al., 2025）的两项简化——去掉 KL 惩罚、优势不除以组内奖励标准差（Â = R − mean(R)）；并进一步采用严格 on-policy（无 PPO epoch）与全参微调。目标函数在任务链上取期望，token 级损失只计入模型生成内容、环境观测全部 mask。与原始 GRPO 的结构性差异在于：同一组内第 2 个任务的生成 o²ᵢ 条件于各不相同的技能库 M²ᵢ（各自 q1 的产物），打破了 GRPO“组内同查询”的假设——这也是选择严格 on-policy（重要性比恒为 1 附近）的现实理由。

## 3. 关键设计

**3.1 统一格式与库操作语义。** 任务求解与技能生成共用同一输出格式（定义函数→立即调用），相较“任务完成后归纳技能”的范式有两点 RL 收益：rollout 上下文不再被二次技能生成撑爆；行为策略与评估策略一致。技能的入库/更新以执行结果为触发（无错入库、出错改写重试），形成“生成—验证—修复—固化”的闭环，全部判据来自环境执行反馈，无需额外模型。

**3.2 Sequential Rollout 与组内异构上下文。** 链内技能传递使第 2 任务的策略输入依赖第 1 任务的随机产出，组内 rollout 因此条件于异构上下文——这是对 GRPO 组比较机制的实质修改。论文用 K=2 作为默认配置，理由在消融中验证（见第 5 节）：链更长时组内库分化加剧、梯度方差增大且奖励结构不对称。附录 B 给出 K 链推广的奖励公式：Rk = rk + 1[rk=1]·max_{k<i≤K}(1[ri=1]·1_skill(qi|qk)) + 1[rk=1]·1_skill(qk|q1..qk−1)，边界任务（k=1 无前序库、k=K 无后验任务）单独处理，说明框架原则上可扩展。

**3.3 奖励的门控分解。** 技能生成奖励是三重门控（自身成功 ∧ 下游成功 ∧ 下游确实复用），技能使用奖励是双重门控（复用 ∧ 成功）。这要求 rollout 基础设施显式追踪技能血缘（1_skill 指示器），是工程上不可忽略的实现负担。与两种替代设计的本质区别在于：Outcome-based 完全不建模技能，Chain-based 只奖励全链成功而不追踪技能使用——消融显示后两者均显著劣化。

**3.4 专家 SFT 冷启动。** 开源基座 + 精心设计 prompt 仍无法稳定遵循技能库 agent 格式，故先用 Claude Sonnet 3.5 V2 拒绝采样构造专家轨迹：温度从 0.05 到 1.0、步进 0.05 共 20 档；在训练集 30 个场景内顺序部署三个任务（技能场景内传递，与 Sequential Rollout 语义对齐）；每任务最多重试 10 次；仅保留三任务全成或至少前两任务成功的场景，最终得 1,129 条有效样本。SFT 用 Llama-Factory 全参微调，batch 128、lr 1e-6（cosine、0.1 warmup）、最大长度 12,500（超限丢弃），梯度只更新 agent 响应 token。

**3.5 训练系统工程。** 基于 verl（vLLM rollout + FSDP 梯度更新），4×H100 8-GPU 节点，Ulysses 序列并行（每样本 4 GPU）。Rollout 关键约束：温度 1.0、每任务最多 40 轮交互、每轮输出上限 1,500 token、上下文上限 28,048（超限即截断并标记完成）；环境返回超过 12,000 字符截断并附加提示；每步环境输出后注入任务信息提醒；早停启发式（未完成 rollout 达 25 步、每任务 ≥6 条、总量达 90% 即停）。采样预算：基线 GRPO 每步 36 例 × G=8 = 288 条 rollout；SAGE 按场景采样，训练集 difficulty 1–2 子集共 24 个场景、每场景取 2 任务成链，48 链 × G=8 = 384 条。lr 1e-6 恒定、梯度裁剪 1；每 5 步存档按 Dev 集选优，最终取 step 75 检查点。注意公平性口径：LOOP 无开源代码且不报效率指标，故自实现 GRPO 基线（与 LOOP 的差异是严格 on-policy + 全参）。

## 4. 实验结果

评估口径：AppWorld（750 任务 / 250 场景 × 3 相似任务；Train 105 / Dev 60 / Test-Normal 168 / Test-Challenge 417；9 个日常应用 + ApiDocs 共 457 个 API；Test-Challenge 刻意包含 Train/Dev/Test-Normal 均未出现的 Amazon 与 Gmail API 以考泛化）；基座 Qwen2.5-32B-Instruct（对齐 LOOP 便于公平比较）；所有数字为同模型 3 次评估平均；TGC 为单任务完成率，SGC 为场景内三任务全部完成的比率；outcome 奖励来自数据集人工编写的环境终态校验程序（0–1 完成率）。

| 方法（除注明外基座为 Qwen2.5-32B-Instruct） | TN-TGC | TN-SGC | Steps | Tokens | TC-TGC | TC-SGC | TC-Tokens |
|---|---|---|---|---|---|---|---|
| GPT-4o / ReAct* | 48.8 | 32.1 | – | – | 30.2 | 13.0 | – |
| OpenAI o1 / ReAct* | 61.9 | 41.1 | – | – | 36.7 | 19.4 | – |
| Claude Sonnet 3.5 V2 / ReAct | 57.1 | 41.1 | 15.7 | 1,542 | 49.2 | 28.8 | 2,084 |
| Qwen2.5-32B / ReAct* | 39.2 | 18.6 | – | – | 21.0 | 7.5 | – |
| LOOP*（无库 RL） | 71.3 | 53.6 | – | – | 45.7 | 26.6 | – |
| GRPO（自实现，无库） | 69.2 | 51.8 | 16.4 | 3,613 | 40.7 | 26.9 | 5,211 |
| Skill Library Agent（纯 prompt） | 30.7 | 19.6 | 13.4 | 2,988 | 15.3 | 7.0 | 4,803 |
| + SFT（专家经验） | 55.2 | 41.7 | 11.4 | 1,340 | 37.2 | 20.9 | 1,909 |
| **+ SAGE（本文）** | **72.0** | **60.7** | **12.1** | **1,475** | **50.1** | **32.4** | **1,807** |

（* 取自 Chen et al. 2025，未报效率指标；TN=Test Normal，TC=Test Challenge）

关键结论：

- **对自实现 GRPO 基线**（论文摘要口径）：SGC 提升 8.9 个百分点（51.8→60.7）、交互步数减少 26%（16.4→12.1）、生成 token 减少 59%（3,613→1,475），TGC 提升 2.8 个百分点。技能库的增益同时体现在跨任务迁移（SGC）与效率上。
- **Test-Challenge 泛化**：TGC 50.1 vs 40.7（+9.4 个百分点）、SGC 32.4 vs 26.9，token 1,807 vs 5,211（按表内数字计算约降 65%）——在训练未见的应用 API 上，技能库+RL 的相对收益比 Test-Normal 更大。
- **对同类无库 RL SOTA（LOOP）**：Test-Normal 72.0/60.7 vs 71.3/53.6，Test-Challenge 50.1/32.4 vs 45.7/26.6，两个口径全面占优，作者据此称双测试集 SOTA。
- **阶梯式归因**：prompt 版技能库 30.7/19.6 低于 ReAct，证实 prompt 路线不可行；SFT 升至 55.2/41.7（token 已压到 1,340）但仍不及 GRPO 基线的 TGC——纯模仿专家不足以优化性能；SAGE 在其上达到 72.0/60.7，且反超专家本身（Claude 3.5 Sonnet V2 ReAct 为 57.1/41.1）：32B 开源模型经 RL+技能库实现了对闭源教师的大幅反超。
- **对 prompt 版技能库**：SGC 约 3.1 倍（60.7 vs 19.6）、token 约降至 49%，与摘要“>3× SGC、<一半 token”一致。
- **技能使用行为分析**（论文以相对基座的比例报告）：SAGE 同时提高技能使用率与使用后成功率（摘要口径：使用习得技能时的成功率提升逾 2 倍）；基座模型技能库更大、生成技能更多，但被使用技能数与使用成功率均低——生成数量不等于库质量；SFT 模型仅在使用成功率一项超过基座，说朗模仿专家经验对自改进能力的塑造有限，真正的技能生成/利用行为由 RL 阶段习得。

## 5. 消融要点

**5.1 空库评估（Test Normal，评估时清空技能库）**：SAGE 带库 72.0/60.7（12.1 步 / 1,475 token）vs 空库 71.4/54.8（16.0 步 / 1,937 token）。TGC 几乎不变而 SGC 降 5.9 个百分点、步数与 token 显著上升——说明技能库的价值集中于**跨任务迁移与交互效率**，单任务能力主要来自策略本身。反例是未训练的 Skill Library Agent：带库 TGC 反降（30.7 vs 34.7）而 SGC 略升（19.6 vs 14.9），即不熟练的模型误用技能会直接导致单任务失败。

**5.2 检索机制**（默认 Same Scenario 为 oracle 口径，直接使用测试集场景标签）：

| 检索方法 | TGC | SGC | Steps | Tokens |
|---|---|---|---|---|
| Same Scenario（oracle） | 72.0 | 60.7 | 12.1 | 1,475 |
| Query N-gram（2-gram Jaccard ≥0.5） | 72.0 | 60.1 | 12.7 | 1,466 |
| Query Embedding（all-MiniLM-L6-v2，cos ≥0.65） | 69.6 | 59.5 | 11.8 | 1,335 |
| Skill Embedding（Qwen3-Embedding-0.6B，top-5） | 66.3 | 56.0 | 14.5 | 1,692 |

N-gram 几乎打平 oracle，因为 AppWorld 同场景查询高度模板化（部分任务仅换模拟用户）；Query Embedding 语义匹配会跨场景借技，步数/token 最优但精度受损；Skill Embedding 最差——按查询检索技能函数需要理解工具用法而非文本相关性，作者据此指出工具/技能专用检索器是必要的 future work。这一结论对部署期（无场景标签）的可行性至关重要。

**5.3 奖励设计**：Skill-integrated 72.0/60.7 > Outcome-based 69.8/55.4 > Chain-based 67.9/56.6（TGC 口径）。行为分析显示三种奖励下“技能使用后的成功率”相近，差异在**使用频率**——Skill-integrated 大幅提高技能使用行为；Chain-based 甚至比 Outcome-based 更少用技，作者归因于早期训练中不带技也能完成链任务、额外奖励反而强化了无技能的行为模式。效率上存在权衡：用技减少步数，但生成函数增加 token（Skill-integrated 步数最少 12.1、token 略高 1,475）。

**5.4 RL 初始化**：SFT（专家数据）72.0/60.7 > RL Warm-Up 68.3/55.3 > Self-Distillation（基座自蒸馏）66.5/53.6 > Base Model 直接 RL 40.7/25.6。基座直接上 SAGE 几乎训不动（rollout 无法产出高质量链式轨迹），专家轨迹冷启动不可省略。

**5.5 链长 K=3**（同一场景三任务连成链，batch 提至 576）：70.6±3.6/54.8±4.2、14.3 步、2,585 token，全面差于 K=2。归因有三：奖励分布不对称（相关技能多在 q1 执行中生成，生成奖励集中于 q1、使用奖励集中于后续任务）；链变长后组内技能库分化加剧、偏离 GRPO 设定导致梯度方差增大；迭代 rollout 的计算成本随任务数显著增长。

**5.6 SFT 初始化的无库 GRPO**：66.1/51.2，低于原始 GRPO 的 69.2/51.8，但 token 最低（1,284）——SFT 习得的模式会约束 RL 探索；同时该对照说明 SAGE 的收益并非 SFT 单独贡献（同一 SFT 起点做无库 RL 仍明显落后于 SAGE）。

## 6. 贡献与启示

**方法贡献**：其一，把“技能库 agent”从 prompt 工程问题转成 RL 训练问题，用 Sequential Rollout 解决跨任务信用分配、用门控式技能奖励显式塑形生成/复用行为，且对 GRPO 的改动极小（去 KL、均值优势、严格 on-policy），复现门槛低；其二，实证证明 32B 开源模型 + 专家 SFT + SAGE 可在精度与效率上同时超过无库 RL SOTA（LOOP）并反超闭源专家；其三，空库消融把技能库收益干净地拆解为“跨任务迁移 + 效率”而非“单任务能力”，这一拆解对后续 agent 记忆/技能方向的工作有方法论参考价值。

**工程启示**：动作宏化就是 token 经济学——59% 的 token 削减对 API 成本和交互时延是直接兑现的收益；代价是链式 rollout 使每步训练的 rollout 量从 288 升到 384 且时长近似翻倍（4×H100 8-GPU 节点规模）；检索是部署期最薄弱环节，模板化任务上 N-gram 够用，通用场景需要工具语义检索器；库卫生是遗留问题——Save 判据仅为执行无错，无去重、无验证、无淘汰机制，而行为分析已显示基座模型的库“大而差”，长期在线部署的库膨胀与坏技能累积未处理。

**局限**（论文自述 + 合理外推）：仅在 AppWorld 单一数据集验证（作者自认）；默认评估使用测试集场景标签的 oracle 检索，与真实部署有差距；SFT 依赖闭源 Claude 生成专家数据，自蒸馏替代方案低约 5.5 个百分点 TGC；K=2 是经验最优而非原理性结论。

**与音视频技术上下游的关联**（本笔记视角）：环境侧，AppWorld 模拟的 9 个日常应用中包含 Spotify（音频流媒体）及 Phone 等通信应用、共 457 个 API，本文方法直接覆盖“媒体服务 API 编排”这一 AV 相邻场景（播放列表管理、跨应用媒体检索、媒体与消息联动类日常任务）。范式侧，可执行技能库等价于媒体处理流水线的宏封装（如将“转码—抽轨—打标—分发”类组合操作固化为可调用函数），Sequential Rollout 的同场景任务链对应媒体生产中同模板批量素材任务，其“下游复用成功回传信用”的机制适用于在批量任务中自动学习可复用流水线。效率侧，−26% 步数 / −59% token 对端侧与低时延语音/视觉助手、多模态 agent 的推理成本控制有直接参考价值。泛化侧，Test-Challenge 在训练未见 API（Amazon/Gmail）上 TGC 50.1 的结果，提示技能库+RL 对新设备生态、新工具链（新终端、新 codec/编辑工具集）的适应潜力。检索侧，“按查询检索技能函数效果最差”的结论对构建媒体工具技能检索器是直接警示：需要工具用法理解而非文本相关性，与 AV 领域的工具语义检索问题同构。

## 7. 与其他论文的联系

- **SkillDuet（arxiv:2611.12109）**：最直接的同类工作——同样让 LLM 参数与外部技能库协同演化、实现技能级自我改进。差异在驱动机制：SAGE 用 GRPO 变体 + 场景结构化任务链做信用回传，且依赖专家 SFT 冷启动与“执行无错入库”的判据；SkillDuet 以响应反馈驱动技能库演化形成递归自改进闭环。两者对照可分离“RL 塑形”与“反馈驱动库演化”两条技术路线的贡献。
- **FGSE（arxiv:2611.14326）**：同属“什么经验写入智能体记忆”的问题。SAGE 的入库判据是执行成功 + 下游复用奖励（软塑形，无显式验证），FGSE 则要求经验教训作为可证伪假设通过三类探针验证后才写入。本文中未训练模型带库时 TGC 反降（30.7 vs 34.7）正是不验证记忆的风险实证，FGSE 的门控是对该风险的一种互补解法。
- **TRUST（arxiv:2611.10787）**：SAGE 对技能库没有任何错误演进控制（技能一旦执行成功即永久入库），TRUST 用在线多重假设检验为递归自改进提供错误率统计保证。两者互补：SAGE 解决“怎么学会生成与复用技能”，TRUST 解决“学进库里的东西是否可信”。
- **AutoTavern（arxiv:2610.33845）**：同为自改进 agent 在模拟交互环境中的长周期运行（20 天自主构建炉石战棋模拟器与 AI）。从 AV 交叉视角，游戏模拟器是交互式音视频环境的近邻场景；SAGE 的可执行技能库可作为此类长程开发型 agent 的程序性记忆底座，其 Sequential Rollout 机制可用于游戏内同族任务的技能沉淀。
- **RSI-PDEbench（arxiv:2611.14949）**：结构性平行——两者都利用“同族任务”做经验/技能迁移：AppWorld 的场景=3 个相似任务构成链，RSI-PDEbench 以 42 个方程模板组织 1001 个案例。SAGE 显式将任务族结构编码进 rollout 组织与奖励设计，为其他领域任务族化基准（含音视频领域按模板组织的批量处理任务）提供了训练侧模板。
