# optimize_anything: A Universal API for Optimizing any Text Parameter

## 1. 背景与动机

“LLM + 自动评估器”作为优化器的范式已被 FunSearch（数学构造）与 AlphaEvolve（代码优化、矩阵乘法界、数据中心调度启发式）验证，但现有系统呈严重的垂直碎片化：AlphaEvolve / OpenEvolve / ShinkaEvolve 仅支持单任务模式（一次优化一个代码工件），暴露孤岛拓扑、evolve-block 标记等框架专有抽象；GEPA / MIPROv2 仅支持泛化模式（面向未见输入优化 prompt），且工件类型锁死在 prompt。没有任何系统同时覆盖 agent 架构、数值优化、图像生成，更没有系统在本质不同的领域上同时取得 SOTA。

作者的核心观察是：大量问题可统一形式化为“优化一个由评分函数评估的文本工件”——CUDA kernel、云调度策略、agent 架构、SVG、系统提示词，结构完全同构：序列化为字符串 → 评估 → LLM 基于诊断反馈提出改进。由此可以导出一个声明式 API（受 DSPy “编程而非提示”理念影响）与一套统一算法：用户只声明 what（种子工件、评估器、领域知识），系统接管 prompt 构造、反思、候选选择与搜索策略。三项目标贡献：(1) 单系统跨六个领域匹配或超越专用工具；(2) 单任务/多任务/泛化三模式统一于一个接口，其中多任务模式（相关问题的批联合优化 + 跨问题迁移）为该方向首个；(3) Side Information（SI，诊断反馈）升格为评估器的一级 API 契约，消融显示可带来 4–6× 收敛加速与显著更高的终值。论文发表于 CAIS '26，系统以 GEPA 项目子模块开源（github.com/gepa-ai/gepa）。

## 2. 方法总览

**接口契约**：`optimize_anything(seed_candidate, evaluator, dataset, valset, objective, background, config)`；评估器签名 `fn(candidate: str) -> (score, side_info dict)`，side_info 可含任意文本、结构化数据、多子分，或经 `oa.Image` 传入图像供 VLM 提议器消费。用户无需提供变异 prompt、任务模板、孤岛配置或 EVOLVE-BLOCK 标记。SI 是 opt-in 但零摩擦：只返回分数的评估器照常工作，`capture_stdio=True` 可自动捕获 print 输出。另设 seedless 模式：仅给自然语言 objective，由 LLM 自举首候选（附录 C 以 build123d + pyrender 的 3D 独角兽演示）。

**形式化**：记工件空间 X，评估器 f: X × E ∪ {⊥} → R × I，f(x,e) = (s(x,e), ι(x,e))。三种模式仅由 dataset/valset 是否提供决定：

- **单任务搜索**：E = ∅，直接最大化 s(x)，工件即解（圆排列算法）；
- **多任务搜索**：给相关任务集 D = {e₁,…,eₙ}，最大化均值分。关键架构决策：Pareto 前沿在提议阶段跨任务共享（任务 eᵢ 上发现的模式可作为 eⱼ 提议的父本），但输出时每任务独立从前沿取最优，产出 N 个受益于共享优化上下文的**专用**工件；
- **泛化**：同时给 Dtrain/Dval，Dtrain 反馈驱动搜索、Dval 度量未见样本泛化——经典 ML 训练/验证划分向任意文本工件（prompt、agent、策略）的推广。多任务与泛化的本质区别是 N 个专用工件 vs 1 个全局泛化工件。

**默认后端与主循环**：后端无关（含适配层），默认后端是对 GEPA 的扩展。核心循环（论文 Algorithm 1）：初始化候选池 P ← [Φ₀] 并全量评估记录逐例分数；预算内循环 {按前沿频率 ParetoSelect 选父本 → 从 D 抽 2–3 例 minibatch → 执行并收集分数+SI → LLM 反思提出 Φ′ → 若 Φ′ 在 minibatch 上改进则全量评估并入池、剪枝被支配候选}；返回平均分最高的 Φ*。单任务下“逐例追踪”退化为“逐指标追踪”；多任务下每个数据元素是独立问题。

## 3. 关键设计

**SI 作为一级类型化原语**。数值优化把全部诊断上下文压缩为标量——无法把栈回溯喂给贝叶斯优化器；既有 LLM 进化框架用框架专有机制传反馈。本文将其统一为评估器契约的一部分：文本（编译错误、运行时异常、profiler 摘要）、结构化（逐测试用例结果、多目标子分、执行 trace）、图像（渲染结果回传 VLM 提议器）。作者的定位是“SI 是文本优化的梯度类比物”：梯度告诉数值优化器方向，SI 告诉 LLM 提议器为什么失败与如何修。这一契约使提议器逻辑跨域可移植。

**Pareto 选择语义**。即便单目标，跨多示例/多指标评估产生的信号也远比标量聚合丰富：朴素做法塌缩为均分并总选 top-1，会掩盖强弱结构、迫使提议器“一次改进所有”。本文改为：逐任务/逐指标追踪分数并维护 Pareto 前沿——任何“在某件事上最好”的候选都存活；每次反思只给提议器 2–3 例 minibatch 以聚焦改进。选择算子继承 GEPA：目标集 J 上非支配候选集 P，对每个 j 取最优者集合 B[j]，按 |{j ∈ J: Φ ∈ B[j]}| 比例采样，把探索集中在广泛有效的解上。前沿规模不构成瓶颈（按前沿频率采样，ARC-AGI 有效使用了 200 个任务）。

**从 prompt 推广到任意文本工件的五项工程改造**（这是“统一接口”背后不可省的算法工作量）：(1) 面向单任务/多任务的新前沿类型与选择语义——GEPA 原始 Pareto 选择依赖多数据点评估，单任务只有一个数据点，必须改为逐指标追踪；(2) 评估前 refiner 修复步骤，拦截 LLM 常见生成伪影（畸形代码块、import 错误、语法问题）——对代码与 agent 工件，微小格式错误会导致评估完全失败；(3) 内容寻址的评估缓存，避免重复昂贵 rollout；(4) SI 类型化原语（域可移植提议逻辑 + 多模态反馈）；(5) 后端与统一接口间的适配层。

**机理分析（§6，基于圆排列轨迹）**：三机制。(1) SI 驱动定向算法切换：圆排列中呈现特征模式——半径塌缩→切换到 LP；中心放置差→切换 SLP；局部饱和→切换 bilevel L-BFGS；无 SI 时提议器只能观察“分数变了”而退化为无向变异。(2) 多模块 Pareto 蛙跳：代码工件与 refiner prompt 同时上前沿，互为对方下一次改进的基础——refiner 先发现 LP 法（此时 code=0.98、refiner=1.93），code 吸收 LP 追至 2.61，refiner 推进 SLP 至 2.63，code 再吸收 SLP 达到纪录；得分为 0.0 的破碎变异可被 refiner 恢复并保留在前沿，形成探索安全网。这是单工件系统（如 AlphaEvolve）不具备的协调机制。(3) Pareto 多样性防早熟：收敛时前沿同时保留 greedy、LP、SLP、bilevel L-BFGS、CMA-ES 多算法族，在 max 分/均分/EMA 稳定性/改进率等维度上共存，保证提议器始终有结构多样的父本可杂交。

ARC-AGI 案例的定性结果对理解“架构搜索被泛化模式吞并”很重要：进化出的四阶段流水线为——模式分析归纳规则 → 带 exec() 验证的代码生成 → 最多 2 次修复的迭代调试 → code-first 到直接 LLM 预测的结构化回退，即系统自发发现了 verify-then-fallback、迭代精炼这类通常需人工工程迭代的架构模式。

## 5. 消融要点

**SI 消融**（Facility Support Analysis 数据集，prompt 优化，带 SI = 评估器返回逐方面子分）：带 SI 条件 100 次 rollout 内验证分达 0.80，score-only 需约 600 次（约 6×）；终测分 86.32 vs 82.5。论文以“4–6× 收敛加速”概括。跨域复证（关键行）：圆排列 score-only 仅达最优的 93.96%；KernelBench 单任务 f₁.₁（≥1.1× 加速的 kernel 占比）32.3% vs 12.9%，均值加速比 4.11× vs 1.15×；KernelBench 多任务 f₁.₁ 40% vs 0%（均值 1.15× vs 1.03×）——SI 缺失时多任务模式几乎完全失效。

**多任务 vs 单任务**（10 个最优多任务问题以等额单问题预算重跑单任务）：多任务各阈值不劣，f₁.₀ 上 90% vs 60% 大幅领先。任务数扩展：20 题上 f₁.₀ 单任务 50% vs MT20 90%；f₁.₁ 单任务 25% vs MT20 40%，f₁.₂ 两者 15% 持平——收益在中速阈值最显著。机理是前沿跨任务迁移：内存合并、向量化访存、warp 级归约等模式发现一次即通过共享前沿成为其他 kernel 提议的父本。

**多任务的失效边界**：任务缺乏共享结构时迁移退化为噪声——圆排列不同 N 联合优化，单任务 2.6360、MT7 2.6313、MT11 2.5973，单调劣化（不同 N 的最优构型不可预测地变化，无可迁移结构）。结论：任务共享底层优化模式（如同型算子同硬件）时多任务获益，本质独立时受损。

**提议器敏感性**：GPT-5-nano 在圆排列上成本降逾 90%（$0.50 vs $6.00）、较种子仍大幅改进（0.98→2.512 vs 2.636），但终值一致逊于 GPT-5.1；AIME 上 nano 46.67%→50.0%（$3.71）vs GPT-5.1 的 60.0%（$6.44）——存在明确的成本-质量权衡，弱提议器可作低成本粗调但换取终值损失。

## 6. 贡献与启示

本文的实质贡献是证明了一个负结果的反面：LLM 文本优化不是“代码进化”或“prompt 工程”这类垂直技巧，而是通用问题求解范式——六个本质不同的域（代码、prompt、agent 架构、数值配置、调度策略、图像）在“工件序列化 + (score, SI) 契约 + Pareto 反思搜索”下被同一 API 与同一算法族覆盖并达 SOTA。工程上最有价值的判断是其成本与专长转移结构：反思开销极小、评估器主导总成本，故该范式适用性由评估器可观测的诊断丰富度决定；作者自述为“以优化专长换领域专长”——用户不再配置后端/超参/提示策略，只需暴露自己已理解的诊断信号。局限亦应如实看待：提议器质量上界决定候选质量；评估可能昂贵（ARC-AGI $144.70）；工件须可文本表示（连续参数需文本代理）；多任务收益依赖任务相关性；已展示的收益来自专家设计的 SI，SI 设计本身仍是领域专长活。

**音视频关联（笔记视角，非论文实验）**：论文未做任何音视频任务，但其三个机制层与音视频工程直接可接。(1) CUDA kernel 生成层：KernelBench 覆盖的 matmul/卷积/归约/逐元素/归一化正是视频超分、神经编解码、去噪等 NN 视频模型的骨干算子，87% 追平或超越 PyTorch、LayerNorm 3.32×、$4.51/kernel 的摊销成本，为边缘 GPU（V100 级）推理算子定制提供了一条比手写 kernel 工程更便宜的路径；同一范式外推到 codec 专用 SIMD/CUDA kernel（论文未验证，属外推）。(2) 云调度层：CloudCast 的多云出口成本最小化与 Can't Be Late 的 SPOT/ON_DEMAND 时限调度，与转码 farm、渲染突发、跨区分发的成本-时限结构同构，ADRS 结果可直接作为 AV 基础设施策略优化的参照系。(3) VLM 评估闭环层：SVG/CAD 任务中“渲染 → VLM 逐方面打分 → 分数回传为 SI”的回路，是感知质量代理评估（无参考质量打分）驱动优化的现成模板。(4) 泛化模式层：agent 即工件（ARC-AGI 从 10 行到 300+ 行）意味着剪辑/审片/转码流水线 agent 同样可作为单一文本工件被进化，架构与提示词联合优化。

- **paper:arxiv:2606.06473（MLEvolve）**：关联依据是 LLM 算法发现框架的通用性对照——MLEvolve 以多智能体 + 渐进 MCGS + 回顾记忆专攻 ML 算法发现；optimize_anything 以单一声明式 API 覆盖含算法工件在内的任意文本工件（圆排列 bilevel 求解器、黑箱求解器代码均为被发现的算法），代表“领域专用流水线 vs 通用接口”两种取向。
