## 1. 背景与动机

长时程智能体的交付物正从代码扩展到报告、电子表格、多文件工件，其正确性评估本身成为高成本工作。与代码/数学域不同——那里有单元测试、可执行检查或形式化证明器提供无参考答案的直接反馈——通用办公类任务缺乏对整份输出的等价校验手段：核查一份报告可能需要溯源声明、重算数值、跨多个文件解释需求。论文将问题限定为**同模型测试时验证**：生成器与验证器共用同一冻结模型与工具，测试时无参考答案、无评分 rubric。该设定的依据有二：前沿实践中不存在比生成器更强的裁判；固定底模保证验证器的任何增益都来自 rollout 池与任务环境，而非更强模型的知识注入。

此设定下验证器有两个独有信息源：(1) 重复采样得到的 rollout 池；(2) 任务环境（源文件、数据、约束）。现有测试时验证方法几乎只用前者——多数投票/自洽性取最常见答案，LLM-as-a-judge 通读打分——依赖的都是“模型已经相信什么”，而非“环境能提供什么证据”。论文的核心经验发现（APEX-Agents v1.0、Claude Opus 4.8、每任务 10 条 rollout 的池，覆盖 434 任务、1,692 条声明；离线分析读取基准 rubric 判定正确性，rubric 对验证器不可见；值正确定义为断言该值的 rollout 多数通过对应准则）是：**共识隐藏错误，分歧暴露正确替代**。具体地，917 条共识声明（声明熵 H=0）中一致值 34% 被判错误；775 条争议声明（H>0）中 74% 含至少一个正确候选，而最高频值仅在 47% 的争议声明中正确。这意味着投票/池内选择存在结构性上限：全员一致的错误无法靠选择修复，正确答案常在少数派中。

由此确立两条互补检查任务：对争议声明，用环境证据区分已暴露的候选（并允许全部候选皆错）；对共识声明，先构造“共识可能如何错”的假设再对环境检验。三条贡献：该验证原则；免训练、即插即用的通用验证 harness（论文称首个面向长时程任务的智能体验证 harness）；验证技能可从失败反馈自进化。同时发布约 26,000 条 rollout（5 基准 × 2 模型 × 每任务 10 条，生成成本超 10 万美元，含轨迹、交付文件与 grader 分），仅依赖池的结果（单 rollout 均值、oracle 曲线）可离线复现。

## 2. 方法总览

形式化：任务 t=(s,E)；rollout r_i=(d_i,w_i,τ_i) 由交付工件、终态工作区、动作轨迹组成，池 R 共 N=10，所有被比较方法共享同一冻结池。工件被分解到**声明**层：关于任务相关数值、解释或需求满足的断言。对每个共同问题/需求 p，将 N 个工件给出的值归并为经验分布 π_p（等价表达记同值、缺省记独立值），声明熵 H(π_p) 由此定义；H=0 为共识声明，H>0 为争议声明。关键语义：熵只度量候选间变异，全错的一致性仍是 H=0。

VeriHarness 与生成侧 harness 对称构造：Verifier = (M, H_V)，H_V = (W, T, Π, S)——工作区 W、证据工具 T、验证协议 Π、技能库 S。协议 Π 将两类检查任务分配到两个互不可见、并发运行的独立模型上下文：

- **分歧解析器**：定位争议声明，将候选值溯源到来源与计算，选择最能区分候选的检查，据证据剔除被反驳候选，产出证据记录 L≠；
- **共识挑战者**：对无竞争值的共识声明提出失效假设并对环境检验，覆盖共识值/共识解读/共识遗漏三类，产出记录 L=。

随后**裁决**在全新上下文（不继承任一调查者的对话历史）审阅两份记录与任务、池，输出 (base, revision_plan, unresolved)：base ∈ R∪{∅} 为改造基底，revision_plan 为有证据支撑的修改清单，unresolved 为证据未决声明。交付时应用计划得 r* 并附验证记录 C=(L≠, L=, base, revision_plan, unresolved)。证据获取是主动的：验证器依据任务、池与已得证据选择检查 χ，证据 e=E(χ) 由在环境中实际运行获得（读源文件、重算合计、查文件元数据等），可支持、反驳候选或确立池外修正值；证据不足则声明保持未决。目标是在外部 grader（验证器不可见）下最大化 r* 质量。

## 3. 关键设计

**3.1 分歧解析器：信息增益驱动的检查选择。** 解析器对争议声明维护基于已有证据 e_<k 的信念 b_p（区别于经验频率 π_p），按期望信息增益（Lindley 1956 形式，期望信念熵的下降）在**定性层面**选择检查——论文明确不实际计算。每得证据即执行淘汰 V_p ← 与 e 一致的候选；证据推翻全部候选时，仅当证据能确立新值才记录，否则声明开放。判断进一步检查不太可能改变结论时停止。这一“候选暴露→证据区分”闭环正是同模型验证的优势来源：单次生成从未遭遇的竞争值在池中被显式化。

**3.2 共识挑战者：从“无竞争值可测”到主动假设生成。** 共识声明没有可测替代值，挑战者须先构造失效假设，检查优先级按 P(χ 暴露该共识声明失效 | t, R, e_<k) 定性评估。三类对象：(1) **共识值**——从原始输入重算、将标签与源元数据比对（论文工作示例：三个 rollout 均将 FY2025 营收标 USD 100m/120m 不一，且全部标 USD；查版本历史确立应引最终版报告、查其元数据发现币种应为 EUR，最终修正为 EUR 120m）；(2) **共识解读**——将共同解释对照任务指名文件、源所述期间或工作簿自带定义检验；(3) **共识遗漏**——将交付工件对照任务描述查所有 rollout 都忽略的需求。遗漏在任何工件中都不出现，必须先被“可见化”为验证目标——提出失效假设需要池本身不提供的失效模式知识，这正是技能库的职责（如符号约定技能给出全员一致值之外仍可检验的具体属性）。

**3.3 裁决与证据支撑修订。** 双调查分离上下文以避免争议声明挤占共识声明的注意力（消融显示合并损失 0.8 分）。裁决上下文可维持、推翻或留置调查结论，按“实质性需求上证据支撑缺陷最少、按对交付物的重要性加权”选 base，无可用起点时 base=∅ 从输入与证据重建。交付规则：空修订计划原样返回 base；未决声明在记录中保持标注，格式允许时对未决解读并列两种读法（base 读法在前）。每条证据记录链接声明—检查—证据—结论，使修改可溯源并保留开放问题，这些记录同时是技能进化的输入。

**3.4 工作区、工具与技能库。** 工作区将各 rollout 工件/终态/轨迹与任务输入、环境只读挂载于无网络沙箱，仅输出目录可写；电子表格渲染为单元格级文本。技能为“短文本 + 可选脚本”的可复用失效模式与检查程序，核心分工是**工具执行检查、技能决定查什么**（工具读财务表；技能指示检验增长率标签所跨年份与公式区间是否一致），且排斥任务特定答案。人工库 18 个技能、四类：6 个证据技能（evidence-xlsx/pdf/docx/pptx/bundle/patch，附 xlsx_dump、pdf_tables、patchlab、pageprobe 等脚本）；4 个解析技能（resolve-answer/bundle/workbook/patch，规定裁决证据与权威顺序，如工作簿权威序为输入批注单元格>标签>同列公式>任务措辞）；3 个证伪技能（falsify-answer/bundle/workbook，逐条列举整池同类工件共同出错的路径）；5 个修订技能（repair-prose/bundle/record/xlsx/patch，说明该类工件如何被评分、未决声明如何收口、什么绝不可改，如 patch 类“改代码树、不改补丁文本，补丁须可应用、可复现并通过 base 已通过的测试”）。运行时为开源 pi coding agent 之上的薄层（Claude 经本地 LiteLLM 代理），验证器持文件读取/检索/shell 工具；协议与技能亦可作纯文本指令注入 Gemini CLI 0.46.0、Claude Code 2.1.246、Codex 0.149.1，以宿主 CLI 的工具与沙箱替代专运行时。保留专运行时的理由：程序化执行协议（分离上下文、记录传递）、显式配置 W 与 T、以及支撑受控组件消融。

**3.5 同模型为何能查出自身错误。** 论文归纳四个不依赖参数更新的优势来源：暴露的替代项（多 rollout 把竞争值显式化）；聚焦检查（面向已完成工件的特定声明分配注意力，双上下文分别保留给争议/共享声明）；环境证据（定向溯源或重算可揭示 rollout 未纳入的证据）；累积技能（含“所有候选都遗漏的需求”的检查知识）。其价值取决于能否找到有信息量的检查——关键声明未被检视或证据无法裁决时共享盲点仍会存留。

## 4. 实验结果

设置：五个长时程工作区基准——APEX-Agents v1.0（480 任务，银行/法律/咨询，专家 rubric）、Workspace-Bench Lite（100 任务，rubric 裁判）、WorkBuddy Bench（200 任务 = code 80 + office 50 + web 70，安全域因 API 安全告警不运行，复合验证器）、SpreadsheetBench 2（321 任务，重算并与参考工作簿逐格比对）、JobBench（65 任务、35 个白领职业，rubric 裁判）。Gemini 3.5 Flash 与 Claude Opus 4.8 同时充当生成器与验证器（thinking high），生成在各基准原生 scaffold 中进行，每任务冻结 N=10 池；各基准用自身 grader 评分，裁判模型类基准中 base 与交付同轮评分、按存档 base 分加同轮差分以控制裁判漂移；报告三种子均值。

| 方法（左：Flash / 右列含 Opus） | Flash Avg | Flash APEX | Opus Avg | Opus APEX |
|---|---|---|---|---|
| 单 rollout（池均值） | 47.2 | 48.1 | 49.6 | 35.8 |
| 多数投票 | 47.5 | 47.3 | 50.4 | 38.0 |
| Best-of-N（judge） | 47.3 | 47.2 | 50.6 | 38.4 |
| 两两锦标赛 | 49.1 | 49.2 | 51.3 | 38.4 |

要点：(1) VeriHarness (select) 在全部 10 个模型×基准组合上超过所有选择类基线，每个格子的增益均超过跨种子标准差；(2) 多数投票与 best-of-N 在此类任务上平均增益微弱（Flash 下 +0.3/+0.1），印证池内信念聚合的天花板；(3) 给足同样工作区与证据工具但无协议/技能的 agentic verifier 仅恢复约一半增益——环境访问本身不充分；(4) 修订在全部 10 个设置再加值：Flash 最大增量在 WSB（65.4，较单 rollout +8.9），Opus 最大在 APEX（+11.7）；无证据检查的池聚合在所有基准低于 harness，说明修订增益来自证据记录而非重写本身；(5) 协议注入现有 CLI：Flash 下两个 CLI 在每个基准与专实现差距 2 分以内（Avg 51.5/51.4 vs 51.6）；Opus 下在 WSB 与 WorkBuddy 恢复大部分、APEX 约一半，但 JobBench 退回单 rollout 水平（Claude Code 在 SB-2 亦然），表明宿主运行时的操作循环影响协议执行质量。

成本（牌价、缓存输入按缓存读计费）：Flash 下选择 $1.44/任务——为 LLM-as-a-Verifier 的十分之一而增益约两倍，且低于两两锦标赛；Opus 下 $3.92/任务，约为 LLM-as-a-Verifier/多数投票/best-of-N 的一半、锦标赛的四分之一；修订约为选择的 3 倍。便宜的结构性原因是调用为同一工作区上的增量回合，86–91% 输入 token 命中缓存；若缓存按全价计，选择成本为 Flash $5.40 / Opus $13.06，仍处成本—增益前沿（基线每次调用重读整个 rollout、不吃缓存）。CLI 部署在 Flash 下以约 3 倍于专运行时的成本达到同等增益。oracle（62.7/63.1）与 harness 间仍有约 9–10 分差距，说明固定池内还有大量选择空间未利用。

## 5. 消融要点

**组件消融**（完整 harness 去一部件，均含修订，五基准均值）：

|---|---|---|
| 单 rollout | 47.2 | 49.6 |

| 完整 VeriHarness | 53.4 | 56.1 |

两部件增益互补：解析器份额在争议声明密集的 APEX 最大；两者在 SB-2 与 JobBench 最接近（单位、符号约定、遗漏需求类共享错误占缺口比重更高）。去技能库每基准均降，APEX 损失最大；合并上下文损失 0.8 分（两模型一致），支持分离上下文设计。

**选择增益来自分歧池**：APEX/Opus 按池声明熵分组，154 个全共识池上 harness 选择分仅高于池均值 0.6 分，262 个争议池上高 6.1 分；争议池内增益随熵单调递增：低熵 4.5（n=139）、中熵 7.7（n=108）、高熵 9.4（n=15）。与第 1 节“分歧暴露正确替代”的观察闭环。

**挑战者的安全性与盲点**：APEX 上将挑战者对全员一致声明的判定匹配到 rubric 项——它**从未推翻过所有 rollout 都答对的声明**；存活的一致错误中约 70% 是它检查了正确的中间量而错误在下游步骤，14% 为同量但定义/期间/源版本不同，12% 为确认了被评量的错误值，4% 为遗漏/匹配噪声。结论：验证器倾向于在 rollout 停下的地方停下，“往哪再看”需要失效模式先验，由技能库供给。

**技能自进化**（Opus 兼任库提议者，APEX 与 SB-2 各自独立运行；约 3:1 划分开发/保留集，同源工作区/模板任务先分组再切分防泄漏；完整 harness 含修订；每轮 K=3 起步、后 K=5 个候选库，自动过滤器拒绝含任务标识/基准名/开发文件名/参考答案值的候选，脚本限时十分钟，开发分配对增益非负才替换）：APEX 保留集四条件——空库 A 38.6、人工库 B 45.3、A 进化 C 49.6、B 进化 D 52.1；SB-2 为 32.8/35.7/38.5/39.4。即从零进化较空库 +11.0（APEX）/ +5.7（SB-2），且两个基准上均超过人工库；从人工库再进化在其上再加 +6.8 / +3.7。进度上 D 更快：APEX 上 C 第 8 轮才达其最终轨迹分 49.6，D 第 1 轮即达；SB-2 上 C 第 8 轮达 38.5，D 第 7 轮以 39.4 反超。保留集分仅在决策后记录、从不用于选择；两条轨迹都出现过保留集回退——进化按开发分选择，无统计控制。

**习得库构成**：四个进化库共 95 条检查中，5 条复述人工检查、48 条以脚本/常量/文档类型将人工检查具体化、42 条为新增——约半数是把通用检查落成针对一类工件的可执行程序。新增检查覆盖共识盲点：APEX 与 SB-2 两次独立进化都习得“与池一致的 重算结果不得当作确认”——提议者能同时读到验证者证据记录与 grader 判定，从而看见“验证者确认了被 grader 判错的共享值”这类案例并反推出规则。

## 6. 贡献与启示

方法学层面，论文把“验证什么”从工件级细化到声明级，并用候选分布熵做验证目标分诊：熵>0 的声明有显式替代项可测、熵=0 的声明需要假设生成——这一二分把同模型验证从“打分/排序”重构为“证据采集 + 裁决 + 修订”的智能体工作流，且每次修改都有可溯源证据链。工程层面三点：(1) 免训练、即插即用，协议与技能可作文本指令移植进现有 agent CLI，专运行时的价值在于程序化执行协议与受控消融；(2) 增量回合 + 高缓存命中（86–91%）的成本结构使其位于成本—增益前沿，对任何要在产线叠加验证层的系统是可直接借鉴的形态；(3) 验证记录天然构成声明级监督信号，论文将“记录→生成器训练数据”列为下一步——这是测试时方法通往训练信号的清晰接口。局限应如实看待：依赖 N=10 rollout 池（与所有基线等生成成本但绝对成本高）；不输出 rollout 级标量分，难以直接作 reward；仅限同模型设定（更强裁判的增益会混淆 harness 贡献与模型能力差）；多回合调查引入时延，定位于质量优先的专业交付物场景；技能进化依赖开发集 grader 反馈，跨任务分布泛化与无监督进化未验证。

对音视频技术上下游的启示：音视频长链路智能体（媒体库检索—剪辑—转码—包装—报告）同样面临“无单元测试、无参考答案”的输出验证问题。VeriHarness 的范式——多 rollout 采样 + 声明熵分诊 + 对源素材元数据/可重算量的定向核查 + 共识挑战（如全员沿用同一错误时间码基准或转码参数的场景）——是结构上可直接迁移的验证架构；其“验证记录→声明级训练信号”的出口，也与用可验证中间检查监督生成式媒体模型的路线相通。此为方向性迁移判断，论文本身未涉及多媒体实验。

## 7. 与其他论文的联系

- **SkillDuet（arxiv:2611.12109）**：同为技能库演化循环。VeriHarness 在固定模型/协议/工具下仅演化验证技能，准入依据是开发任务上基于 grader 反馈的配对增益；SkillDuet 以响应反馈协同 LLM 参数更新与外部技能库，实现技能级递归自改进。共同点是“技能作为冻结模型之外的可进化知识层”，差异在 VeriHarness 只演化验证侧（查什么、怎么改）而不触碰生成侧 scaffold。
- **FGSE（arxiv:2611.14326）**：证伪门控的自进化。FGSE 把经验教训作为可证伪假设、经三类探针验证后才写入记忆；VeriHarness 的共识挑战者在验证时同构地“先提出失效假设、再以环境证据检验”，而其技能库更新的门控用的是开发分配对增益而非证伪探针。两文在“提交前先证伪”原则上一致，在门控机制上互补。
- **TRUST（arxiv:2611.10787）**：直接针对本文自进化 loop 的缺口。VeriHarness 的库替换只要求开发集配对增益非负，附录明确记录保留集出现回退且无统计控制；TRUST 用在线多重假设检验为递归自改进控制错误进化率并提供统计保证，恰好是这类“开发分选择”循环缺失的准入统计层。
- **LongCapHarness（arxiv:2611.10463）**：同属“冻结模型 + harness 层 + 递归自我改进、免数据合成与后训练”的路线。LongCapHarness 挂接长上下文推理底层能力，VeriHarness 挂接验证能力；两者都以低于基线约一半的成本取得增益（本文：缓存命中 86–91%，选择 $1.44/$3.92 每任务），共同支撑“能力扩展可以不训模型而在 harness 层完成”的判断。
- **InfraRSI（arxiv:2611.11558）**：结构上平行——在开放式智能体任务中嵌入五阶段验证工作流以保障产出质量并控制调用成本。差异在于 InfraRSI 验证的是自身生成的训练基础设施优化方案（生成侧质控），VeriHarness 验证的是外部任务工件（独立验证侧）；两者的多阶段验证工作流设计可互为参照。
