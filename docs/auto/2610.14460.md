# Re-executing Coding-Agent Evaluations: Unchanged Decisions and Unresolved Policy Risk

## 1. 背景与动机

这篇论文属于 LLM 编码智能体评测基础设施的审计型实证研究，核心问题是：可执行测试的判定到底有多稳定、对评测策略配置有多敏感。这直接关系到榜单排名、智能体 RL 的奖励信号以及自我改进系统的选择压力——这三者的输入都是同一个二值判定，而判定不仅取决于测试本身，还取决于镜像内容、依赖解析器、网络策略、缓存状态与 CPU/内存/时间限制。

作者指出两类被既有工作分别处理但未被联合检验的风险：

- **离线化评测对非参考解的结构性误杀**。出于可复现性与防作弊（DSec 报告智能体通过模块代理从 GitHub 拉取上游修复代码）的考虑，评测器趋向离线化：Lego-RL 将测试依赖打包进任务镜像，SWE-rebench V2 预构建环境，SWE-bench Pro v1 评测器提供 `--block_network` 离线选项。但常见的验证方式是“金标补丁仍通过、空补丁仍失败”，这只验证了参考解。若一个正确解 bump 的模块版本与金标不同而离线缓存按金标 go.mod 解析，构建会失败并得到错误判负。Lego-RL 工具链文档自己承认这一点（其缓存按金标 go.sum 解析，“bump 到与金标不同版本的正确修复依然无法下载”）。在 RL 场景中，这类错误等价于把失败 rollout 的奖励错赋给已解决的 rollout，且错误是结构性的（落在依赖与金标不同的解上），区别于 Cai et al. (2025) 建模的一般性噪声验证器。
- **自我改进档案的判定可复现性**。自我改进智能体（如 DGM）用测试判定在数百个版本间比较并晋升版本。若重执行同一冻结补丁得到不同判定，记录在案的决策是否成立？

论文以两项预注册研究分别检验上述两点，两者均预测负结果，且负结果如约出现——但作者明确指出负结果不等于安全保证（Study 1 的预注册本身就警告了这一点），并对暴露样本量不足导致的“3% 风险未解决”做了坦诚的统计学边界分析。这种“证据到结论”的克制是本文方法论上最显著的特点。

对音视频/RL 系统工程师的上下文意义：凡是“以自动判定为奖励、以判定差驱动选择”的闭环系统（RLVR、自改进 agent、benchmark 驱动的模型筛选），其奖励通道的策略敏感性与重执行噪声都是同构问题。

## 2. 方法总览

两项预注册研究 + 一个无 kill 规则的扩展 + 一个可行性分层，全部用“重执行已冻结工件”的方式检验判定稳定性，预注册协议、代码、种子在确认性数据采集前以 pushed commit 封存。

**Study 1：SWE-bench Pro v1 离线评测重放。** 语料为 SWE-bench Pro v1 公开切分（固定 revision），官方运行脚本与解析器固定于 commit 66f92766。维护者发布九个 agent 运行的补丁及判定；候选 = 官方判定为 resolved 的补丁。抽样框 = 含 resolved 候选的所有任务（减去 pilot/可行性/已知损坏任务），按种子哈希排序，确认性样本为前 120 个任务，且在获取任何候选补丁前仅凭元数据完成预留。每任务至多贡献四个候选（按模型轮转冻结顺序）+ 金标/空补丁控制 + 至多一个官方 unresolved 负控制。共 664 个工件、5,997 次容器运行、93.99 容器小时。

设计为多臂对照：

- **A0（基线）**：模拟官方网络化评测契约——容器无网络，但用只读文件模块代理按 go.sum 种子、逐轮添加该工件验证所请求的每个模块版本文件（字节从公共模块代理在宿主机获取，Go 工具链按 go.sum 校验）。A0 必须三次复现官方判定，候选才算数。
- **A1BLOCK（确认性分析中的 A1）**：离线策略 PBLOCK，即评测器自带的 `--block_network`，禁网且不改其他任何东西。唯一确认性策略。
- **A2（恢复臂）**：按候选自身 A0 镜像提供候选声明依赖（排除任务自身模块路径，因其后续版本可能包含修复）。
- **A1LEGO**：仅对金标补丁编辑 go.mod/go.sum 的 Go 任务，重建 Lego-RL 金标绑定缓存（PLEGO 策略），描述性分析。

有效性规则：任务在策略下“合格”当且仅当金标补丁三次全过、空补丁三次全败；只有合格任务上的候选计入。每个 (工件, 臂) 单元跑三次，每次新容器、4 CPU、8 GiB、无网络、官方一小时超时。**确认性可逆损失**的定义极其严格：A1 三次全拒 + A2 三次全解 + 受限日志含预注册网络不可用签名（NET_RE，精确的 case-sensitive 正则，含 `dial tcp`、`DNS lookup errors`、`no such host` 等）。候选按任务内纳入概率倒数加权（两万次固定种子蒙特卡洛估计），主量为加权损失率，任务聚类 bootstrap 的单侧 95% 下界。Gate 要求 ≥200 个可评估候选、≥2 模型、率 ≥3%、下界 >1%、损失覆盖 ≥5 任务；完整有效样本低于阈值即 KILL。预注册功效模拟：真实率 3% 时通过概率仅 0.48（独立）/0.40（聚类），5% 时 0.95/0.88——即设计在 3% 处本身是低功效的，作者透明披露。

**Study 2：DGM 自我改进档案重执行。** DGM 在 SWE-bench Verified 上（每版本至多 200 任务）评估自修改的编码智能体，档案含 245 个 agent 版本、6,006 次评估、三臂（完整系统 / 无开放探索 / 无自我改进）。重构两个记录决策：D1（最优节点选择，八个完整系统节点在完整任务集上，记录为 100/200 vs 次优 87/200）、D2（臂排序，臂内最优分数排序：100/200、23/59、14/60）。分级门限（staged gate）不可重构——档案中 89 个保留非根节点里 38 个的首子集成功数低于发布阈值（附录 E）。

重放 1,929 个选定单元（D1 八节点 + 每臂记录分数前三节点含并列，共 15 节点）：每单元标称（4 CPU）三次 + 争用（1/4 CPU 配额）三次，每次全新网络隔离容器。三个量：Q1 重跑不稳定性（标称判定非全一致）、Q2 漂移（记录判定 ≠ 标称多数）、Q3 争用分歧（争用多数 ≠ 标称多数）。只有 Q1/Q3 型反转计入假设；反转须在确认批次复现。漂移单独报告（无漂移单元同时不稳定）。

**重放保真度检查（封存前发现，附录 E）**：DGM 对补丁先剥离测试文件与 tox.ini 的 diff 再评分——直接 apply 存档补丁会重放 DGM 从未评估的测试改动，作者重新实现该过滤器，所有 6,006 单元的评估补丁与存档在大小和 CRC32 上匹配；重放镜像 commit 了存档运行未 commit 的 setup 编辑，每次运行恢复存档布局；评分用 DGM README 钉定的 grader commit dc4c087c（2024-10-25），且全部 6,006 份存档日志的重评分须与存档判定 ≥99% 一致（实际 99.88%）。

## 3. 关键设计

**分层暴露结构是全篇最关键的设计洞察。** 281 个可评估候选中，222 个 Python/JS/TS 补丁在三个臂下面临完全相同的配置（A0/A1/A2 对非 Go 任务不加任何东西），设计在这些任务上只能观测背景性分歧——而实际为零。真正被离线策略改变配置的只有 59 个 Go 候选（25 任务）。随机任务抽样会稀释这一对比。这直接引出 Lesson 1：审计应直接抽样策略暴露分层，并在采数据前检查独立单元数是否足以分辨目标容差。

**零事件上界的算术设计极限。** 59 个独立暴露候选零拒绝的单侧 95% Clopper-Pearson 上界为 4.95%，不排除 3%；需要 99 个独立暴露候选零拒绝才能压到 3% 以下。任务层面更糟：即使抽样框中全部 91 个 Go 任务都合格且零拒绝，任务独立上界仍为 3.24%——即在该框架下任务级估计原则上无法分辨 3% 假设。这是把“阴性结果 ≠ 无风险”量化到具体数字的范例。

**NET_RE 签名与三重门条件**将“策略性拒绝”与一般性 flakiness 区分开：只在受限臂拒绝、恢复臂全解、且日志有网络不可用签名，才计为确认性可逆损失。这一条件在扩展中主动放宽（任何一次受限运行失败即计拒绝，且不要求签名与 A2 恢复），因此扩展的计数是描述性的——这一放宽与控制失败共同构成扩展“不确定”的定性。

**金标绑定缓存重建的保真度论证**（附录 D）值得细读：在金标状态上运行上游 builder 的 `go mod download -json all` 与 `go list -deps -test ./...`，同一钉定镜像与工具链，用文件代理替代上游代理、禁用校验数据库，以金标 go.sum 中所有模块版本的 .mod/.info 元数据文件种子镜像（注册偏离：zip 仅按需提供），迭代至无新请求。11 个任务上两命令末轮均无错误输出且无“最新版本”查询。作者明确这只是“所需模块版本与上游 builder 缓存一致”的校验而非文件级一致，因为跑上游 builder 需联网容器。

**权重与估计口径。** 候选按抽取时仅凭可用性估计的任务内纳入概率倒数加权，2 万次固定种子蒙特卡洛。敏感性分析将合格任务上 11 个基线未复现候选计为损失时加权率 3.90%——超过 3% 但不满足注册的下界与五任务条件，作者以此强调 KILL 不提供安全保证。

**RQ4 的安全准则与负控制的局限**：恢复臂不得在其他两臂均拒时接受任何候选（防止 A2 无中生有）。该准则实际未通过：一个官方 unresolved 的 Python 候选在三次恢复运行中通过一次（其余全败），其恢复臂无镜像、与其他配置相同，与背景 flakiness 一致，原因未隔离，按冻结规则计数。另有标签自身局限：112 个抽样负控制中 9 个（扩展 63 个中 3 个）在所有臂所有运行中都 resolved，重放无法复现官方拒绝。

结论 KILL：H1 不支持。完整性审计在第四轮通过（数据后附录仅修正报告措辞，不改运行）。两项无效性份额均低于预注册 10%：4/120 任务控制未完成（3.33%，均为同一 JS 仓库的测试 worker 超 8 GiB）、2/120 金标基线未复现金标判定（1.67%）。113/120 任务在 PBLOCK 下合格；3 个不合格任务中 2 个金标补丁在所有臂（含基线）都失败，第 3 个（Go 任务 Vuls）基线与恢复臂全过、受限臂三次全败于模块下载失败——离线选项无法给该任务的参考解评分。

**暴露与事后上界（探索性、非加权）**：59 个暴露 Go 候选零拒绝的候选独立上界 4.95%；25 任务任务独立上界 11.29%；若 13 个不可评估 Go 抽取计为拒绝则候选独立上界 27.17%。无一排除 3%。

**扩展（63 个后续 Go 任务，单独预注册，无 kill 规则）**：不确定。一个合格任务的金标补丁三次基线运行中失败一次（注册控制规则不允许弃任务或重跑），注册计数为 59 个合格任务中 2 个拒绝任务（其一即该控制失败任务）。两个拒绝任务上候选均全过基线与恢复运行、三次受限运行中败一次。三次受限失败与失败金标运行都记录到同一 Teleport lib/srv 心跳代码的 nil-pointer panic——该 panic 同样打击了拥有受限臂所缺模块的基线臂，故并非仅限策略，策略贡献量未测。描述性上界：任务带拒绝比例 10.29%（2/59，任务独立）、候选拒绝率 4.25%（2/146 复现候选）、与前缀 25 个合格 Go 任务合并 7.31%（2/84 任务）。

**RQ3（金标绑定缓存）**：前缀含 1 个金标 bump 模块任务，PLEGO 下无损失；扩展补 4 个（即 PBLOCK 下金标失败的 4 个），其 9 个可评估候选无一丢判定。唯一缓存致拒来自可行性分层（刻意选出 11 个此类任务，非流行率估计）：PBLOCK 在 8/11 任务上败金标补丁，重建缓存在 11/11 全过。这 11 个任务中 7 个的 15 个基线复现候选里，**6 个（3 任务、4 模型、5 次运行）在缓存下三次全败**，加上其自身许可模块后三次全过。一个 Flipt 任务上，三个模型的候选各自引入金标 go.sum 中不存在的 Masterminds/semver 版本（v3.1.1 或 v1.5.0），基线与恢复各 3/3 解、缓存下 0/3。

**RQ4（候选感知配置）**：恢复臂恢复可行性分层的全部 6 个损失；确认性运行无可恢复对象；安全准则因上述 Python 负控制的一次性通过而未达。

**Study 2（1,929 单元 × 6 运行 = 11,574 次运行，68.55 容器小时，无超时/内存杀）**：重评分复现 6,006 存档判定中的 5,999（99.88%），7 个分歧全部在一个 Astropy 任务上（其参考测试列表在 SWE-bench Verified 的某个副本中被修订）。重跑不稳定性仅 2 单元，且争用分歧也仅同 2 单元，均属一个 Sphinx 任务（sphinx-10466）；独立假设下单侧 95% 上界每单元 0.33%、每任务 2.35%（1/200）。两类不稳定均未反转 D1/D2，无需确认批次，预注册检验 KILL。替换最多将 D1 差距从 13 缩到 12 任务；臂排序 (100/200, 23/59, 14/60) 不动。事后分析：反转 D1 需至少 13 次定向翻转、D2 顶对至少 7 次；23 个漂移单元超过 7 但 22 个落在 D1 八节点上、1 个在无开放探索节点上，D1 冠亚军上净变化均为 0——D2 成立既因差距也因漂移落点。

**漂移（Q2，23 单元 / 1.19%，4 任务，每单元六次运行全部一致）**：7 个源于参考测试列表修订（删掉了存档运行未报告为通过的必需测试）；9 个在两个 Sphinx 任务上，其必需测试抓取外部 URL，网络隔离重放无法到达而存档运行联网；7 个在一个 Django 任务上，两种测试列表下原宿主机每次重跑都解，原因未隔离。

## 5. 消融要点

本文没有传统意义的消融，其“消融”角色由探索性跟进（附录 I，X1–X5，均标注为不重算封存门限）承担，且多数结论是“决策不动、原因未隔离”：

- **X1 第二宿主机重放**：全部 11,574 次运行在第二台机器重跑（6 个 4-CPU 槽位、调整 CPU 亲和性与调度优先级）。匹配运行索引上判定一致率 99.49%（描述性）。原 23 个漂移单元中 **7 个（django-10097）在第二台机器不再分歧**——它们在原宿主机全部 42 次运行中全解、第二机器 42 次全不解（日志含与存档失败签名匹配的数据库错误）。注册复现准则 NOT MET（要求保留每个原漂移单元），但名义多数分歧 10/1,929 低于容差、重构决策不变。原宿主机运行时与日志未检查，原因未隔离。
- **X2 重建镜像对比**（2026-10-05 快照，5,787 次标称运行覆盖全部单元）：标称多数在 **16 单元（0.83%）** 上改变（8 Astropy、7 Django、1 Sphinx）。8 个 Astropy 单元钉定镜像下每次都不解、重建镜像下每次都解，两镜像 pytest 版本分别为 7.1.2 与 7.4.0，钉定镜像日志有 suite 错误——但该对比不隔离 pytest 替换效应。注册报告条件（端点改变或 >1% 分歧）未触发。
- **X3 grader 版本对比**：SWE-bench 5.0.2 对存档日志直接返回全量 not_found（缺测试输出定界符），声明式适配器（仅加 Start/End Test Output 定界符）后所有单元判定与钉定 grader 一致；但两 grader 下均 unresolved 的单元上有 7 个逐测试成败赋值不同——单元级一致不等于解析器/规则等价。709 个适配后 not_found 按未解处理。D1/D2 不变。
- **X4 套件不完整性诊断**（exploratory-unsealed）：三检查规则在 189/1,929 单元（9.8%）触发，严格变体 150（7.8%）；13 单元钉定镜像标记、重建镜像不标记（其中 8 个变为 resolved）。traceback 检查也标记了 15 个记录为 resolved 的存档单元；两个变体都不捕获 django-10097 失败族。文本模式分组，非因果归因。
- **X5 测试基础设施干预**：6,006 存档单元中 1,291 的评估补丁触碰被标记文件（conftest.py、pytest.ini 等），其中 1,203 的标记编辑仅为 harness 预安装命令插入的依赖版本 pin（按加行字符串分类，不证明 agent 撰写了这些编辑）。59 个记录 resolved 的重放单元（7.67%）做移除标记文件 diff 块的单次干预：53 解、6 不解——但 6 个失败在全补丁运行中也失败，故相对存档接受度不提供“移除导致失败”的新证据；镜像内既有环境编辑保持不动。该干预不能排除档案中存在奖励操纵。

版本覆盖审计（附录 H，2026-10-07 核查）给出 CURRENT / TESTED-PIN / FIXED-UPSTREAM / UNVERIFIED-CURRENT 四类标注：如 v1 评测器与镜像在上游 head 不变（CURRENT），Astropy 7606 的空参数化条目在上游某 commit 已修但 DGM 实际加载的 princeton-nlp 副本仍保留（哪个副本评分决定 7 个 Astropy 分歧是否出现），SWE-bench Pro V2（2026-09-22 起默认配置，网络化验证器、新镜像、丢弃前缀 120 任务中 13 个与扩展 63 中 4 个但保留前缀全部 28 个 Go 任务）完全未测。

## 6. 贡献与启示

**核心贡献**是三项性质不同的证据及其严格边界：

1. **阴性但功效受限的策略检验**：SWE-bench Pro v1 离线选项在 59 个暴露 Go 候选上零拒绝，但 3% 暴露风险在统计学上未解决，且任务级估计在该框架下原则上无法分辨 3%——这不是实验失败而是设计极限的显式计算。
2. **存在性证据**：重建的金标绑定缓存在刻意选择的分层上拒绝 6/15 已接受候选（金标自身 11/11 全过），证实“金标验证 ≠ 策略对替代解有效”，并为 Lego-RL 文档中自述的缓存限制提供了实例。候选感知配置（提交后补装候选自身声明依赖）恢复全部 6 个损失，但其“不误收错误解”的性质未验证（确认性安全准则实际未通过）。
3. **决策稳定性**：DGM 的两个记录端点在原重放、第二宿主机、重建镜像、grader 5.0.2 适配对比下均保持；但 7 个漂移单元跨宿主机不复现、16 个多数判定随镜像重建改变，环境噪声是真实存在的，只是被 D1/D2 的大差距（13 任务 / 0.110、0.156 分数差，且封存前已知）吸收。

**四条审计方法论教训**均有直接工程含义：（i）围绕策略暴露单元规划抽样，事先核算独立单元数与容差的匹配——本文示范了 Clopper-Pearson 零事件界如何用来做这个核算；（ii）预注册间歇性崩溃的处理（扩展的 nil-pointer panic 同时打击基线与受限臂导致整个扩展失效；可行的做法是基线臂先跑 k 次金标做稳定性筛选，需报告合格总体的条件化）；（iii）重执行前核对补丁与评分输入（DGM 的测试文件过滤、镜像 setup commit 差异都可能默默改变重放语义；size+checksum 比对抓到了补丁差异，重评分日志则抓不到）；（iv）密闭评测器必须在已接受替代解上验证，而不只验证金标——重放已接受候选不需要新标注，只花容器时间。

**边界同样清晰**：结论限于已接受补丁与固定历史决策，不构成一般性策略安全保证；自适应学习稳健性未测（Study 2 固定了搜索历史与未重跑单元的分数）；单一 benchmark、少量模型家族、单一时点；金标缓存案例无流行率估计；官方测试接受是操作正确性标准，语义正确性需另行验证。

**对音视频技术上下游的关联**：音视频领域的自动评测同样大量依赖可执行验收（解码一致性比对、码流合规性检查、客观质量指标 VMAF/PSNR 的阈值门、A/B 感知测试的自动判分）。本文的直接启示是：当把这类判定接入 RL 奖励或自动模型筛选时，必须审计判定对评测环境配置（编解码器版本、参考实现依赖、网络可达的测试素材、资源配额）的敏感性——特别是“参考实现验证通过”不能推广到“任何合格替代实现都能通过”，这在存在多个合法实现路径（如不同编码器配置达到同一质量门）的场景下是结构性的误杀风险。
